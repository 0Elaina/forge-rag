# ForgeRAG 可观测性设计

## 1. 文档目的

本文档用于定义 ForgeRAG 第一版可观测性设计，承接已有需求、架构、数据库、API、RAG 核心链路、Agentic RAG 和自动化评测设计。

本文档重点说明：

1. ForgeRAG 如何记录 RAG 和 Agentic RAG 的关键执行过程。
2. `request_id`、`trace_id` 与业务记录如何关联。
3. 结构化日志、Langfuse Trace 和 PostgreSQL 业务摘要如何分工。
4. 文档入库、检索、重排、问答、Agentic RAG 和评测流程应记录哪些观测信息。
5. Langfuse 不可用时如何降级。
6. 如何避免日志和 Trace 记录不必要的敏感信息。

本文档不重复展开数据库字段、API 路径、RAG 流程、Agentic RAG 节点和评测指标细节。

------

## 2. 设计边界

### 2.1 覆盖范围

第一版可观测性覆盖以下核心链路：

```text
请求入口
  → 文档入库
  → 语义检索
  → Rerank
  → Prompt 构造
  → LLM 调用
  → 基础 RAG 问答
  → Agentic RAG 节点流转
  → 自动化评测
  → 异常与降级
```

可观测性数据主要服务于：

1. 开发调试。
2. 问题排查。
3. 检索质量分析。
4. Prompt 和模型调用分析。
5. Agentic RAG 决策路径分析。
6. 评测失败样本复盘。
7. 后续链路优化。

### 2.2 不覆盖范围

第一版暂不实现：

1. 自研完整 APM 平台。
2. 自研 Trace 可视化控制台。
3. 复杂日志采集平台。
4. 指标大屏和告警系统。
5. 分布式链路治理。
6. 生产级日志归档系统。
7. 完整审计日志平台。
8. 用户行为分析平台。

第一版优先接入 Langfuse，并配合结构化日志和业务表中的关联 ID 完成轻量可观测闭环。

------

## 3. 设计目标

ForgeRAG 可观测性设计的核心目标是：让开发者能够回答一次请求“发生了什么、为什么这样回答、失败在哪里、如何优化”。

具体目标：

| 目标       | 说明                                      |
| ---------- | ----------------------------------------- |
| 请求可追踪 | 每次核心请求应具备 `request_id`           |
| 链路可还原 | RAG、Agentic RAG 和评测流程应关联 Trace   |
| 节点可分析 | 检索、重排、模型调用和 Agent 节点应可查看 |
| 异常可定位 | 外部依赖异常和业务异常应记录失败位置      |
| 质量可复盘 | 评测失败样本可追踪到问答和 Trace          |
| 观测可降级 | Langfuse 不可用时不阻断核心业务           |
| 信息可控制 | 日志和 Trace 应避免记录密钥等敏感信息     |

------

## 4. 观测数据分层

ForgeRAG 第一版采用三层观测数据设计。

| 层级                  | 存储位置         | 职责                                     |
| --------------------- | ---------------- | ---------------------------------------- |
| 结构化日志            | 控制台或日志文件 | 本地调试、异常排查、请求状态记录         |
| Langfuse Trace / Span | Langfuse         | RAG、Agent、模型调用和 Prompt 链路追踪   |
| 业务摘要              | PostgreSQL       | 保存问答、Agent、评测等业务结果和关联 ID |

设计原则：

1. PostgreSQL 不保存完整 Trace。
2. Langfuse 保存完整链路细节。
3. 结构化日志保存必要运行过程。
4. 业务表只保存 `request_id`、`trace_id` 和关键摘要。
5. 评测结果通过 `trace_id` 关联完整执行过程。

## 5. 核心标识设计

### 5.1 标识总览

| 标识                | 作用                | 主要出现位置                   |
| ------------------- | ------------------- | ------------------------------ |
| `request_id`        | 应用请求标识        | API 响应、结构化日志、业务表   |
| `trace_id`          | Langfuse Trace 标识 | API 响应、业务表、Langfuse     |
| `span_id`           | Langfuse Span 标识  | Agent 节点、模型调用、外部调用 |
| `qa_record_id`      | 问答记录 ID         | QA 响应、评测结果、Agent 记录  |
| `agent_run_id`      | Agentic RAG 执行 ID | Agent 响应、评测结果、节点记录 |
| `eval_task_id`      | 评测任务 ID         | 评测任务、评测结果、日志       |
| `eval_result_id`    | 单条评测结果 ID     | 评测结果、失败样本分析         |
| `knowledge_base_id` | 知识库范围          | 检索、问答、评测、日志         |
| `document_id`       | 文档 ID             | 文档入库、chunk、引用、日志    |
| `chunk_id`          | 文本块 ID           | 检索结果、引用、评测、Qdrant   |

### 5.2 request_id

`request_id` 用于串联一次 HTTP 请求在应用内部的日志。

生成规则：

1. 如果客户端传入 `X-Request-Id`，优先使用客户端传入值。
2. 如果客户端未传入，由服务端生成。
3. 所有结构化日志应携带 `request_id`。
4. 核心 API 响应应返回 `request_id`。
5. 业务表中可保存 `request_id`，用于关联应用日志。

### 5.3 trace_id

`trace_id` 用于关联 Langfuse 中的一次完整执行链路。

生成规则：

1. 文档入库、基础 RAG、Agentic RAG 和评测任务可以创建 Trace。
2. 普通管理类接口不强制创建 Trace。
3. 如果 Langfuse 创建失败，`trace_id` 可以为空。
4. `trace_id` 为空不应影响核心业务流程。
5. 已创建的 `trace_id` 应写入相关业务记录。

## 6. Trace 设计

### 6.1 Trace 创建范围

第一版建议以下流程创建或关联 Trace：

| 流程             | 是否创建 Trace | 说明                         |
| ---------------- | -------------- | ---------------------------- |
| 文档上传         | 可选           | 上传本身只保存元数据         |
| 文档处理         | 是             | 记录解析、切分、向量化流程   |
| 语义检索         | 是             | 记录查询、召回结果和耗时     |
| 基础 RAG 问答    | 是             | 记录完整检索、重排、生成链路 |
| Agentic RAG 问答 | 是             | 记录节点状态流转和决策路径   |
| 评测任务         | 是             | 任务级 Trace 可选            |
| 评测样本执行     | 是             | 每条样本尽量独立关联 Trace   |
| 健康检查         | 否             | 避免产生无意义 Trace         |
| 知识库 CRUD      | 否             | 使用结构化日志即可           |

### 6.2 Trace 元数据

每个 Trace 建议携带以下元数据：

| 字段                | 说明                        |
| ------------------- | --------------------------- |
| `request_id`        | 应用请求 ID                 |
| `client_id`         | 调用方标识，可为空          |
| `knowledge_base_id` | 知识库 ID                   |
| `qa_mode`           | `basic_rag` / `agentic_rag` |
| `eval_task_id`      | 评测任务 ID，可为空         |
| `qa_record_id`      | 问答记录 ID，可为空         |
| `agent_run_id`      | Agent 执行 ID，可为空       |
| `model_name`        | 模型名称                    |
| `prompt_version`    | Prompt 版本                 |
| `environment`       | `dev` / `test` / `prod`     |

## 7. Span 设计

### 7.1 Span 划分原则

Span 用于记录一次 Trace 内部的关键步骤。

划分原则：

1. 一个 Span 对应一个明确动作。
2. Span 不应过细，避免 Trace 噪声过多。
3. 外部服务调用应单独记录 Span。
4. Agentic RAG 的关键节点应记录节点级 Span。
5. Span 中记录输入输出摘要、耗时、状态和异常。

### 7.2 推荐 Span 类型

| Span 名称           | 记录内容                                   |
| ------------------- | ------------------------------------------ |
| `document_parse`    | 文件类型、解析结果、失败原因               |
| `text_split`        | chunk 数量、切分策略、切分耗时             |
| `embedding`         | chunk 数量、模型名称、向量维度、耗时       |
| `qdrant_upsert`     | collection、point 数量、写入耗时           |
| `query_embedding`   | 查询文本摘要、模型名称、耗时               |
| `qdrant_search`     | top_k、score_threshold、召回数量、最高得分 |
| `rerank`            | 候选数量、输出数量、是否降级、耗时         |
| `prompt_build`      | Prompt 版本、上下文数量、上下文长度        |
| `llm_call`          | 模型名称、输入输出 token、耗时、状态       |
| `citation_build`    | 引用数量、引用 chunk ID                    |
| `agent_node`        | 节点名称、输入摘要、输出摘要、决策结果     |
| `evaluation_sample` | 样本 ID、状态、得分、失败原因              |

## 8. 各链路观测内容

### 8.1 文档入库链路

文档入库应记录：

| 阶段        | 记录内容                                     |
| ----------- | -------------------------------------------- |
| 处理开始    | `document_id`、`knowledge_base_id`、文件类型 |
| 解析文本    | 解析耗时、文本长度、失败原因                 |
| 文本切分    | chunk 数量、切分器名称、切分参数             |
| 向量化      | Embedding 模型、chunk 数量、耗时             |
| 写入 Qdrant | collection、point 数量、失败原因             |
| 处理结束    | 文档状态、chunk 数量、总耗时                 |

处理失败时：

1. 文档状态更新为 `failed`。
2. 失败原因写入文档记录。
3. 日志记录异常类型和失败阶段。
4. Trace 中标记失败 Span。

### 8.2 检索与 Rerank 链路

检索阶段应记录：

| 阶段       | 记录内容                               |
| ---------- | -------------------------------------- |
| 查询向量化 | query 摘要、Embedding 模型、耗时       |
| 向量检索   | top_k、score_threshold、召回数量       |
| 检索结果   | chunk ID、document ID、得分摘要        |
| Rerank     | 输入数量、输出数量、是否启用、是否降级 |
| 上下文选择 | 选中 chunk 数量、上下文长度            |

记录原则：

1. 不必在 PostgreSQL 保存完整检索过程。
2. 检索摘要可写入 Trace。
3. 用于回答的引用快照写入 `qa_citations`。
4. Rerank 异常时记录降级信息，但问答流程可继续执行。

### 8.3 基础 RAG 问答链路

基础 RAG 应记录：

| 阶段     | 记录内容                                   |
| -------- | ------------------------------------------ |
| 请求入口 | question 摘要、knowledge_base_id、配置快照 |
| 检索     | 召回数量、最高得分、检索耗时               |
| 重排     | 是否启用、是否降级、最终上下文数量         |
| Prompt   | Prompt 版本、上下文长度                    |
| LLM 调用 | 模型名称、Token、耗时、状态                |
| 引用构造 | 引用数量、引用来源                         |
| 响应结束 | `qa_record_id`、status、latency_ms         |

问答记录应保存最终状态和 `trace_id`，完整 Prompt、上下文和模型调用细节由 Langfuse 管理。

### 8.4 Agentic RAG 链路

Agentic RAG 的观测重点是状态流转和决策依据。

应记录：

| 阶段        | 记录内容                                 |
| ----------- | ---------------------------------------- |
| 请求入口    | `request_id`、`trace_id`、`agent_run_id` |
| 问题分析    | 问题类型、是否需要检索                   |
| 问题改写    | 改写结果摘要、触发原因                   |
| 检索节点    | 检索轮次、召回数量、最高得分             |
| Rerank 节点 | 是否启用、是否降级、输出数量             |
| 判断节点    | 是否二次检索、上下文是否足够、拒答原因   |
| 生成节点    | 模型名称、Token、耗时、回答状态          |
| 结束节点    | 最终状态、`qa_record_id`、`trace_id`     |

设计要求：

1. `agent_runs` 保存一次 Agentic RAG 执行摘要。
2. `agent_steps` 保存关键节点摘要。
3. 完整节点输入输出、Prompt 和模型调用细节交给 Langfuse。
4. Langfuse 不可用时，节点摘要仍应写入 `agent_steps`。
5. 节点异常后应记录失败节点和错误信息。

### 8.5 自动化评测链路

评测模块应记录：

| 阶段       | 记录内容                            |
| ---------- | ----------------------------------- |
| 任务创建   | 数据集、知识库、问答模式、配置快照  |
| 任务执行   | 开始时间、结束时间、样本数量        |
| 样本执行   | 问题摘要、状态、耗时、失败原因      |
| 检索结果   | 召回数量、最高得分、命中情况        |
| 生成结果   | 回答摘要、引用数量、Token、模型名称 |
| Agent 结果 | `agent_run_id`、最终状态、节点摘要  |
| 结果汇总   | 成功数、失败数、平均分              |

评测结果应保存必要快照，并通过 `qa_record_id`、`agent_run_id` 和 `trace_id` 关联完整链路。

## 9. 结构化日志设计

### 9.1 日志用途

结构化日志用于本地开发、异常排查和服务运行分析。

日志应覆盖：

1. 请求入口和响应结果。
2. 核心业务状态变化。
3. 文档处理状态变化。
4. 外部依赖调用异常。
5. Rerank、Langfuse 等可降级组件异常。
6. Agentic RAG 节点异常。
7. 评测任务状态变化。

### 9.2 日志字段

建议统一日志字段：

| 字段                | 说明                  |
| ------------------- | --------------------- |
| `timestamp`         | 日志时间              |
| `level`             | 日志级别              |
| `message`           | 日志消息              |
| `request_id`        | 请求 ID               |
| `trace_id`          | Trace ID，可为空      |
| `module`            | 模块名称              |
| `operation`         | 操作名称              |
| `knowledge_base_id` | 知识库 ID，可为空     |
| `document_id`       | 文档 ID，可为空       |
| `qa_record_id`      | 问答记录 ID，可为空   |
| `agent_run_id`      | Agent 执行 ID，可为空 |
| `eval_task_id`      | 评测任务 ID，可为空   |
| `latency_ms`        | 耗时，可为空          |
| `error_type`        | 错误类型，可为空      |
| `error_message`     | 错误摘要，可为空      |

### 9.3 日志级别

| 级别       | 使用场景                         |
| ---------- | -------------------------------- |
| `DEBUG`    | 本地开发调试、详细中间结果       |
| `INFO`     | 请求完成、状态变化、任务执行进度 |
| `WARNING`  | 可降级异常、非阻断问题           |
| `ERROR`    | 业务失败、外部依赖失败           |
| `CRITICAL` | 服务无法启动或核心依赖不可用     |

## 10. Langfuse 接入设计

### 10.1 接入位置

Langfuse 客户端应封装在 Infrastructure 层，不应在 API 层或业务代码中到处直接调用 SDK。

建议模块：

```text
app/
  infrastructure/
    observability/
      langfuse_client.py
  core/
    observability/
      trace_context.py
      decorators.py
  common/
    logging.py
```

设计要求：

1. Service 或 Core 通过统一封装记录 Trace。
2. 业务逻辑不直接依赖 Langfuse SDK 细节。
3. Langfuse 配置通过环境变量或配置文件管理。
4. Langfuse 异常应被捕获并降级为本地日志。

### 10.2 配置项

第一版建议配置：

| 配置项                      | 说明                     |
| --------------------------- | ------------------------ |
| `LANGFUSE_ENABLED`          | 是否启用 Langfuse        |
| `LANGFUSE_HOST`             | Langfuse 服务地址        |
| `LANGFUSE_PUBLIC_KEY`       | Public Key               |
| `LANGFUSE_SECRET_KEY`       | Secret Key               |
| `LANGFUSE_ENVIRONMENT`      | 环境标识                 |
| `OBSERVABILITY_SAMPLE_RATE` | 采样率，第一版可默认 1.0 |
| `LOG_LEVEL`                 | 日志级别                 |

敏感配置不得写死在代码中，也不得提交到 Git 仓库。

## 11. 敏感信息与脱敏策略

可观测性数据可能包含用户问题、文档片段、Prompt、模型输出和异常信息，因此需要控制记录范围。

第一版脱敏要求：

1. 不记录模型 API Key。
2. 不记录数据库密码。
3. 不记录 Langfuse Secret Key。
4. 不记录完整环境变量。
5. 不在日志中记录完整上传文件路径中的敏感部分。
6. 生产环境中可只记录 Prompt 和上下文摘要。
7. 开发环境中如需记录完整 Prompt，应通过配置显式开启。
8. 异常响应不返回内部堆栈，堆栈只进入受控日志。

建议策略：

| 数据类型   | 日志记录               | Trace 记录                       |
| ---------- | ---------------------- | -------------------------------- |
| 用户问题   | 摘要或原文，按配置控制 | 可记录，用于调试和评测           |
| 检索 chunk | ID、得分、摘要         | 可记录摘要或完整内容，按配置控制 |
| Prompt     | 默认摘要               | 开发环境可记录完整 Prompt        |
| LLM 输出   | 摘要和状态             | 可记录完整输出，按配置控制       |
| API Key    | 不记录                 | 不记录                           |
| 异常堆栈   | 受控记录               | 受控记录                         |

------

## 12. 异常与降级策略

### 12.1 Langfuse 不可用

如果 Langfuse 不可用：

1. 核心问答流程应尽量继续执行。
2. `trace_id` 可以为空。
3. 结构化日志应记录 Langfuse 异常。
4. PostgreSQL 业务记录仍应正常保存。
5. 评测结果仍应保存问答结果、评分和错误信息。
6. Agentic RAG 节点摘要仍应写入 `agent_steps`。

### 12.2 外部依赖异常

| 异常类型        | 处理方式                 | 观测要求               |
| --------------- | ------------------------ | ---------------------- |
| Qdrant 异常     | 返回向量库异常或任务失败 | 记录依赖名称、失败阶段 |
| Embedding 异常  | 文档或检索流程失败       | 记录模型名称、错误摘要 |
| Rerank 异常     | 降级使用原始检索排序     | 记录是否降级           |
| LLM 异常        | 问答失败或样本失败       | 记录模型名称、错误摘要 |
| PostgreSQL 异常 | 当前业务操作失败         | 记录数据库错误摘要     |
| Langfuse 异常   | 降级为结构化日志         | 不阻断核心流程         |

------

## 13. 测试要求

第一版至少覆盖：

| 测试类型        | 测试内容                                   |
| --------------- | ------------------------------------------ |
| request_id 测试 | 未传入时自动生成，传入时正确透传           |
| trace_id 测试   | 核心链路能够创建或关联 Trace               |
| 日志测试        | 关键日志包含 `request_id` 和模块信息       |
| QA 观测测试     | 问答记录能够保存 `trace_id`                |
| Agent 观测测试  | `agent_runs` 和 `agent_steps` 能关联 Trace |
| 评测观测测试    | `evaluation_results` 能保存 `trace_id`     |
| 降级测试        | Langfuse 不可用时核心问答不被阻断          |
| 脱敏测试        | 日志和 Trace 不记录密钥                    |
| 异常测试        | 外部依赖异常能够写入日志和业务失败原因     |

外部 Langfuse、Qdrant 和模型服务应支持 mock 或测试替身，避免自动化测试强依赖真实服务。

------

## 14. 第一版实现范围

第一版必须实现：

1. 统一 `request_id` 中间件。
2. 核心响应返回 `request_id`。
3. 基础结构化日志。
4. Langfuse 客户端封装。
5. 基础 RAG 问答 Trace。
6. Agentic RAG 节点 Trace 或节点摘要。
7. 评测结果关联 `trace_id`。
8. 问答记录保存 `trace_id`。
9. Agent 执行记录保存 `trace_id`。
10. Langfuse 不可用时降级为结构化日志。
11. 日志和 Trace 的基础脱敏策略。
12. 健康检查中体现 Langfuse 依赖状态。

第一版暂不实现：

1. 自研可观测性控制台。
2. 复杂监控告警。
3. 完整审计日志系统。
4. 分布式 Trace 平台。
5. Prometheus / Grafana 指标大屏。
6. ELK / Loki 日志平台。
7. 复杂采样和动态观测规则。
8. 长期日志归档策略。

------

## 15. 设计总结

ForgeRAG 第一版可观测性设计的重点不是搭建复杂监控平台，而是保证 RAG 后端主链路可追踪、可分析、可复盘。

设计重点如下：

1. 用 `request_id` 串联应用日志。
2. 用 `trace_id` 关联 Langfuse Trace。
3. 用 PostgreSQL 保存业务结果和关联 ID。
4. 用 Langfuse 保存完整 Trace、Span、Prompt、模型调用和 Token 信息。
5. 用结构化日志兜底记录异常和状态变化。
6. 文档入库、RAG、Agentic RAG 和评测链路都应可观测。
7. Langfuse 异常不应阻断核心业务流程。
8. 日志和 Trace 应避免记录密钥和不必要的敏感信息。
9. 第一版优先实现轻量可用的可观测闭环，后续再扩展指标、告警和日志平台。
