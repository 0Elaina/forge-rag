# ForgeRAG 需求分析

## 1. 文档目的

本文档用于对 ForgeRAG 企业知识库 Agentic RAG 后端系统进行需求分析，承接 `docs/01-project-overview.md` 中已经明确的项目背景、项目定位、项目目标、核心功能范围、非目标范围和分阶段建设路线。

`01-project-overview.md` 主要回答“ForgeRAG 是什么、为什么做、整体做哪些能力、不做哪些范围”；而本文档进一步回答“ForgeRAG 需要满足哪些具体需求、这些需求如何拆分、后续如何设计、开发和验收”。

本文档的核心目的包括：

1. **明确系统需求边界**

   将 ForgeRAG 的项目定位转化为更具体的需求范围，明确系统当前阶段需要支持的能力，以及暂不纳入当前阶段的内容，避免需求范围在开发过程中不断扩大。

2. **指导后续设计文档编写**

   本文档将作为后续架构设计、数据库设计、接口设计、RAG 核心链路设计、Agentic RAG 流程设计、评测设计和可观测性设计的重要依据。

3. **指导分阶段开发任务拆解**

   本文档会将项目能力拆解为功能性需求、非功能性需求、数据需求、接口需求和验收标准，使后续每个开发阶段都能对应明确的需求来源。

4. **保证需求可开发、可测试、可验收**

   本文档中的需求描述应尽量具备可实现性和可验证性，避免只写抽象目标。每个核心需求都应能够在后续转化为接口、数据模型、服务逻辑、测试用例或评测指标。

5. **保持项目目标与工程实现一致**

   ForgeRAG 的目标不是构建完整 Web 平台，也不是训练大语言模型，而是构建一个可被前端、后端服务或智能 Agent 调用的 RAG 后端能力系统。因此，本文档会围绕企业知识库管理、文档入库、语义检索、Rerank、带引用问答、Agentic RAG、自动化评测、可观测性和工程规范展开需求分析。

本文档不负责展开具体代码实现方案，也不详细定义数据库字段、API 请求响应字段或 LangGraph 节点实现细节。这些内容将在后续专项设计文档中进一步说明。





## 2. 需求分析范围

本文档的需求分析范围以 `docs/01-project-overview.md` 中已经明确的项目定位、核心功能范围、非目标范围和分阶段建设路线为基础。ForgeRAG 当前阶段的核心目标是构建一个企业知识库 Agentic RAG 后端系统，因此本文档会围绕 RAG 后端能力、Agentic RAG 流程控制、自动化评测、可观测性和企业级工程规范展开需求分析。

本文档不会将 ForgeRAG 扩展为完整 Web 平台、商业化 SaaS 平台、模型训练平台或大规模分布式系统。所有需求分析都应服务于当前项目主线：构建一个可被前端、业务后端、自动化脚本或智能 Agent 调用的 RAG 后端能力系统。

### 2.1 覆盖范围

本文档主要覆盖以下需求范围。

#### 2.1.1 知识库管理需求

系统需要支持企业知识库的基础管理能力，包括知识库创建、查询、更新、删除、状态管理和基础元数据维护。

知识库是 ForgeRAG 的核心业务边界。后续文档、文本块、向量数据、检索请求、问答记录和评测任务都需要围绕知识库进行组织。

#### 2.1.2 文档管理需求

系统需要支持文档上传、文档元数据保存、文档状态管理、文档查询和文档删除等能力。

文档管理需求主要关注原始文档从上传到处理完成的生命周期管理，包括文档所属知识库、文件类型、文件大小、处理状态、失败原因和处理时间等信息。

#### 2.1.3 文档解析与切分需求

系统需要支持将原始文档解析为文本内容，并按照合理的切分策略生成适合检索的文本块。

该部分需求主要关注：

1. 文档内容提取。
2. 文本清洗。
3. 文本切分。
4. chunk 元数据保留。
5. 文本块与原始文档之间的来源关联。

文档解析与切分结果会直接影响后续向量化、语义检索、引用溯源和评测效果。

#### 2.1.4 向量化入库需求

系统需要支持将文本块转换为向量表示，并写入 Qdrant 向量数据库。

该部分需求主要关注：

1. Embedding 模型调用。
2. 文本块向量生成。
3. 向量数据写入。
4. 向量 metadata 管理。
5. PostgreSQL 业务数据与 Qdrant 向量数据之间的关联。
6. 文档删除或重新处理时的向量同步清理。

#### 2.1.5 语义检索需求

系统需要支持根据用户问题从指定知识库中召回相关文本块。

该部分需求主要关注：

1. 查询问题向量化。
2. 基于知识库范围的向量检索。
3. top_k、score_threshold 等检索参数控制。
4. 检索结果返回。
5. 检索结果与原始文档来源的关联。

语义检索是 RAG 问答链路中的核心能力之一。

#### 2.1.6 Rerank 重排需求

系统需要支持对语义检索召回结果进行二次排序，以提高最终上下文的相关性和可用性。

该部分需求主要关注：

1. 接收候选文本块。
2. 根据用户问题和候选文本内容计算相关性。
3. 对候选结果重新排序。
4. 过滤低质量或低相关性文本块。
5. 为问答生成阶段提供更可靠的上下文。

#### 2.1.7 带引用问答需求

系统需要支持基于知识库上下文生成回答，并返回引用来源。

该部分需求主要关注：

1. 接收用户问题和知识库范围。
2. 执行检索和重排。
3. 构造 RAG Prompt。
4. 调用大语言模型生成回答。
5. 返回答案内容。
6. 返回引用片段、文档来源和相关元数据。
7. 在缺少可靠上下文时避免无依据生成。

带引用问答是 ForgeRAG 对外提供的核心能力。

#### 2.1.8 Agentic RAG 流程需求

系统需要支持 Agentic RAG 流程控制，使 RAG 问答不再局限于固定的“检索—生成”路径。

该部分需求主要关注：

1. 判断问题是否需要检索。
2. 判断问题是否需要改写。
3. 根据检索结果判断是否需要二次检索。
4. 判断上下文是否足以支持回答。
5. 在知识依据不足时执行拒答策略。
6. 记录流程节点的输入、输出和状态变化。

Agentic RAG 需求会在后续专项设计文档中进一步细化为状态结构、节点设计和流程图。

#### 2.1.9 RAG 自动化评测需求

系统需要支持对 RAG 检索质量、回答质量、上下文利用情况和引用质量进行评测。

该部分需求主要关注：

1. 评测数据集管理。
2. 评测问题管理。
3. 标准答案或参考答案管理。
4. 期望引用管理。
5. 批量执行评测任务。
6. 记录评测结果。
7. 对比不同切分策略、检索参数、Rerank 策略和 Prompt 版本的效果。

自动化评测是 ForgeRAG 持续优化检索和回答效果的重要依据。

#### 2.1.10 可观测性与链路追踪需求

系统需要支持记录 RAG 和 Agentic RAG 请求的关键执行过程，使开发者能够分析系统行为和定位问题。

该部分需求主要关注：

1. 记录用户问题。
2. 记录检索查询。
3. 记录召回结果和重排结果。
4. 记录 Prompt 输入。
5. 记录 LLM 输出。
6. 记录 Token 消耗和调用耗时。
7. 记录 Agentic RAG 节点流转。
8. 记录异常信息和失败原因。

可观测性需求需要与日志系统、Langfuse 接入和评测结果关联设计保持一致。

#### 2.1.11 系统工程需求

系统需要具备基础企业级后端工程能力，保证项目可维护、可测试、可部署和可持续迭代。

该部分需求主要关注：

1. FastAPI 分层架构。
2. 统一 API 响应结构。
3. 全局异常处理。
4. 配置管理。
5. 结构化日志。
6. PostgreSQL 数据持久化。
7. Qdrant 向量库集成。
8. SQLAlchemy 与 Alembic 数据库迁移。
9. pytest 自动化测试。
10. Docker Compose 本地部署。
11. GitHub Actions 基础 CI 检查。

### 2.2 不覆盖范围

为了保证项目边界清晰，本文档当前阶段不展开以下需求。

#### 2.2.1 不展开完整 Web 前端需求

ForgeRAG 当前阶段不开发完整 Web 前端，因此本文档不分析完整管理后台、用户控制台、聊天页面、可视化运营平台等前端需求。

系统只需要保证 API 设计清晰、响应结构统一、错误信息明确，方便后续前端应用或其他调用方接入。

#### 2.2.2 不展开复杂权限系统需求

ForgeRAG 第一版不优先实现复杂权限系统。

本文档可以保留基础用户身份、知识库归属和权限扩展点，但不展开以下复杂权限需求：

1. 完整 RBAC 权限模型。
2. 多租户组织架构。
3. 部门级数据隔离。
4. 细粒度文档访问控制。
5. 企业单点登录。
6. 审批流和权限继承机制。

复杂权限能力可以作为后续版本扩展方向，不作为当前阶段核心需求。

#### 2.2.3 不展开大规模分布式架构需求

ForgeRAG 当前阶段以单体后端服务和 Docker Compose 本地部署为主，不分析大规模分布式系统需求。

本文档不展开以下内容：

1. Kubernetes 集群部署。
2. 微服务拆分。
3. 服务注册与发现。
4. 分布式事务。
5. 消息队列集群。
6. 多副本高可用架构。
7. 多地域部署。
8. 分布式链路治理平台。

这些能力可以作为后续工程扩展方向，不纳入当前需求分析主线。

#### 2.2.4 不展开模型训练需求

ForgeRAG 不负责训练大语言模型、Embedding 模型或 Rerank 模型。

本文档不分析以下需求：

1. 大语言模型预训练。
2. 指令微调。
3. 强化学习训练。
4. 私有模型训练平台。
5. GPU 训练集群管理。
6. 自研 Embedding 模型训练。
7. 自研 Rerank 模型训练。

系统重点是调用已有模型能力，并围绕 RAG 链路进行工程化集成。

#### 2.2.5 不展开完整商业化 SaaS 平台需求

ForgeRAG 不是完整商业化 SaaS 知识库平台，因此本文档不展开以下需求：

1. 租户套餐。
2. 计费系统。
3. 企业组织架构管理。
4. 完整运营后台。
5. 商业化插件市场。
6. 客户支持系统。
7. 复杂审计报表。
8. 多区域云部署管理。

当前阶段项目重点是企业级规范的 RAG 后端能力建设，而不是完整商业产品设计。

#### 2.2.6 不展开高级 RAG 扩展需求

ForgeRAG 当前阶段优先完成稳定的文本知识库 RAG 后端闭环，不在第一版展开所有高级 RAG 能力。

本文档不深入分析以下高级扩展需求：

1. 多模态 RAG。
2. 知识图谱增强 RAG。
3. 多 Agent 协作。
4. 长期记忆系统。
5. 自动工具调用市场。
6. 跨系统知识同步。
7. 复杂工作流编排平台。

这些能力可以作为项目后续演进方向，但不作为当前阶段需求分析重点。

### 2.3 范围控制原则

本文档在需求分析过程中遵循以下范围控制原则：

1. **围绕 RAG 后端主链路展开**

   所有需求优先服务于文档入库、语义检索、重排、带引用问答、Agentic RAG、评测和观测这一主链路。

2. **优先保证核心闭环可运行**

   第一阶段应优先完成可运行、可测试、可评测、可观测的后端闭环，而不是堆叠大量高级功能。

3. **需求必须能够落地实现**

   需求描述应尽量能够转化为后续接口、数据模型、服务逻辑、测试用例或评测指标。

4. **需求必须能够验收**

   每个核心需求后续都应能够通过接口测试、单元测试、链路测试、评测任务或运行日志进行验证。

5. **保持与项目概述一致**

   本文档中的需求分析不得偏离 `docs/01-project-overview.md` 已经确定的项目定位、核心功能范围和非目标范围。

通过以上范围约束，ForgeRAG 的需求分析能够保持清晰、可控和可执行，为后续架构设计、数据库设计、接口设计和分阶段开发提供稳定依据。





## 3. 用户角色与使用场景

ForgeRAG 是一个通过 API 对外提供能力的企业知识库 Agentic RAG 后端系统。系统的直接使用对象并不局限于最终用户，还包括前端应用、业务后端服务、智能 Agent、开发者、评测人员和运维人员。

本章从需求分析角度梳理不同角色的典型使用场景，并明确这些角色对 ForgeRAG 提出的系统需求。后续功能需求、接口需求、数据需求和验收标准都应围绕这些角色与场景展开。

### 3.1 前端应用

前端应用不是 ForgeRAG 当前阶段的开发重点，但 ForgeRAG 需要为后续前端接入提供稳定、清晰、可调用的 API 能力。前端应用可以基于 ForgeRAG 构建知识库管理页面、文档上传页面、智能问答页面、问答历史页面和评测结果展示页面。

**典型使用场景：**

1. 用户在前端页面创建一个新的知识库。
2. 用户查看已有知识库列表和知识库详情。
3. 用户向指定知识库上传文档。
4. 用户查看文档解析、切分和向量化处理状态。
5. 用户在问答页面向指定知识库提问。
6. 前端展示系统返回的答案、引用片段、文档来源和相关元数据。
7. 前端展示问答历史、评测任务状态和评测结果。

**对应系统需求：**

1. 系统应提供知识库创建、查询、更新和删除 API。
2. 系统应提供文档上传、文档列表查询、文档详情查询和文档删除 API。
3. 系统应提供文档处理状态查询能力。
4. 系统应提供基于知识库的问答 API。
5. 系统应在问答结果中返回答案内容和引用来源。
6. 系统应提供统一 API 响应结构，方便前端统一处理成功、失败、空数据和异常状态。
7. 系统应提供清晰的错误码和错误信息，便于前端展示用户可理解的提示。
8. 系统应提供自动生成的接口文档，方便前端开发和联调。

### 3.2 业务后端服务

业务后端服务可以通过 ForgeRAG 提供的 API，将企业知识检索和问答能力集成到已有业务系统中。对业务后端而言，ForgeRAG 是一个独立的 RAG 能力服务，而不是某个业务系统内部的临时代码模块。

**典型使用场景：**

1. 客服系统调用 ForgeRAG，根据企业知识库生成带依据的回复建议。
2. 工单系统调用 ForgeRAG，基于历史问题和解决方案辅助分析工单。
3. 研发知识库系统调用 ForgeRAG，检索接口规范、技术文档、故障记录和项目经验。
4. 企业内部搜索系统调用 ForgeRAG，提供语义检索能力。
5. 自动化办公系统调用 ForgeRAG，从制度文档、流程规范和项目资料中获取答案。
6. 其他业务服务将用户问题、知识库范围和检索参数传递给 ForgeRAG，获取结构化问答结果。

**对应系统需求：**

1. 系统应通过 REST API 对外提供核心能力。
2. 系统应支持业务调用方指定知识库范围。
3. 系统应支持返回结构化问答结果，包含答案、引用、来源文档和相关元数据。
4. 系统应支持返回明确的失败原因，例如知识库不存在、文档未完成入库、检索结果不足或模型调用失败。
5. 系统应支持记录业务调用过程，便于问题追踪。
6. 系统应具备基础的接口稳定性，避免调用方依赖频繁变化的接口结构。
7. 系统应预留后续鉴权、调用方标识和访问控制扩展点。

### 3.3 智能 Agent

智能 Agent 可以将 ForgeRAG 作为外部知识工具，在执行复杂任务时调用系统提供的检索、问答和引用能力。对 Agent 来说，ForgeRAG 既可以是一个普通工具 API，也可以是一个内部具备 Agentic RAG 流程控制的知识服务。

**典型使用场景：**

1. Agent 在回答用户问题前，调用 ForgeRAG 检索企业知识库。
2. Agent 根据 ForgeRAG 返回的引用片段生成更可靠的最终回答。
3. Agent 在任务执行过程中查询项目规范、接口文档、运维手册或历史记录。
4. Agent 根据 ForgeRAG 返回的检索结果判断是否继续执行任务。
5. Agent 调用 ForgeRAG 获取带引用的答案，并将引用来源展示给用户。
6. ForgeRAG 内部通过 Agentic RAG 流程判断是否检索、是否改写问题、是否二次检索或是否拒答。

**对应系统需求：**

1. 系统应提供可被 Agent 调用的检索 API 或问答 API。
2. 系统应返回结构化结果，而不是只返回自然语言文本。
3. 系统应在回答中包含引用来源，便于 Agent 判断答案依据。
4. 系统应支持在知识依据不足时返回拒答或无法回答提示。
5. 系统应支持问题改写、二次检索和上下文充分性判断等 Agentic RAG 能力。
6. 系统应记录 Agentic RAG 流程中的关键节点输入、输出和状态变化。
7. 系统应避免在缺少知识依据时强行生成看似确定的回答。

### 3.4 开发者

开发者是 ForgeRAG 的主要建设者和调试者，关注系统架构是否清晰、接口是否稳定、代码是否可维护、RAG 链路是否可调试、测试是否覆盖关键逻辑。

**典型使用场景：**

1. 开发者通过接口文档调试知识库、文档、检索、问答和评测接口。
2. 开发者查看日志，分析文档入库失败、向量写入失败或模型调用失败原因。
3. 开发者通过链路追踪查看一次 RAG 请求的完整执行过程。
4. 开发者根据评测结果调整文本切分策略、检索参数、Rerank 策略和 Prompt 模板。
5. 开发者编写单元测试、接口测试和核心链路测试。
6. 开发者根据分层架构维护 API 层、Service 层、Repository 层、Core 层和 Infrastructure 层代码。

**对应系统需求：**

1. 系统应具备清晰的后端分层结构。
2. 系统应提供统一的配置管理方式。
3. 系统应提供统一响应结构和全局异常处理机制。
4. 系统应记录结构化日志，便于定位问题。
5. 系统应支持查看 RAG 请求链路，包括检索、重排、Prompt、模型输出和引用来源。
6. 系统应提供基础测试能力，覆盖核心 Service、Repository 和 RAG 链路。
7. 系统应具备清晰的文档体系，包括项目概述、需求分析、架构设计、接口设计和部署说明。
8. 系统应支持本地快速启动，降低开发调试成本。

### 3.5 评测人员

评测人员关注 RAG 系统的效果是否稳定、检索结果是否相关、回答是否准确、引用是否可靠。评测人员可以是开发者本人，也可以是负责质量验证的成员。

**典型使用场景：**

1. 评测人员创建或维护一组评测问题。
2. 评测人员为问题配置参考答案、期望引用或评测标签。
3. 评测人员批量运行 RAG 问答评测任务。
4. 评测人员查看每个问题的检索结果、生成答案和引用来源。
5. 评测人员分析不同切分策略、检索参数、Rerank 策略和 Prompt 版本的效果差异。
6. 评测人员根据评测结果提出优化方向。

**对应系统需求：**

1. 系统应支持评测数据集管理。
2. 系统应支持评测问题、参考答案和期望引用的管理。
3. 系统应支持批量执行评测任务。
4. 系统应记录每次评测对应的检索结果、生成结果、引用来源和评测得分。
5. 系统应支持对比不同实验配置下的评测结果。
6. 系统应支持将评测结果与链路追踪数据关联，便于分析失败原因。
7. 系统应支持导出或查询评测结果，为后续优化提供依据。

### 3.6 运维人员

运维人员关注 ForgeRAG 是否能够稳定运行、是否容易部署、是否容易排查问题。当前阶段 ForgeRAG 不追求复杂生产级运维平台，但仍需要具备基础的可部署、可配置、可观测和可排查能力。

**典型使用场景：**

1. 运维人员通过 Docker Compose 启动 FastAPI、PostgreSQL、Qdrant 和 Langfuse 等组件。
2. 运维人员查看服务运行状态，确认各组件是否正常启动。
3. 运维人员通过日志定位接口异常、数据库异常、向量库异常和模型调用异常。
4. 运维人员通过环境变量管理数据库连接、模型配置、向量库地址和日志级别。
5. 运维人员在服务异常时根据错误日志和链路追踪信息定位问题。
6. 运维人员根据部署文档复现本地开发或演示环境。

**对应系统需求：**

1. 系统应提供 Docker Compose 本地部署方案。
2. 系统应提供 `.env` 或环境变量配置方式。
3. 系统应提供健康检查接口。
4. 系统应记录关键运行日志和异常日志。
5. 系统应支持查看外部依赖组件的连接状态。
6. 系统应提供基础部署说明文档。
7. 系统应避免将数据库密码、模型密钥等敏感配置硬编码在代码中。

### 3.7 用户角色与需求总结

ForgeRAG 的主要用户角色与需求可以概括如下：

| 用户角色     | 典型使用场景                              | 核心需求                                           |
| ------------ | ----------------------------------------- | -------------------------------------------------- |
| 前端应用     | 展示知识库、上传文档、发起问答、展示引用  | 稳定 API、统一响应、清晰错误信息、引用返回         |
| 业务后端服务 | 将 RAG 能力集成到客服、工单、知识库等系统 | REST API、结构化结果、知识库范围控制、调用记录     |
| 智能 Agent   | 将 ForgeRAG 作为知识检索与问答工具        | 工具化接口、引用来源、拒答提示、Agentic RAG 流程   |

## 4. 核心业务流程

ForgeRAG 的核心业务流程围绕企业知识库 RAG 后端系统展开，主要包括知识库创建流程、文档入库流程、基础 RAG 问答流程、Agentic RAG 问答流程、RAG 自动化评测流程和可观测性记录流程。

这些流程共同构成 ForgeRAG 的主要业务闭环：

```text
知识库创建 → 文档上传 → 文档解析 → 文本切分 → 向量化入库 → 语义检索 → Rerank 重排 → 带引用问答 → Agentic RAG 流程控制 → 自动化评测 → 链路追踪与优化
```

本章只描述业务流程和关键要求，不展开具体 API 字段、数据库字段、LangGraph 节点实现或代码结构。这些内容将在后续架构设计、数据库设计、接口设计、RAG 链路设计和 Agentic RAG 设计文档中进一步细化。

### 4.1 知识库创建流程

知识库是 ForgeRAG 中组织企业文档、文本块、向量数据、问答记录和评测任务的核心业务边界。系统中的文档入库、检索问答和评测任务都应围绕某个具体知识库展开。

**流程步骤：**

1. 调用方提交知识库创建请求。
2. 系统校验知识库名称、描述等基础信息。
3. 系统创建知识库记录。
4. 系统初始化知识库状态。
5. 系统返回知识库基础信息。
6. 后续文档、chunk、向量数据、问答记录和评测任务通过知识库 ID 与该知识库建立关联。

**关键要求：**

1. 系统应支持创建多个知识库。
2. 每个知识库应具备唯一标识。
3. 系统应支持查询知识库列表和知识库详情。
4. 系统应支持更新知识库基础信息。
5. 系统应支持删除知识库或禁用知识库。
6. 删除知识库时，应考虑关联文档、文本块、向量数据、问答记录和评测任务的处理策略。
7. 后续所有文档入库、检索问答和评测操作都应能够指定知识库范围。

**流程产物：**

1. 知识库记录。
2. 知识库唯一标识。
3. 知识库状态。
4. 后续业务数据的归属边界。

### 4.2 文档入库流程

文档入库流程是 ForgeRAG 的数据准备链路，负责将原始企业文档转换为可被语义检索使用的文本块和向量数据。该流程的质量会直接影响后续检索结果和问答效果。

**流程步骤：**

```text
上传文档 → 保存文档元数据 → 解析文本 → 清洗文本 → 文本切分 → 保存 chunk → 生成 Embedding → 写入 Qdrant → 更新文档处理状态
```

具体过程如下：

1. 调用方选择目标知识库并上传文档。
2. 系统校验知识库是否存在、文档类型是否支持、文件大小是否符合限制。
3. 系统保存原始文档或文档访问路径。
4. 系统保存文档元数据，例如文件名、文件类型、文件大小、所属知识库和初始处理状态。
5. 系统解析文档内容，将原始文件转换为文本内容。
6. 系统对解析出的文本进行基础清洗，去除无效空白、重复噪声或明显无意义内容。
7. 系统按照切分策略将长文本拆分为多个 chunk。
8. 系统为每个 chunk 保存来源信息，例如所属知识库、所属文档、chunk 序号、页码或段落位置。
9. 系统调用 Embedding 模型，将 chunk 文本转换为向量。
10. 系统将向量数据写入 Qdrant，并将知识库 ID、文档 ID、chunk ID 和来源信息写入 payload。
11. 系统更新文档处理状态，例如处理中、处理成功或处理失败。
12. 如果流程失败，系统应记录失败原因，方便后续重试或排查。

**关键要求：**

1. 系统应保证文档元数据先于解析和向量化流程保存。
2. 系统应能够记录文档处理状态。
3. 系统应能够记录文档处理失败原因。
4. 系统应保证 PostgreSQL 中的文档、chunk 数据与 Qdrant 中的向量数据可以关联。
5. 系统应支持按知识库维度隔离文档和向量检索范围。
6. 系统应支持文档删除时同步处理关联 chunk 和向量数据。
7. 系统应为后续重新入库或失败重试预留能力。
8. 系统应避免部分入库成功但状态不可追踪的情况。

**流程产物：**

1. 文档元数据记录。
2. 文档处理状态。
3. 文本块 chunk 记录。
4. 文本块来源信息。
5. Qdrant 向量数据。
6. PostgreSQL 与 Qdrant 的关联标识。

### 4.3 基础 RAG 问答流程

基础 RAG 问答流程是 ForgeRAG 对外提供知识库问答能力的核心链路。该流程基于用户问题从指定知识库中检索相关文档片段，并将检索结果作为上下文提供给大语言模型生成回答。

**流程步骤：**

```text
接收问题 → 校验知识库 → 问题向量化 → 向量检索 → Rerank 重排 → 构造 Prompt → 调用 LLM → 返回答案和引用
```

具体过程如下：

1. 调用方提交用户问题，并指定目标知识库。
2. 系统校验知识库是否存在、是否可用。
3. 系统校验问题内容是否为空或明显无效。
4. 系统调用 Embedding 模型，将用户问题转换为查询向量。
5. 系统基于知识库范围在 Qdrant 中执行向量检索。
6. 系统获取候选文本块及其相似度得分。
7. 系统根据需要调用 Rerank 模块，对候选文本块进行二次排序。
8. 系统选择最终上下文。
9. 系统根据问题和上下文构造 RAG Prompt。
10. 系统调用 LLM 生成回答。
11. 系统返回答案内容、引用来源和相关元数据。
12. 系统记录问答请求、检索结果、生成结果和执行耗时。

**关键要求：**

1. 系统应支持按知识库范围进行检索。
2. 系统应支持配置检索数量和相似度阈值。
3. 系统应支持对召回结果进行 Rerank。
4. 系统应在回答中返回引用来源。
5. 引用来源应能够关联到知识库、文档和 chunk。
6. 当检索结果不足以支持回答时，系统应返回无法回答提示，而不是强行生成无依据答案。
7. 系统应记录问答过程，便于后续调试、追踪和评测。
8. 系统应保证返回结构适合前端、后端服务或 Agent 调用。

**流程产物：**

1. 用户问题记录。
2. 检索结果。
3. Rerank 结果。
4. Prompt 输入。
5. LLM 回答。
6. 引用来源。
7. 问答记录。
8. 链路追踪数据。

### 4.4 Agentic RAG 问答流程

Agentic RAG 问答流程是在基础 RAG 问答流程上的增强。它不再固定执行单一的“检索—生成”流程，而是根据用户问题和中间结果动态决定是否检索、是否改写问题、是否二次检索、是否生成回答或是否拒答。

**流程步骤：**

```text
接收问题 → 问题分析 → 判断是否需要检索 → 问题改写 → 执行检索 → 判断是否需要二次检索 → 判断上下文是否足够 → 生成回答或执行拒答
```

具体过程如下：

1. 调用方提交用户问题，并指定目标知识库或业务上下文。
2. 系统对问题进行初步分析，识别问题类型和检索需求。
3. 系统判断该问题是否需要检索知识库。
4. 如果问题可以直接回答，系统可以进入直接回答流程。
5. 如果问题需要知识库支持，系统判断问题是否需要改写。
6. 如果问题表达不清晰，系统生成改写后的检索查询。
7. 系统使用原始问题或改写问题执行语义检索。
8. 系统根据检索结果质量判断是否需要二次检索。
9. 如果需要二次检索，系统调整查询并再次检索。
10. 系统对最终候选上下文进行相关性判断。
11. 如果上下文足以支持回答，系统生成带引用的答案。
12. 如果上下文不足以支持回答，系统执行拒答策略。
13. 系统记录每个流程节点的输入、输出、判断结果和状态变化。

**关键要求：**

1. 系统应支持以状态流转方式组织 Agentic RAG 流程。
2. 系统应支持问题分析节点。
3. 系统应支持是否检索的判断逻辑。
4. 系统应支持问题改写。
5. 系统应支持二次检索。
6. 系统应支持上下文充分性判断。
7. 系统应支持拒答策略。
8. 系统应返回最终回答、引用来源或拒答原因。
9. 系统应记录每个节点的执行过程，便于调试和观测。
10. 系统应避免 Agentic 流程过度复杂，第一版应优先保证核心路径可运行。

**流程产物：**

1. Agentic RAG 状态记录。
2. 原始问题。
3. 改写问题。
4. 检索判断结果。
5. 一次或多次检索结果。
6. 上下文充分性判断结果。
7. 最终回答或拒答结果。
8. 节点级链路追踪数据。

### 4.5 RAG 自动化评测流程

RAG 自动化评测流程用于评估 ForgeRAG 的检索质量、回答质量、上下文利用情况和引用质量。该流程为后续优化文本切分策略、检索参数、Rerank 策略和 Prompt 模板提供依据。

**流程步骤：**

```text
准备评测集 → 创建评测任务 → 批量执行问答 → 记录检索和生成结果 → 计算或记录评测结果 → 对比分析 → 输出优化方向
```

具体过程如下：

1. 评测人员创建或导入评测数据集。
2. 系统保存评测问题、参考答案、期望引用和评测标签。
3. 评测人员创建评测任务，选择目标知识库和评测配置。
4. 系统批量执行 RAG 或 Agentic RAG 问答流程。
5. 系统记录每个问题对应的检索结果、重排结果、最终答案和引用来源。
6. 系统根据评测规则或评分模型记录评测结果。
7. 系统汇总评测任务结果。
8. 评测人员对比不同配置下的效果差异。
9. 开发者根据评测结果优化切分策略、检索参数、Rerank 策略或 Prompt 模板。

**关键要求：**

1. 系统应支持评测数据集管理。
2. 系统应支持批量执行评测任务。
3. 系统应记录每条评测样本的完整问答过程。
4. 系统应记录检索结果、生成结果和引用结果。
5. 系统应支持评测结果查询。
6. 系统应支持不同实验配置之间的结果对比。
7. 系统应支持将评测结果与 Trace 数据关联。
8. 系统应服务于 RAG 链路持续优化，而不是只作为一次性测试脚本。

**流程产物：**

1. 评测数据集。
2. 评测任务。
3. 评测样本执行记录。
4. 检索结果记录。
5. 生成结果记录。
6. 评测结果。
7. 优化依据。

### 4.6 可观测性与链路追踪流程

可观测性与链路追踪流程贯穿 ForgeRAG 的文档入库、检索问答、Agentic RAG 和自动化评测过程。它的目标是让开发者能够理解系统每一步做了什么、为什么这样回答、失败发生在哪里，以及如何进行优化。

**流程步骤：**

```text
接收请求 → 创建 Trace → 记录关键节点输入输出 → 记录外部服务调用 → 记录结果和异常 → 关联业务记录 → 支持后续分析
```

具体过程如下：

1. 系统接收文档入库、问答或评测请求。
2. 系统为关键请求创建追踪记录。
3. 系统记录请求输入，例如用户问题、知识库 ID、文档 ID 或评测任务 ID。
4. 系统记录检索查询、召回结果和重排结果。
5. 系统记录 Prompt 输入和 LLM 输出。
6. 系统记录 Embedding、Qdrant、Rerank、LLM 等外部调用的耗时和结果。
7. 系统记录 Token 消耗、模型名称和调用参数。
8. 系统记录 Agentic RAG 节点输入、输出和状态变化。
9. 系统记录异常信息和失败原因。
10. 系统将链路追踪数据与问答记录、评测记录或文档处理记录建立关联。
11. 开发者通过追踪数据分析系统行为并优化链路。

**关键要求：**

1. 系统应在关键链路中记录可观测性数据。
2. 系统应支持追踪一次 RAG 请求的完整过程。
3. 系统应支持追踪 Agentic RAG 节点流转。
4. 系统应支持记录外部模型和向量库调用情况。
5. 系统应支持记录异常和失败原因。
6. 系统应避免记录不必要的敏感信息。
7. 系统应使可观测性数据能够服务于调试、评测和优化。
8. 系统应保证即使观测工具不可用，核心业务流程也应尽量具备降级能力。

**流程产物：**

1. Trace 记录。
2. 节点执行记录。
3. 模型调用记录。
4. 检索与重排记录。
5. 异常记录。
6. 问答记录与 Trace 的关联。
7. 评测记录与 Trace 的关联。

### 4.7 核心流程总结

ForgeRAG 的核心业务流程可以概括如下：

| 流程                   | 输入                 | 主要处理                                           | 输出                      |
| ---------------------- | -------------------- | -------------------------------------------------- | ------------------------- |
| 知识库创建流程         | 知识库名称、描述     | 校验信息、创建知识库、初始化状态                   | 知识库记录                |
| 文档入库流程           | 文档文件、知识库 ID  | 解析、清洗、切分、Embedding、写入向量库            | 文档记录、chunk、向量数据 |
| 基础 RAG 问答流程      | 用户问题、知识库 ID  | 向量检索、Rerank、Prompt、LLM 生成                 | 答案、引用、问答记录      |
| Agentic RAG 问答流程   | 用户问题、知识库 ID  | 问题分析、问题改写、检索判断、二次检索、生成或拒答 | 答案或拒答结果、节点记录  |
| RAG 自动化评测流程     | 评测数据集、评测配置 | 批量问答、记录结果、计算评分、对比分析             | 评测结果、优化依据        |
| 可观测性与链路追踪流程 | 请求上下文、执行过程 | 记录 Trace、节点、外部调用、异常和耗时             | 可分析的链路追踪数据      |

通过以上核心业务流程，ForgeRAG 可以形成从知识库构建、文档入库、知识检索、问答生成、智能流程控制，到效果评测和链路观测的完整后端业务闭环。

知识库管理模块负责维护企业知识库的基础信息和业务边界。系统中的文档、chunk、向量数据、问答记录和评测任务都应能够归属于某个知识库。

| 编号      | 需求描述                           | 验收要点                                                     |
| --------- | ---------------------------------- | ------------------------------------------------------------ |
| FR-KB-001 | 系统应支持创建知识库               | 调用创建接口后，数据库中生成知识库记录，并返回知识库唯一标识 |
| FR-KB-002 | 系统应支持查询知识库列表           | 可返回知识库列表，至少包含知识库 ID、名称、描述、状态、创建时间等信息 |
| FR-KB-003 | 系统应支持查询知识库详情           | 通过知识库 ID 可以查询对应知识库的基础信息                   |
| FR-KB-004 | 系统应支持更新知识库基础信息       | 可以修改知识库名称、描述、状态等可编辑字段                   |
| FR-KB-005 | 系统应支持删除或禁用知识库         | 删除或禁用后，该知识库不应继续作为普通问答和文档入库的可用目标 |
| FR-KB-006 | 系统应支持知识库状态管理           | 知识库应至少具备正常、禁用或删除等状态表达                   |
| FR-KB-007 | 系统应支持按知识库维度组织业务数据 | 文档、chunk、向量数据、问答记录和评测任务应能关联到知识库    |
| FR-KB-008 | 系统应在知识库不存在时返回明确错误 | 调用不存在的知识库 ID 时，应返回统一错误结构和明确错误信息   |

### 5.2 文档管理需求

文档管理模块负责管理进入 ForgeRAG 的原始文档，是文档解析、切分和向量化入库流程的入口。

| 编号       | 需求描述                       | 验收要点                                                     |
| ---------- | ------------------------------ | ------------------------------------------------------------ |
| FR-DOC-001 | 系统应支持向指定知识库上传文档 | 上传文档时必须指定知识库，上传成功后生成文档记录             |
| FR-DOC-002 | 系统应保存文档基础元数据       | 文档记录应包含文件名、文件类型、文件大小、所属知识库、上传时间、处理状态等信息 |
| FR-DOC-003 | 系统应支持查询文档列表         | 可按知识库查询文档列表，并返回文档基础信息和处理状态         |
| FR-DOC-004 | 系统应支持查询文档详情         | 通过文档 ID 可以查询文档元数据、处理状态和失败原因           |
| FR-DOC-005 | 系统应支持删除文档             | 删除文档时，应处理该文档关联的 chunk 和向量数据              |
| FR-DOC-006 | 系统应支持文档处理状态流转     | 文档应支持上传成功、处理中、处理成功、处理失败等状态         |
| FR-DOC-007 | 系统应记录文档处理失败原因     | 当解析、切分、向量化或写入向量库失败时，应保存失败原因       |
| FR-DOC-008 | 系统应限制不支持的文件类型     | 上传不支持的文件类型时，应返回明确错误信息                   |
| FR-DOC-009 | 系统应限制超出大小的文件       | 上传超过限制的文件时，应拒绝处理并返回明确错误信息           |
| FR-DOC-010 | 系统应为文档重新处理预留能力   | 对处理失败或需要更新的文档，应预留重新解析和重新入库的扩展点 |

### 5.3 文档解析与切分需求

文档解析与切分模块负责将原始文档转换为适合检索的文本块。该模块直接影响后续向量化、语义检索、引用溯源和评测效果。

| 编号         | 需求描述                           | 验收要点                                                     |
| ------------ | ---------------------------------- | ------------------------------------------------------------ |
| FR-PARSE-001 | 系统应支持从文档中提取文本内容     | 对支持的文档格式，应能提取可用于切分和向量化的文本           |
| FR-PARSE-002 | 系统应支持基础文本清洗             | 应能够清理明显无效的空白字符、重复换行和格式噪声             |
| FR-PARSE-003 | 系统应支持将长文本切分为 chunk     | 文档解析后应生成多个可检索的文本块                           |
| FR-PARSE-004 | 系统应支持配置 chunk 大小          | 切分策略应支持配置 chunk_size 等参数                         |
| FR-PARSE-005 | 系统应支持配置 chunk 重叠长度      | 切分策略应支持配置 chunk_overlap，以减少语义断裂             |
| FR-PARSE-006 | 系统应保存 chunk 内容              | 每个 chunk 的文本内容应保存到业务数据库中                    |
| FR-PARSE-007 | 系统应保存 chunk 来源信息          | chunk 应关联知识库 ID、文档 ID、chunk 序号和来源位置等元数据 |
| FR-PARSE-008 | 系统应支持空文档或无有效文本的处理 | 如果文档无法提取有效文本，应将文档标记为处理失败并记录原因   |
| FR-PARSE-009 | 系统应保证 chunk 可用于引用溯源    | 后续问答引用应能够定位到对应文档和 chunk                     |
| FR-PARSE-010 | 系统应为不同切分策略预留扩展能力   | 后续可以扩展按标题、段落、Markdown 结构或语义边界切分        |

### 5.4 向量化入库需求

向量化入库模块负责将 chunk 文本转换为向量，并写入 Qdrant 向量数据库。该模块连接文档处理流程和语义检索流程。

| 编号       | 需求描述                                   | 验收要点                                                 |
| ---------- | ------------------------------------------ | -------------------------------------------------------- |
| FR-EMB-001 | 系统应支持调用 Embedding 模型生成向量      | 输入 chunk 文本后，应能生成对应向量表示                  |
| FR-EMB-002 | 系统应支持批量向量化文本块                 | 一个文档生成多个 chunk 后，应支持批量生成向量            |
| FR-EMB-003 | 系统应支持将向量写入 Qdrant                | chunk 向量应能够写入指定 Qdrant collection               |
| FR-EMB-004 | 系统应为向量数据写入 payload               | payload 应包含知识库 ID、文档 ID、chunk ID 和来源信息    |
| FR-EMB-005 | 系统应保证 PostgreSQL 与 Qdrant 数据可关联 | 通过 chunk ID 或业务标识，可以从检索结果关联回数据库记录 |
| FR-EMB-006 | 系统应在向量写入失败时记录失败原因         | 向量化或写入 Qdrant 失败时，应更新文档处理状态并记录错误 |
| FR-EMB-007 | 系统应支持删除文档时清理向量数据           | 删除文档后，应删除或标记清理该文档对应的向量数据         |
| FR-EMB-008 | 系统应支持按知识库隔离向量检索范围         | 向量 payload 或 collection 设计应支持按知识库过滤        |
| FR-EMB-009 | 系统应为 Embedding 模型切换预留配置能力    | Embedding 模型名称、维度和服务地址不应硬编码             |
| FR-EMB-010 | 系统应避免重复入库导致脏数据               | 文档重新处理时，应考虑旧 chunk 和旧向量的清理或版本控制  |

### 5.5 语义检索需求

语义检索模块负责根据用户问题从指定知识库中召回相关文本块，是 RAG 问答链路的核心模块之一。

| 编号       | 需求描述                                   | 验收要点                                                     |
| ---------- | ------------------------------------------ | ------------------------------------------------------------ |
| FR-RET-001 | 系统应支持将用户问题向量化                 | 输入用户问题后，应生成查询向量                               |
| FR-RET-002 | 系统应支持按知识库范围检索                 | 检索时应能够限定目标知识库                                   |
| FR-RET-003 | 系统应支持从 Qdrant 中召回候选 chunk       | 查询后应返回候选文本块及相关得分                             |
| FR-RET-004 | 系统应支持配置 top_k                       | 调用方或系统配置可以控制召回数量                             |
| FR-RET-005 | 系统应支持配置 score_threshold             | 系统可以过滤低于相似度阈值的结果                             |
| FR-RET-006 | 系统应返回检索结果元数据                   | 检索结果应包含 chunk ID、文档 ID、知识库 ID、文本内容和相似度得分 |
| FR-RET-007 | 系统应在无检索结果时返回空结果而非异常崩溃 | 没有相关内容时，应返回可识别的空检索结果                     |
| FR-RET-008 | 系统应支持检索参数集中管理                 | top_k、score_threshold 等参数应可配置                        |
| FR-RET-009 | 系统应记录检索请求与检索结果               | 检索过程应可用于后续链路追踪和评测                           |
| FR-RET-010 | 系统应为后续混合检索预留扩展能力           | 后续可扩展关键词检索、全文检索或混合检索                     |

### 5.6 Rerank 重排需求

Rerank 重排模块负责对语义检索召回的候选文本块进行二次排序，提高最终上下文质量。

| 编号          | 需求描述                                    | 验收要点                                    |
| ------------- | ------------------------------------------- | ------------------------------------------- |
| FR-RERANK-001 | 系统应支持接收候选检索结果进行重排          | 输入用户问题和候选 chunk 后，应返回重排结果 |
| FR-RERANK-002 | 系统应支持计算候选 chunk 与问题的相关性得分 | 重排结果应包含 rerank_score 或等价得分      |
| FR-RERANK-003 | 系统应支持按重排得分重新排序                | 返回结果应按照重排后的相关性排序            |
| FR-RERANK-004 | 系统应支持过滤低相关性结果                  | 低于阈值的候选 chunk 可以被过滤             |
| FR-RERANK-005 | 系统应支持限制最终上下文数量                | 可控制最终传入 LLM 的 chunk 数量            |
| FR-RERANK-006 | 系统应支持在 Rerank 不可用时降级            | Rerank 服务异常时，可降级使用原始检索排序   |
| FR-RERANK-007 | 系统应记录重排前后的结果                    | 便于分析 Rerank 是否改善上下文质量          |
| FR-RERANK-008 | 系统应为不同 Rerank 实现预留扩展能力        | 可后续接入本地模型、API 模型或规则重排策略  |

### 5.7 RAG 问答需求

RAG 问答模块负责基于检索上下文生成最终答案，并返回引用来源。该模块是 ForgeRAG 对外提供知识库问答能力的核心入口。

| 编号      | 需求描述                             | 验收要点                                                  |
| --------- | ------------------------------------ | --------------------------------------------------------- |
| FR-QA-001 | 系统应支持向指定知识库提问           | 调用方提交问题和知识库 ID 后，系统执行 RAG 问答流程       |
| FR-QA-002 | 系统应支持自动执行检索流程           | 问答过程中应自动完成问题向量化和语义检索                  |
| FR-QA-003 | 系统应支持在问答流程中调用 Rerank    | 如果启用 Rerank，应对候选上下文进行重排                   |
| FR-QA-004 | 系统应支持构造 RAG Prompt            | Prompt 应包含用户问题、检索上下文和回答约束               |
| FR-QA-005 | 系统应支持调用 LLM 生成回答          | 输入 Prompt 后，应返回自然语言答案                        |
| FR-QA-006 | 系统应返回引用来源                   | 回答结果应包含使用到的 chunk、文档来源和相关元数据        |
| FR-QA-007 | 系统应支持无依据时拒绝生成确定性答案 | 当检索上下文不足时，应返回无法回答或知识不足提示          |
| FR-QA-008 | 系统应保存问答记录                   | 问答记录应包含问题、答案、知识库 ID、引用、耗时和创建时间 |
| FR-QA-009 | 系统应返回结构化问答结果             | 返回结果应便于前端、业务后端或 Agent 解析                 |
| FR-QA-010 | 系统应支持问答参数配置               | 如 top_k、是否启用 Rerank、模型名称等参数应可配置或预留   |
| FR-QA-011 | 系统应记录 LLM 调用异常              | 模型调用失败时，应返回统一错误结构并记录日志              |
| FR-QA-012 | 系统应避免引用与回答脱节             | 返回引用应与生成回答所使用的上下文保持一致                |

### 5.8 Agentic RAG 流程需求

Agentic RAG 流程模块负责让系统根据问题和中间结果动态决策，而不是固定执行单一路径。

| 编号         | 需求描述                                | 验收要点                                                     |
| ------------ | --------------------------------------- | ------------------------------------------------------------ |

| FR-AGENT-003 | 系统应支持判断是否需要检索              | 对不需要检索的问题，可以不执行知识库检索                     |
| FR-AGENT-004 | 系统应支持问题改写                      | 对表达不清晰或检索效果差的问题，系统可以生成改写后的检索查询 |

| FR-AGENT-006 | 系统应支持判断是否需要二次检索          | 当第一次检索结果不足时，系统可以触发二次检索                 |
| FR-AGENT-007 | 系统应支持上下文充分性判断              | 系统应判断当前上下文是否足以支持回答                         |
| FR-AGENT-008 | 系统应支持生成带引用回答                | 如果上下文足够，应生成答案并返回引用来源                     |
| FR-AGENT-009 | 系统应支持拒答策略                      | 如果上下文不足，应返回拒答结果和原因                         |
| FR-AGENT-010 | 系统应记录 Agentic RAG 状态流转         | 每个节点的输入、输出、判断结果和下一步路径应可追踪           |
| FR-AGENT-011 | 系统应避免无限循环                      | 二次检索或反思流程应有最大次数限制                           |
| FR-AGENT-012 | 系统应为 LangGraph 编排预留清晰状态模型 | 后续实现时应能将流程映射为状态图节点和边                     |

### 5.9 RAG 自动化评测需求

RAG 自动化评测模块负责评估检索质量、回答质量、上下文利用情况和引用质量，为系统持续优化提供依据。

| FR-EVAL-003 | 系统应支持创建评测任务               | 可以基于指定评测集和知识库创建评测任务                    |

### 5.12 功能性需求总结

ForgeRAG 的功能性需求可以概括为以下主线：

```text
知识库管理 → 文档管理 → 文档解析与切分 → 向量化入库 → 语义检索 → Rerank 重排 → RAG 问答 → Agentic RAG → 自动化评测 → 可观测性 → 工程基础
```

各模块之间的关系如下：

1. **知识库管理** 提供业务边界。
2. **文档管理** 提供原始知识入口。
3. **文档解析与切分** 将原始文档转换为文本块。
4. **向量化入库** 将文本块写入向量数据库。
5. **语义检索** 根据问题召回相关文本块。
6. **Rerank 重排** 提升候选上下文质量。
7. **RAG 问答** 基于上下文生成带引用回答。
8. **Agentic RAG** 对问答流程进行动态控制。
9. **自动化评测** 评估检索和回答效果。
10. **可观测性** 记录链路过程并支持问题分析。
11. **工程基础** 保证系统可维护、可测试、可部署。

后续架构设计、数据库设计、接口设计、测试策略和开发阶段任务都应以本章功能性需求为依据。





## 6. 非功能性需求

非功能性需求用于描述 ForgeRAG 在可维护性、可扩展性、可配置性、可靠性、性能、安全、测试、部署和协作等方面需要满足的工程质量要求。

ForgeRAG 的目标不是简单完成一个 RAG Demo，而是构建一个具备企业级后端工程规范的 Agentic RAG 后端系统。因此，系统不仅要能够完成知识库管理、文档入库、语义检索、Rerank、问答生成、Agentic RAG、自动化评测和链路追踪等功能，还需要保证代码结构清晰、配置可管理、异常可处理、日志可追踪、测试可执行、环境可复现。

本章描述的是系统整体质量要求，不展开具体代码实现方案。

### 6.1 可维护性需求

ForgeRAG 应具备良好的可维护性，使后续开发者能够理解系统结构、定位业务逻辑、修改功能模块并持续迭代。

**需求说明：**

1. 系统应采用清晰的后端分层架构。
2. API 层只负责请求接收、参数校验、调用 Service 和返回响应。
3. Service 层负责组织业务流程和业务规则。
4. Repository 层负责数据库访问。
5. Core 层负责 RAG、Agentic RAG、Prompt、评测等核心逻辑。
6. Infrastructure 层负责对接数据库、向量库、模型服务、Langfuse 等外部基础设施。
7. 不应将接口逻辑、业务逻辑、数据库访问和外部服务调用混杂在同一个文件中。
8. 模块命名、目录结构和代码风格应保持一致。

**验收要点：**

1. 项目目录结构能够体现 API、Schema、Service、Repository、Core、Infrastructure 等职责划分。
2. 任一核心功能模块都能找到对应的接口入口、业务服务和数据访问位置。
3. 新增功能时不需要大面积修改无关模块。
4. 开发文档能够说明主要模块职责和代码组织方式。

### 6.2 可扩展性需求

ForgeRAG 应具备适度可扩展性，便于后续替换模型、调整检索策略、增加评测指标或扩展 Agentic RAG 流程。

**需求说明：**

1. 系统应支持后续切换不同 LLM、Embedding 模型和 Rerank 模型。
2. 系统应支持调整文本切分策略。
3. 系统应支持调整检索参数，例如 `top_k`、`score_threshold` 等。
4. 系统应支持扩展不同检索方式，例如后续增加关键词检索、全文检索或混合检索。
5. 系统应支持扩展不同 Rerank 实现方式。
6. 系统应支持扩展不同 Prompt 模板。
7. 系统应支持扩展 Agentic RAG 节点，例如问题分类、反思检查、多轮澄清等。
8. 系统应支持扩展评测指标和评分方式。

**验收要点：**

1. 模型名称、模型服务地址和关键调用参数不应硬编码在业务逻辑中。
2. 检索参数和切分参数应能够通过配置或参数传入进行调整。
3. Prompt 模板应独立管理，避免散落在多个业务函数中。
4. Agentic RAG 流程应具备清晰状态模型，便于后续增加节点。
5. 新增评测指标时不应破坏已有评测任务结构。

### 6.3 可配置性需求

ForgeRAG 应通过配置文件或环境变量管理系统运行参数，避免把环境相关信息写死在代码中。

**需求说明：**

系统配置应至少覆盖以下内容：

1. FastAPI 服务配置。
2. PostgreSQL 数据库连接配置。
3. Qdrant 向量数据库连接配置。
4. LLM 模型配置。
5. Embedding 模型配置。
6. Rerank 模型配置。
7. Langfuse 可观测性配置。
8. 文档上传限制配置。
9. 文本切分参数配置。
10. 检索参数配置。
11. 日志级别配置。
12. 运行环境配置，例如 `dev`、`test`、`prod`。

**验收要点：**

1. 数据库连接地址、用户名、密码不应硬编码。
2. 模型 API Key 不应硬编码。
3. Qdrant、Langfuse 等外部服务地址应可通过配置修改。
4. 不同环境可以使用不同配置。
5. 配置缺失或格式错误时，系统应给出明确错误提示。
6. `.env.example` 或等价示例配置文件应能够指导开发者准备本地环境。

### 6.4 可靠性需求

ForgeRAG 应具备基础可靠性，保证常见异常场景不会导致系统不可控崩溃，并能够返回明确错误信息。

**需求说明：**

1. 系统应对接口参数进行校验。
2. 系统应对知识库不存在、文档不存在、文档未处理完成等业务异常进行处理。
3. 系统应对数据库连接失败、Qdrant 调用失败、模型服务调用失败等外部依赖异常进行处理。
4. 系统应记录文档处理失败原因。
5. 系统应记录问答生成失败原因。
6. 系统应避免将未处理异常直接暴露给调用方。
7. 系统应保证局部失败可追踪，例如文档入库失败后能够查看失败状态。
8. 系统应为外部观测工具不可用时预留降级策略，避免观测工具异常直接阻断核心问答流程。

**验收要点：**

1. 参数错误时返回统一错误响应。
2. 资源不存在时返回统一错误响应。
3. 外部服务异常时返回统一错误响应并记录日志。
4. 文档处理失败后可以查询到失败状态和失败原因。
5. 模型调用失败后不会导致整个服务进程崩溃。
6. Langfuse 或类似观测工具不可用时，核心业务流程应尽量继续执行。

### 6.5 可观测性需求

ForgeRAG 应具备较强的可观测性，使开发者能够理解 RAG 和 Agentic RAG 请求的执行过程。

**需求说明：**

系统应记录以下关键链路信息：

1. 用户原始问题。
2. 知识库范围。
3. 检索查询。
4. 召回文本块。
5. 相似度得分。
6. Rerank 前后的结果。
7. Prompt 输入。
8. LLM 输出。
9. Token 消耗。
10. 调用耗时。
11. Agentic RAG 节点状态流转。
12. 异常信息和失败原因。
13. 问答记录与 Trace 的关联。
14. 评测记录与 Trace 的关联。

**验收要点：**

1. 一次普通 RAG 问答请求应能够追踪到检索、重排、生成和引用结果。
2. 一次 Agentic RAG 请求应能够追踪到每个节点的输入、输出和判断结果。
3. 一次评测任务中的失败样本应能够关联到具体问答链路。
4. 日志中应包含必要的请求标识或 Trace 标识。
5. 可观测性数据应服务于调试、评测和优化，而不是只记录零散日志。

### 6.6 性能需求

ForgeRAG 当前阶段不以高并发、大规模分布式部署为目标，但仍应具备合理的基础性能要求，避免明显低效的实现影响本地开发、演示和中小规模测试。

**需求说明：**

1. 系统应避免在接口中执行不必要的重复计算。
2. 文档入库应支持批量处理 chunk，而不是逐条低效阻塞。
3. 向量写入应尽量支持批量写入。
4. 检索流程应支持限制召回数量。
5. 传入 LLM 的上下文长度应受到控制，避免无限拼接文本。
6. Rerank 输入数量应受到控制，避免对过多候选文本执行重排。
7. Agentic RAG 的二次检索或循环判断应设置最大次数。
8. 评测任务应避免阻塞核心问答接口。
9. 接口响应时间应能够通过日志或 Trace 进行分析。

**验收要点：**

1. 检索接口支持 `top_k` 等参数限制召回数量。
2. RAG 问答流程能够控制最终上下文数量。
3. Agentic RAG 流程不存在无限循环风险。
4. 文档入库和评测任务有明确状态，不应表现为不可追踪的长时间卡死。
5. Trace 或日志中能够查看关键步骤耗时。

### 6.7 安全性需求

ForgeRAG 第一版不优先实现复杂权限系统，但仍需要具备基础安全要求，避免出现明显工程风险。

**需求说明：**

1. 系统应校验接口输入，避免无效参数进入核心业务流程。
2. 系统不应硬编码数据库密码、模型 API Key 或其他敏感信息。
3. 系统不应在接口响应中直接暴露原始异常堆栈。
4. 系统应限制上传文件类型。
5. 系统应限制上传文件大小。
6. 系统应为后续用户身份、知识库归属和访问控制预留扩展点。
7. 日志和 Trace 中应避免记录不必要的敏感信息。
8. Prompt 构造时应尽量约束模型只基于检索上下文回答，降低无依据生成风险。

**验收要点：**

1. 上传非法文件类型时，系统返回明确错误。
2. 上传超出大小限制的文件时，系统返回明确错误。
3. `.env` 等敏感配置文件不应提交到 Git 仓库。
4. API Key 不出现在代码仓库中。
5. 生产或演示环境下的异常响应不直接暴露内部堆栈。
6. 问答结果在缺少知识依据时能够返回无法回答提示。

ForgeRAG 应具备可测试性，使核心逻辑可以通过自动化测试进行验证。

10. 评测设计文档。
11. 部署说明文档。
12. 测试策略文档。

协作规范应至少覆盖：

1. Git 分支规范。
2. Commit Message 规范。
3. 目录结构规范。
4. 代码风格规范。
5. 文档命名规范。

**验收要点：**

1. 文档目录结构清晰。
2. 每份设计文档职责边界明确，避免大量重复。
3. 新功能开发前能够在文档中找到对应需求来源。
4. 需求、设计、接口、测试之间能够建立基本对应关系。
5. README 能够说明项目定位、技术栈、启动方式和当前阶段进度。

### 6.11 非功能性需求总结

ForgeRAG 的非功能性需求可以概括为以下原则：

1. **可维护**

   通过清晰分层和模块边界降低后续修改成本。

2. **可扩展**

   为模型替换、检索策略、Rerank、Prompt、Agentic RAG 节点和评测指标预留扩展空间。

3. **可配置**

   使用配置文件和环境变量管理运行参数，避免硬编码。

4. **可可靠运行**

   对参数错误、业务异常和外部依赖异常进行统一处理。

5. **可观测**

   能够追踪 RAG 和 Agentic RAG 的关键执行过程。

6. **性能适度可控**

   不追求大规模分布式指标，但要避免明显低效和不可追踪的长流程。

7. **基础安全合格**

   不做复杂权限系统，但要避免密钥泄露、堆栈暴露和无效输入。

8. **可测试**

   核心业务逻辑、RAG 链路和异常处理应具备测试覆盖。

9. **可部署**

   支持 Docker Compose 快速启动本地开发和演示环境。

10. **可协作**

通过文档、规范和 CI/CD 支撑长期迭代。





## 7. 数据需求

数据需求用于说明 ForgeRAG 需要管理哪些核心数据对象、这些数据对象分别服务于哪些业务流程、数据之间如何关联，以及不同类型的数据应存储在什么位置。

ForgeRAG 的数据设计应服务于以下核心链路：

```text
知识库管理 → 文档管理 → 文档解析与切分 → 向量化入库 → 语义检索 → RAG 问答 → Agentic RAG → 自动化评测 → 链路追踪与优化
```

本章只分析数据对象和数据关系，不展开具体数据库表字段、索引设计、外键约束或迁移脚本。具体字段设计将在后续数据库设计文档中进一步说明。

### 7.1 知识库数据

知识库数据用于表示一个独立的企业知识边界，是 ForgeRAG 中组织文档、chunk、向量数据、问答记录和评测任务的核心业务对象。

**数据用途：**

1. 区分不同业务场景下的知识范围。
2. 作为文档上传和文档管理的归属对象。
3. 作为语义检索和问答请求的检索范围。
4. 作为评测任务执行的目标知识范围。
5. 为后续权限控制、多知识库管理和知识隔离预留基础。

**主要内容：**

1. 知识库基础信息。
2. 知识库描述信息。
3. 知识库状态。
4. 创建时间和更新时间。
5. 创建者或归属信息的扩展点。

**关联关系：**

1. 一个知识库可以包含多个文档。
2. 一个知识库可以包含多个 chunk。
3. 一个知识库可以对应多条向量数据。
4. 一个知识库可以产生多条问答记录。
5. 一个知识库可以关联多个评测数据集或评测任务。
6. 一个知识库可以作为 Agentic RAG 流程的知识检索范围。

**建议存储位置：**

知识库数据属于结构化业务元数据，建议存储在 PostgreSQL 中。

### 7.2 文档数据

文档数据用于记录上传到知识库中的原始文件及其处理状态，是文档解析、切分和向量化入库流程的起点。

**数据用途：**

1. 管理上传到系统中的原始文档。
2. 记录文档所属知识库。
3. 跟踪文档从上传到入库完成的处理状态。
4. 记录文档解析、切分、向量化过程中的失败原因。
5. 为问答引用溯源提供文档来源。

**主要内容：**

1. 文档基础信息。
2. 文件名称、文件类型和文件大小。
3. 文件存储路径或文件访问标识。
4. 所属知识库。
5. 文档处理状态。
6. 处理失败原因。
7. 上传时间、处理开始时间和处理完成时间。
8. 文档版本或重新处理标识的扩展点。

**关联关系：**

1. 一个文档必须归属于一个知识库。
2. 一个文档可以被切分为多个 chunk。
3. 一个文档可以对应多条向量数据。
4. 一个文档可以被多个问答引用。
5. 一个文档可以参与多个评测样本的检索结果。

**建议存储位置：**

文档元数据建议存储在 PostgreSQL 中。

原始文件本身可以根据项目阶段选择本地文件系统、对象存储或其他文件存储方案。当前阶段可以优先使用本地文件存储，并在数据库中保存文件路径或访问标识。

### 7.3 文本块 Chunk 数据

Chunk 数据用于表示文档切分后的文本片段，是向量化、语义检索、RAG 问答和引用溯源的核心数据单元。

**数据用途：**

1. 作为 Embedding 向量化的输入。
2. 作为语义检索返回的候选上下文。
3. 作为 RAG Prompt 构造的上下文来源。
4. 作为回答引用溯源的最小文本单位。
5. 作为评测检索结果分析的基础数据。

**主要内容：**

1. chunk 文本内容。
2. 所属知识库。
3. 所属文档。
4. chunk 序号。
5. chunk 来源位置，例如页码、段落位置或字符范围。
6. chunk 长度。
7. 切分策略相关信息。
8. 创建时间和更新时间。

**关联关系：**

1. 一个 chunk 必须归属于一个文档。
2. 一个 chunk 必须间接归属于一个知识库。
3. 一个 chunk 通常对应一条向量数据。
4. 一个 chunk 可以出现在多次检索结果中。
5. 一个 chunk 可以被多条问答记录引用。
6. 一个 chunk 可以作为评测结果中的召回证据。

**建议存储位置：**

chunk 的业务数据和文本内容建议存储在 PostgreSQL 中。

chunk 对应的向量表示建议存储在 Qdrant 中，并通过 `chunk_id`、`document_id`、`knowledge_base_id` 等标识与 PostgreSQL 中的数据建立关联。

### 7.4 向量数据

向量数据用于表示 chunk 文本经过 Embedding 模型转换后的语义向量，是语义检索的基础。

**数据用途：**

1. 支持基于用户问题的语义相似度检索。
2. 支持按知识库范围过滤候选文本块。
3. 支持根据 chunk ID 关联回 PostgreSQL 中的文本块和文档数据。
4. 支持后续 RAG 问答、Rerank 和引用溯源。

**主要内容：**

1. chunk 对应的向量。
2. 向量 ID。
3. knowledge_base_id。
4. document_id。
5. chunk_id。
6. 文本片段摘要或必要文本内容。
7. 文档来源信息。
8. Embedding 模型名称或版本信息的扩展点。

**关联关系：**

1. 一条向量数据通常对应一个 chunk。
2. 一条向量数据需要关联所属文档。
3. 一条向量数据需要关联所属知识库。
4. 检索结果需要通过向量 payload 关联回业务数据。
5. 文档删除或重新处理时，需要同步处理关联向量数据。

**建议存储位置：**

向量数据建议存储在 Qdrant 中。

PostgreSQL 不负责存储完整向量本体，但需要保存 chunk、文档和知识库等业务元数据，以便和 Qdrant 检索结果进行关联。

### 7.5 问答记录数据

问答记录数据用于保存用户问题、系统回答、引用来源和执行结果，是后续追踪、评测、调试和历史查询的重要依据。

**数据用途：**

1. 保存用户提问和系统回答。
2. 记录问答所属知识库。
3. 记录问答使用的检索结果和引用来源。
4. 记录问答执行耗时和执行状态。
5. 关联链路追踪数据，便于后续分析。
6. 为评测和优化提供样本依据。

**主要内容：**

1. 用户原始问题。
2. 最终回答内容。
3. 所属知识库。
4. 问答类型，例如基础 RAG 或 Agentic RAG。
5. 问答状态，例如成功、失败、拒答。
6. 引用来源摘要。
7. 模型名称或模型配置。
8. 执行耗时。
9. 创建时间。
10. trace_id 或链路追踪标识。

**关联关系：**

1. 一条问答记录通常关联一个知识库。
2. 一条问答记录可以关联多个引用来源。
3. 一条问答记录可以关联一次 Trace。
4. 一条问答记录可以作为评测样本的执行结果。
5. Agentic RAG 问答记录可以关联多个流程节点记录。

**建议存储位置：**

问答记录属于结构化业务数据，建议存储在 PostgreSQL 中。

完整的链路细节、模型调用过程和节点执行细节可以存储或关联到 Langfuse、日志系统或专门的追踪记录中。

### 7.6 引用来源数据

引用来源数据用于描述系统生成回答时使用了哪些文档片段，是保证回答可追溯性和可信度的关键数据。

**数据用途：**

1. 标识回答依据来自哪些 chunk。
2. 展示引用文档、页码、段落或文本片段。
3. 支持前端展示“答案来源”。
4. 支持评测引用是否正确。
5. 支持开发者分析回答是否忠实于检索上下文。

**主要内容：**

1. qa_record_id。
2. knowledge_base_id。
3. document_id。
4. chunk_id。
5. 引用文本片段。
6. 检索相似度得分。
7. Rerank 得分。
8. 引用排序。
9. 文档名称、页码或段落位置等展示信息。

**关联关系：**

1. 一条问答记录可以包含多个引用来源。
2. 一个引用来源应关联一个 chunk。
3. 一个引用来源应能追溯到原始文档。
4. 一个引用来源应能追溯到所属知识库。
5. 引用来源可与检索结果、Rerank 结果和评测结果关联。

**建议存储位置：**

引用来源数据建议存储在 PostgreSQL 中，作为问答记录的结构化关联数据。

如果引用来源同时出现在链路追踪中，可以通过 trace_id 与 Langfuse 或日志系统中的追踪数据建立关联。

### 7.7 Agentic RAG 流程数据

Agentic RAG 流程数据用于记录智能流程中的状态流转、节点输入输出和决策结果，使系统能够追踪一次 Agentic RAG 请求是如何完成的。

**数据用途：**

1. 记录 Agentic RAG 的执行状态。
2. 记录问题分析结果。
3. 记录是否需要检索的判断结果。
4. 记录问题改写结果。
5. 记录一次或多次检索结果。
6. 记录上下文充分性判断。
7. 记录最终回答或拒答原因。
8. 支持调试 Agentic RAG 流程。
9. 支持后续评测 Agentic RAG 的决策质量。

**主要内容：**

1. 原始问题。
2. 改写后的问题。
3. 当前流程状态。
4. 节点名称。
5. 节点输入。
6. 节点输出。
7. 节点判断结果。
8. 下一步节点。
9. 执行耗时。
10. 错误信息。
11. trace_id。
12. 关联问答记录 ID。

**关联关系：**

1. 一次 Agentic RAG 请求通常对应一条问答记录。
2. 一次 Agentic RAG 请求可以包含多个节点执行记录。
3. 每个节点执行记录可以关联 Trace 或 Span。
4. 检索节点可以关联检索结果和引用来源。
5. 最终回答节点可以关联问答记录。
6. 拒答节点可以关联拒答原因。

**建议存储位置：**

关键流程摘要和最终状态建议存储在 PostgreSQL 中。

详细节点输入、输出、耗时、模型调用和 Span 信息建议通过 Langfuse 或链路追踪系统记录。PostgreSQL 中可保存 trace_id，用于关联外部追踪数据。

### 7.8 评测数据集数据

评测数据集数据用于组织 RAG 自动化评测所需的问题、参考答案、期望引用和标签，是评测任务执行的基础。

**数据用途：**

1. 管理一组评测样本。
2. 保存评测问题。
3. 保存参考答案或期望答案。
4. 保存期望引用或相关文档标识。
5. 保存评测标签，例如问题类型、难度、所属业务场景。
6. 支持后续批量评测和效果对比。

**主要内容：**

1. 评测数据集名称。
2. 评测数据集描述。
3. 评测样本列表。
4. 样本问题。
5. 参考答案。
6. 期望引用。
7. 标签信息。
8. 创建时间和更新时间。

**关联关系：**

1. 一个评测数据集可以包含多个评测样本。
2. 一个评测数据集可以关联一个或多个知识库。
3. 一个评测数据集可以被多个评测任务复用。
4. 一个评测样本可以产生多个评测结果。
5. 一个评测样本可以关联期望文档或期望 chunk。

**建议存储位置：**

评测数据集和评测样本属于结构化业务数据，建议存储在 PostgreSQL 中。

### 7.9 评测任务与评测结果数据

评测任务与评测结果数据用于记录一次批量评测的执行配置、执行状态、样本结果和评分信息。

**数据用途：**

1. 创建并管理评测任务。
2. 记录评测任务使用的数据集和知识库。
3. 记录评测任务使用的检索参数、Rerank 配置、Prompt 版本和模型配置。
4. 记录每个样本的检索结果、生成答案、引用来源和评分。
5. 支持不同实验配置之间的效果对比。
6. 支持从失败样本追踪到具体 RAG 链路。

**主要内容：**

1. 评测任务名称。
2. 评测任务状态。
3. 关联评测数据集。
4. 关联知识库。
5. 评测配置。
6. 样本执行结果。
7. 检索结果摘要。
8. 生成答案。
9. 引用来源。
10. 评测得分。
11. 失败原因。
12. trace_id。
13. 创建时间、开始时间和结束时间。

**关联关系：**

1. 一个评测任务对应一个评测数据集。
2. 一个评测任务可以包含多个样本执行结果。
3. 一个样本执行结果可以关联一条问答记录。
4. 一个样本执行结果可以关联一次 Trace。
5. 一个评测任务可以与不同实验配置关联，用于横向对比。
6. 一个评测结果可以关联检索结果、引用来源和模型输出。

**建议存储位置：**

评测任务、评测样本执行结果和评分摘要建议存储在 PostgreSQL 中。

详细执行链路、模型调用过程和节点级信息建议通过 Langfuse 或链路追踪系统记录，并通过 trace_id 与评测结果关联。

### 7.10 链路追踪与日志数据

链路追踪与日志数据用于记录系统运行时的关键过程，帮助开发者分析 RAG 和 Agentic RAG 请求的执行路径、耗时、异常和质量问题。

**数据用途：**

1. 追踪一次 RAG 问答请求的完整执行过程。
2. 追踪 Agentic RAG 的节点状态流转。
3. 记录模型调用输入输出。
4. 记录 Token 消耗和调用耗时。
5. 记录检索、Rerank、Prompt 和 LLM 生成过程。
6. 记录异常信息和失败原因。
7. 支持评测失败样本的问题定位。
8. 支持系统性能分析和链路优化。

**主要内容：**

1. trace_id。
2. request_id。
3. 用户问题。
4. 知识库 ID。
5. 检索查询。
6. 检索结果。
7. Rerank 结果。
8. Prompt 输入。
9. LLM 输出。
10. 模型名称。
11. Token 消耗。
12. 节点输入输出。
13. 异常信息。
14. 调用耗时。
15. 时间戳。

**关联关系：**

1. Trace 可以关联问答记录。
2. Trace 可以关联评测任务结果。
3. Trace 可以关联 Agentic RAG 节点记录。
4. Trace 可以关联外部模型调用记录。
5. 日志可以通过 request_id 或 trace_id 与业务记录关联。

**建议存储位置：**

链路追踪数据建议由 Langfuse 或类似可观测性工具管理。

系统运行日志建议由应用日志系统管理，可以输出到控制台、文件或后续日志平台。PostgreSQL 中可以保存关键 trace_id、request_id 或状态摘要，用于关联业务数据和观测数据。

### 7.11 配置与系统运行数据

配置与系统运行数据用于支撑系统在不同环境下稳定运行，包括数据库配置、模型配置、切分参数、检索参数、日志级别和外部服务连接信息等。

**数据用途：**

1. 管理系统运行环境。
2. 管理数据库、Qdrant、Langfuse 和模型服务连接配置。
3. 管理文档上传限制。
4. 管理文本切分参数。
5. 管理检索参数。
6. 管理模型名称和调用参数。
7. 支持不同环境的配置隔离。
8. 降低硬编码带来的维护风险。

**主要内容：**

1. 数据库连接配置。
2. Qdrant 连接配置。
3. LLM 配置。
4. Embedding 模型配置。
5. Rerank 模型配置。
6. Langfuse 配置。
7. chunk_size、chunk_overlap 等切分参数。
8. top_k、score_threshold 等检索参数。
9. 日志级别。
10. 文件上传限制。
11. 运行环境标识。

**关联关系：**

1. 配置会影响文档入库流程。
2. 配置会影响检索和问答结果。
3. 配置会影响评测任务对比结果。
4. 配置会影响部署环境和运行状态。
5. 评测结果应尽量记录关键实验配置，便于复现效果。

**建议存储位置：**

系统运行配置建议优先通过 `.env`、环境变量和配置文件管理。

如果后续需要在运行时动态管理模型配置、Prompt 版本、检索参数或评测实验配置，可以将部分配置持久化到 PostgreSQL 中。当前阶段不需要一开始就设计复杂配置中心。

### 7.12 数据关联关系总结

ForgeRAG 中的核心数据对象之间可以概括为以下关系：

```text
KnowledgeBase
  ├── Document
  │     ├── Chunk
  │     │     └── Vector in Qdrant
  │     └── DocumentProcessStatus
  ├── QARecord
  │     ├── Citation
  │     └── Trace
  ├── EvaluationDataset
  │     └── EvaluationSample
  └── EvaluationTask
        ├── EvaluationResult
        ├── QARecord
        └── Trace
```

核心关联标识包括：

1. `knowledge_base_id`
2. `document_id`
3. `chunk_id`
4. `qa_record_id`
5. `citation_id`
6. `eval_dataset_id`
7. `eval_sample_id`
8. `eval_task_id`
9. `eval_result_id`
10. `trace_id`
11. `request_id`

这些标识应保证 PostgreSQL、Qdrant、日志系统和 Langfuse 之间能够建立基本关联。

### 7.13 数据存储职责总结

ForgeRAG 中不同类型数据的建议存储位置如下：

| 数据类型             | 建议存储位置           | 说明                                |
| -------------------- | ---------------------- | ----------------------------------- |
| 知识库数据           | PostgreSQL             | 结构化业务元数据                    |
| 文档元数据           | PostgreSQL             | 文件信息、处理状态、所属知识库      |
| 原始文档文件         | 本地文件系统或对象存储 | 当前阶段可先使用本地文件存储        |
| chunk 文本数据       | PostgreSQL             | 用于引用、检索结果展示和业务关联    |
| 向量数据             | Qdrant                 | 用于语义检索                        |
| 向量 payload         | Qdrant                 | 保存知识库、文档、chunk 等关联标识  |
| 问答记录             | PostgreSQL             | 保存问题、答案、状态和 trace_id     |
| 引用来源             | PostgreSQL             | 保存回答引用的 chunk 和文档来源     |
| Agentic RAG 流程摘要 | PostgreSQL             | 保存关键状态、最终结果和 trace_id   |
| Agentic RAG 节点细节 | Langfuse 或日志系统    | 记录节点输入输出和状态变化          |
| 评测数据集           | PostgreSQL             | 保存评测问题、参考答案和期望引用    |
| 评测任务与结果       | PostgreSQL             | 保存任务状态、结果、评分和 trace_id |
| Trace / Span         | Langfuse               | 保存 RAG 和 Agent 执行过程          |
| 系统运行日志         | 日志系统               | 保存请求日志、业务日志和异常日志    |
| 系统配置             | 环境变量 / 配置文件    | 管理数据库、模型、向量库和日志配置  |

### 7.14 数据需求总结

ForgeRAG 的数据需求可以概括为以下原则：

1. **PostgreSQL 管理业务数据**

   知识库、文档、chunk、问答记录、引用来源、评测数据集、评测任务和评测结果等结构化数据应由 PostgreSQL 管理。

2. **Qdrant 管理向量数据**

   chunk 对应的向量表示应存储在 Qdrant 中，并通过 payload 保存必要业务标识，保证检索结果可以关联回 PostgreSQL。

3. **Langfuse 管理链路追踪数据**

   RAG 和 Agentic RAG 的 Trace、Span、模型调用、Prompt、输出、耗时和 Token 消耗等观测数据应交给 Langfuse 或类似工具管理。

4. **日志系统管理运行日志**

   系统运行日志、异常日志和关键业务日志应通过结构化日志记录，便于本地开发和后续排查问题。

5. **配置文件和环境变量管理运行配置**

   数据库连接、模型参数、向量库地址、Langfuse 配置和日志级别等运行参数应通过配置文件或环境变量管理，避免硬编码。

6. **核心数据必须可关联**

   PostgreSQL、Qdrant、Langfuse 和日志系统之间应通过 `knowledge_base_id`、`document_id`、`chunk_id`、`qa_record_id`、`eval_task_id`、`trace_id` 等标识建立关联，保证系统行为可追踪、数据来源可解释、评测结果可复现。







## 8. 接口需求概览

接口需求概览用于说明 ForgeRAG 需要对外提供哪些类型的 API，以及这些 API 面向哪些调用方、需要支持哪些核心能力和遵守哪些设计原则。

ForgeRAG 的接口设计应服务于企业知识库 Agentic RAG 后端系统的核心目标：让前端应用、业务后端服务、自动化脚本和智能 Agent 能够通过标准化接口调用知识库管理、文档入库、语义检索、RAG 问答、Agentic RAG、自动化评测和链路追踪等能力。

本章只描述接口类别和接口需求边界，不定义具体 URL、HTTP 方法、请求字段、响应字段和错误码细节。具体接口设计将在后续 API 设计文档中展开。

### 8.1 接口服务对象

ForgeRAG 的 API 主要面向以下调用方：

1. **前端应用**

   前端应用通过 API 完成知识库管理、文档上传、文档状态展示、知识库问答、引用来源展示和评测结果展示。

2. **业务后端服务**

   企业内部业务系统可以通过 API 集成 ForgeRAG 的知识检索和问答能力，例如客服系统、工单系统、研发知识库系统和内部搜索系统。

3. **智能 Agent**

   智能 Agent 可以将 ForgeRAG 作为外部知识工具，调用检索、问答、带引用回答和 Agentic RAG 能力。

4. **开发者**

   开发者通过 API 调试系统功能、验证 RAG 链路、检查接口响应、定位异常和执行开发阶段测试。

5. **评测人员**

   评测人员通过 API 管理评测数据集、创建评测任务、运行批量问答评测并查询评测结果。

6. **运维人员**

   运维人员通过健康检查、运行状态和基础管理接口确认系统是否正常运行。

### 8.2 接口设计原则

ForgeRAG 的接口设计应遵循以下原则：

1. **REST API 风格**

   系统应优先采用清晰、稳定、易理解的 REST API 风格组织接口，使不同调用方能够以统一方式接入系统能力。

2. **统一响应结构**

   所有接口应使用统一响应格式，便于前端、业务后端和 Agent 统一解析成功响应、失败响应、空数据响应和异常响应。

3. **统一错误码机制**

   系统应对参数错误、资源不存在、业务状态异常、外部服务异常和系统内部异常提供明确错误码和错误信息。

4. **参数校验**

   接口应对请求参数进行校验，例如必填字段、字段类型、字符串长度、文件类型、文件大小和枚举值范围。

5. **结构化返回**

   接口返回结果应尽量结构化，避免只返回自然语言文本。尤其是问答接口，应返回答案、引用来源、检索结果摘要、状态和 trace_id 等结构化信息。

6. **分页查询**

   对知识库列表、文档列表、问答记录、评测任务和评测结果等列表类接口，应支持分页查询。

7. **状态可查询**

   对文档处理、评测任务等可能耗时较长的流程，应提供状态查询能力，避免调用方无法判断任务是否完成。

8. **引用可追溯**

   RAG 问答和 Agentic RAG 问答接口应返回引用来源，使调用方能够展示或分析答案依据。

9. **链路可追踪**

   关键接口应返回或关联 trace_id，便于后续查看链路追踪数据、日志和评测结果。

10. **避免过早绑定具体前端**

接口设计应服务于多种调用方，而不是只服务于某一个固定 Web 页面。

### 8.3 健康检查接口

健康检查接口用于确认 ForgeRAG 服务及其关键依赖是否处于可用状态。

**使用对象：**

1. 开发者。
2. 运维人员。
3. CI/CD 流程。
4. 部署脚本。

**主要能力：**

1. 检查 FastAPI 服务是否正常启动。
2. 返回服务基础运行状态。
3. 可扩展检查 PostgreSQL 连接状态。
4. 可扩展检查 Qdrant 连接状态.
5. 可扩展检查 Langfuse 或其他外部依赖状态。

**关键要求：**

1. 接口应轻量、稳定、响应快速。
2. 基础健康检查不应触发复杂业务逻辑。
3. 返回结果应能明确表示服务是否可用。
4. 后续可以区分基础存活检查和依赖就绪检查。

### 8.4 知识库管理接口

知识库管理接口用于管理企业知识库，是文档入库、检索问答和评测任务的业务入口。

**使用对象：**

1. 前端应用。
2. 业务后端服务。
3. 开发者。
4. 评测人员。

**主要能力：**

1. 创建知识库。
2. 查询知识库列表。
3. 查询知识库详情。
4. 更新知识库基础信息。
5. 删除或禁用知识库。
6. 查询知识库下的文档数量、chunk 数量、问答数量等统计信息的扩展能力。

**关键要求：**

1. 知识库应具有唯一标识。
2. 知识库名称、描述、状态等基础信息应可管理。
3. 删除或禁用知识库时，应明确其对文档、chunk、向量数据和问答记录的影响。
4. 知识库不存在时，应返回统一错误结构。
5. 后续文档、检索、问答和评测接口应能够基于知识库 ID 工作。

### 8.5 文档管理接口

文档管理接口用于处理原始文档上传、文档元数据查询、文档状态查询和文档删除等需求。

**使用对象：**

1. 前端应用。
2. 业务后端服务。
3. 开发者。
4. 运维人员。

**主要能力：**

1. 向指定知识库上传文档。
2. 查询指定知识库下的文档列表。
3. 查询文档详情。
4. 查询文档处理状态。
5. 删除文档。
6. 查询文档处理失败原因。
7. 为后续文档重新处理或重新入库预留接口能力。

**关键要求：**

1. 文档上传时必须指定知识库。
2. 系统应校验文件类型和文件大小。
3. 文档上传后应生成文档记录。
4. 文档处理状态应可查询。
5. 文档删除时，应考虑关联 chunk 和向量数据的处理。
6. 文档处理失败时，应能通过接口查询失败原因。

### 8.6 文档处理接口

文档处理接口用于触发或管理文档解析、切分和向量化入库流程。

**使用对象：**

1. 前端应用。
2. 业务后端服务。
3. 开发者。
4. 运维人员。

**主要能力：**

1. 触发文档解析。
2. 触发文档切分。
3. 触发向量化入库。
4. 查询文档处理进度。
5. 查询文档生成的 chunk 列表。
6. 对处理失败的文档进行重试。
7. 对已入库文档进行重新处理的扩展能力。

**关键要求：**

1. 文档处理流程应具备明确状态。
2. 文档处理失败时应记录失败原因。
3. 接口不应让调用方无法判断长流程是否完成。
4. 文档重新处理时，应考虑旧 chunk 和旧向量数据的清理策略。
5. 文档处理接口应避免和文档管理接口职责混乱。

### 8.7 检索接口

检索接口用于根据用户查询从指定知识库中召回相关文本块。该接口可以被 RAG 问答流程内部调用，也可以作为独立调试或 Agent 工具接口暴露。

**使用对象：**

1. 智能 Agent。
2. 业务后端服务。
3. 开发者。
4. 评测人员。

**主要能力：**

1. 接收用户查询。
2. 指定知识库范围。
3. 执行查询向量化。
4. 在 Qdrant 中执行语义检索。
5. 返回候选 chunk。
6. 返回相似度得分和来源元数据。
7. 支持 top_k、score_threshold 等检索参数。
8. 可扩展支持混合检索。

**关键要求：**

1. 检索接口应返回结构化结果。
2. 检索结果应包含 chunk ID、document ID、knowledge base ID 和文本内容摘要。
3. 检索结果应包含相似度得分。
4. 无结果时应返回空结果，而不是系统异常。
5. 检索过程应可被日志或 Trace 追踪。
6. 检索接口应便于开发者调试检索质量。

### 8.8 Rerank 接口

Rerank 接口用于对候选检索结果进行二次排序。该接口可以作为内部能力，也可以在开发调试阶段作为独立接口使用。

**使用对象：**

1. 开发者。
2. 评测人员。
3. 智能 Agent。
4. RAG 问答服务内部流程。

**主要能力：**

1. 接收用户问题和候选 chunk。
2. 计算候选 chunk 与问题的相关性。
3. 返回重排后的候选结果。
4. 返回 rerank_score 或等价重排得分。
5. 支持限制最终返回数量。
6. 支持在 Rerank 服务不可用时降级。

**关键要求：**

1. Rerank 接口应能够对候选结果重新排序。
2. 重排前后的结果应可被追踪或记录。
3. Rerank 失败时应返回明确错误或允许上游流程降级。
4. Rerank 参数和模型配置不应硬编码。
5. 后续应支持替换不同 Rerank 实现。

### 8.9 RAG 问答接口

RAG 问答接口是 ForgeRAG 对外提供知识库问答能力的核心接口，用于基于知识库检索结果生成带引用的回答。

**使用对象：**

1. 前端应用。
2. 业务后端服务。
3. 智能 Agent。
4. 开发者。
5. 评测人员。

**主要能力：**

1. 接收用户问题。
2. 指定知识库范围。
3. 执行语义检索。
4. 可选执行 Rerank。
5. 构造 RAG Prompt。
6. 调用 LLM 生成回答。
7. 返回答案内容。
8. 返回引用来源。
9. 返回问答状态。
10. 返回 trace_id 或 request_id。
11. 保存问答记录。

**关键要求：**

1. 问答接口应返回结构化结果。
2. 结果中应包含答案、引用来源、知识库 ID、问答状态和 trace_id。
3. 引用来源应能追溯到文档和 chunk。
4. 检索结果不足时，应返回无法回答提示，而不是强行生成无依据答案。
5. 模型调用失败时，应返回统一错误结构并记录异常。
6. 问答接口应支持后续扩展模型参数、Prompt 版本和检索配置。

### 8.10 Agentic RAG 问答接口

Agentic RAG 问答接口用于执行具备流程判断能力的问答链路，使系统能够根据问题和中间结果判断是否检索、是否改写问题、是否二次检索、是否生成回答或是否拒答。

**使用对象：**

1. 智能 Agent。
2. 前端应用。
3. 业务后端服务。
4. 开发者。
5. 评测人员。

**主要能力：**

1. 接收用户问题和知识库范围。
2. 执行问题分析。
3. 判断是否需要检索。
4. 必要时改写问题。
5. 执行一次或多次检索。
6. 判断上下文是否足够。
7. 生成带引用回答。
8. 在依据不足时返回拒答结果。
9. 返回流程状态摘要。
10. 返回节点执行信息摘要或 trace_id。

**关键要求：**

1. Agentic RAG 接口应返回最终结果和流程摘要。
2. 返回结果应能区分成功回答、直接回答、拒答和失败。
3. 节点执行过程应可追踪。
4. 二次检索或循环判断应设置最大次数。
5. 接口不应暴露过多内部实现细节，但应提供足够信息用于调试和观测。
6. 后续 LangGraph 节点设计应能够映射到该接口的流程结果。

### 8.11 评测管理接口

评测管理接口用于管理评测数据集、评测样本、评测任务和评测结果，是 RAG 自动化评测能力的接口入口。

**使用对象：**

1. 评测人员。
2. 开发者。
3. 业务后端服务。
4. 自动化脚本。

**主要能力：**

1. 创建评测数据集。
2. 查询评测数据集列表。
3. 管理评测样本。
4. 创建评测任务。
5. 启动评测任务。
6. 查询评测任务状态。
7. 查询评测任务结果。
8. 查询样本级评测结果。
9. 对比不同评测配置下的结果。
10. 关联查看评测样本对应的 Trace。

**关键要求：**

1. 评测任务应具备明确状态。
2. 批量评测不应表现为不可追踪的长时间阻塞。
3. 评测结果应包含检索结果、生成答案、引用来源和评分信息。
4. 评测失败时应记录失败原因。
5. 评测结果应支持后续分析和优化。
6. 评测接口应为自动化脚本调用预留能力。

### 8.12 可观测性与运行记录接口

可观测性与运行记录接口用于查询系统中的问答记录、检索记录、评测记录、Trace 关联信息和运行状态摘要。

**使用对象：**

1. 开发者。
2. 评测人员。
3. 运维人员。
4. 前端应用的管理页面扩展。

**主要能力：**

1. 查询问答历史。
2. 查询问答详情。
3. 查询问答引用来源。
4. 查询问答关联的 trace_id。
5. 查询评测任务关联的 trace_id。
6. 查询文档处理记录。
7. 查询请求执行状态摘要。
8. 为跳转到 Langfuse 或观测平台预留关联信息。

**关键要求：**

1. 运行记录接口应避免暴露敏感信息。
2. 问答记录和评测记录应支持分页查询。
3. Trace 详情可以由 Langfuse 或类似工具管理，ForgeRAG 只需保存必要关联标识。
4. 系统应能够通过记录定位文档处理失败、问答失败和评测失败原因。

### 8.13 系统配置与管理接口

系统配置与管理接口用于支持开发、调试和基础管理。当前阶段不设计复杂后台管理平台，也不将系统扩展为完整 SaaS 管理系统。

**使用对象：**

1. 开发者。
2. 运维人员。
3. 管理类调用方。

**主要能力：**

1. 查询当前服务基础信息。
2. 查询当前运行环境。
3. 查询部分非敏感配置摘要。
4. 查询模型配置摘要。
5. 查询向量库连接状态。
6. 查询数据库连接状态。
7. 为后续动态 Prompt、检索配置和模型配置管理预留能力。

**关键要求：**

1. 不应通过接口返回敏感配置明文。
2. API Key、数据库密码等敏感信息不得暴露。
3. 当前阶段只需要基础运行信息和状态查询。
4. 动态配置管理可以作为后续扩展能力，不作为第一版核心需求。

### 8.14 接口类别总结

ForgeRAG 当前阶段需要提供的接口类别可以概括如下：

| 接口类别               | 主要使用对象               | 核心能力                           |
| ---------------------- | -------------------------- | ---------------------------------- |
| 健康检查接口           | 运维人员、开发者、CI/CD    | 检查服务和依赖是否可用             |
| 知识库管理接口         | 前端、后端服务、开发者     | 管理知识库基础信息                 |
| 文档管理接口           | 前端、后端服务、开发者     | 上传、查询、删除文档               |
| 文档处理接口           | 前端、开发者、运维人员     | 触发解析、切分、入库和重试         |
| 检索接口               | Agent、开发者、评测人员    | 执行语义检索并返回候选 chunk       |
| Rerank 接口            | 开发者、评测人员、内部流程 | 对候选 chunk 进行二次排序          |
| RAG 问答接口           | 前端、后端服务、Agent      | 生成带引用的知识库回答             |
| Agentic RAG 问答接口   | Agent、前端、开发者        | 执行带流程判断的智能问答           |
| 评测管理接口           | 评测人员、开发者、脚本     | 管理评测集、任务和结果             |
| 可观测性与运行记录接口 | 开发者、评测人员、运维人员 | 查询问答记录、Trace 关联和失败原因 |
| 系统配置与管理接口     | 开发者、运维人员           | 查询基础运行状态和非敏感配置摘要   |

### 8.15 接口需求总结

ForgeRAG 的接口需求可以概括为以下原则：

1. **接口面向能力，而不是面向页面**

   ForgeRAG 不开发完整 Web 前端，因此 API 应作为后端能力层设计，服务于前端、业务后端、自动化脚本和智能 Agent 等多种调用方。

2. **接口返回必须结构化**

   尤其是检索、问答、Agentic RAG 和评测接口，应返回可解析的结构化数据，而不是只返回自然语言文本。

3. **问答接口必须支持引用来源**

   RAG 问答和 Agentic RAG 问答结果应包含引用来源，保证回答具备可追溯性。

4. **关键接口必须可追踪**

   文档入库、检索问答、Agentic RAG 和评测任务应能够关联 trace_id 或 request_id。

5. **长流程必须可查询状态**

   文档处理和评测任务等耗时流程应具备状态查询能力。

6. **错误响应必须统一**

   参数错误、资源不存在、处理失败、外部服务异常和系统异常应遵循统一错误结构。

7. **接口细节后续单独设计**

   本章只定义接口类别和能力边界，具体 URL、请求字段、响应字段、错误码和示例将在 API 设计文档中详细定义。





## 9. 权限与安全需求

ForgeRAG 当前阶段的安全目标是：在不引入复杂权限系统的前提下，保证系统具备基础的访问边界、输入校验、文件上传限制、配置与密钥保护、异常响应控制、日志与 Trace 安全，以及 RAG 回答安全约束。

ForgeRAG 第一版不优先实现完整 RBAC、多租户组织架构、企业单点登录、部门级数据隔离和复杂审批流，但系统在设计时应为后续权限扩展预留基础能力，避免后续重构成本过高。

### 9.1 当前阶段安全定位

当前阶段的 ForgeRAG 主要面向学习型企业级 RAG 后端系统建设，安全能力应保持适度，不应过早引入复杂权限体系，但也不能忽视基本工程安全要求。

**需求说明：**

1. 系统第一版可以不实现完整 RBAC 权限模型。
2. 系统第一版可以不实现多租户组织架构。
3. 系统第一版可以不实现企业单点登录。
4. 系统第一版可以不实现复杂文档级权限控制。
5. 系统必须具备基础接口输入校验能力。
6. 系统必须限制文件上传类型和大小。
7. 系统不得硬编码数据库密码、模型 API Key、Langfuse Secret Key 等敏感配置。
8. 系统不得在接口响应中直接暴露内部异常堆栈。
9. 系统应避免在日志和 Trace 中记录不必要的敏感信息。
10. 系统应在缺少可靠知识依据时执行拒答或无法回答策略。

**验收要点：**

1. 项目文档明确说明第一版不做复杂权限系统。
2. 所有接口请求参数均经过基础校验。
3. 上传文件类型和大小受到限制。
4. `.env` 等敏感配置文件不提交到代码仓库。
5. 异常响应不直接暴露内部堆栈。
6. 日志和 Trace 中不主动记录 API Key、数据库密码等敏感信息。

### 9.2 用户身份与调用方标识需求

ForgeRAG 当前阶段可以先采用简单调用模式，但应为后续用户身份、调用方标识和访问控制预留扩展点。

**需求说明：**

1. 系统可以在第一版中暂不实现完整用户注册、登录和角色系统。
2. 系统可以预留 `user_id`、`owner_id`、`created_by` 等字段，用于记录资源归属。
3. 系统可以预留调用方标识，例如 `client_id`、`api_key_id` 或请求来源标识。
4. 系统应为后续接入 API Key、JWT、OAuth2 或企业单点登录预留扩展空间。
5. 问答记录、文档记录、评测任务等关键业务数据可以预留创建者或调用方信息。
6. 系统应避免将所有资源设计为完全无归属状态，以免后续权限扩展困难。

**验收要点：**

1. 数据模型设计时为用户身份或调用方标识预留字段。
2. 文档、知识库、问答记录和评测任务具备后续归属扩展能力。
3. 接口设计不应阻碍后续添加认证和授权机制。
4. 后续接入 API Key 或 JWT 时，不需要大规模重写核心业务逻辑。

### 9.3 知识库访问边界需求

知识库是 ForgeRAG 的核心业务边界。即使第一版不做复杂权限控制，也应保证请求在指定知识库范围内执行，避免跨知识库误检索或误操作。

**需求说明：**

1. 文档上传时必须指定目标知识库。
2. 文档查询应支持按知识库范围过滤。
3. 语义检索必须限定知识库范围。
4. RAG 问答必须指定知识库或明确的知识库检索范围。
5. Agentic RAG 流程中的检索节点也必须遵守知识库范围。
6. 评测任务应明确绑定目标知识库。
7. 删除知识库、删除文档等操作应明确处理关联数据边界。
8. 系统不应在未指定知识库范围的情况下默认检索全部知识库，除非后续明确设计全局检索能力。

**验收要点：**

1. 检索接口可以根据 `knowledge_base_id` 限定范围。
2. 问答接口可以根据 `knowledge_base_id` 限定范围。
3. 文档列表可以按知识库查询。
4. 评测任务可以绑定指定知识库。
5. 不存在知识库时，系统返回统一错误响应。
6. 禁用或删除状态的知识库不应作为普通问答和文档入库目标。

### 9.4 文件上传安全需求

文档上传是 ForgeRAG 的重要入口，也可能带来文件类型、文件大小、异常文件和无效内容等风险。当前阶段应至少具备基础上传安全控制。

**需求说明：**

1. 系统应限制允许上传的文件类型。
2. 系统应限制单个文件大小。
3. 系统应校验文件扩展名和基础 MIME 类型。
4. 系统应对空文件或无法解析出有效文本的文件返回明确错误。
5. 系统应为文档解析失败记录失败原因。
6. 系统应避免直接使用用户上传文件名作为最终存储路径。
7. 系统应为上传文件生成内部唯一标识。
8. 系统应避免文件路径穿越风险。
9. 系统应为后续接入病毒扫描、对象存储或更严格文件检测预留扩展空间。

**验收要点：**

1. 上传不支持的文件类型时，系统返回明确错误。
2. 上传超过大小限制的文件时，系统拒绝处理。
3. 空文档或无有效文本内容的文档会被标记为处理失败。
4. 文档处理失败原因可以被查询。
5. 文件存储路径不直接信任用户原始文件名。
6. 上传文件不会覆盖系统已有文件。

### 9.5 配置与密钥安全需求

ForgeRAG 需要连接 PostgreSQL、Qdrant、LLM 服务、Embedding 服务、Rerank 服务和 Langfuse 等外部系统，因此必须正确管理配置与密钥。

**需求说明：**

1. 数据库连接地址、用户名和密码应通过环境变量或配置文件管理。
2. 模型 API Key 不得硬编码在代码中。
3. Langfuse Public Key、Secret Key 和 Host 应通过环境变量或配置文件管理。
4. `.env` 文件不应提交到 Git 仓库。
5. 项目应提供 `.env.example` 或等价示例配置文件。
6. 配置加载失败时，应返回明确错误或启动失败提示。
7. 日志中不得输出完整密钥、密码或 Token。
8. CI/CD 配置中应通过 Secrets 管理敏感信息。
9. 本地开发、测试和部署环境应能够使用不同配置。

**验收要点：**

1. 代码仓库中不存在明文数据库密码。
2. 代码仓库中不存在明文模型 API Key。
3. 代码仓库中不存在明文 Langfuse Secret Key。
4. `.gitignore` 已排除 `.env` 等敏感配置文件。
5. `.env.example` 只包含示例值，不包含真实密钥。
6. 系统启动时可以从配置模块读取必要配置。

### 9.6 接口输入校验需求

接口输入校验用于保证无效参数不会直接进入业务逻辑、数据库访问、向量检索或模型调用流程。

**需求说明：**

1. 所有接口应校验必填字段。
2. 所有接口应校验字段类型。
3. 字符串字段应限制长度。
4. 枚举字段应限制可选值。
5. ID 类型字段应校验格式或有效性。
6. 分页参数应限制最小值和最大值。
7. 检索参数如 `top_k`、`score_threshold` 应限制合理范围。
8. Agentic RAG 最大循环次数、二次检索次数等参数应限制范围。
9. 文件上传接口应校验文件类型和大小。
10. 参数错误时应返回统一错误结构。

**验收要点：**

1. 缺少必填字段时，接口返回参数错误。
2. 字段类型错误时，接口返回参数错误。
3. 非法枚举值不会进入业务逻辑。
4. 非法分页参数不会导致异常查询。
5. 不合理的 `top_k` 或阈值参数会被拒绝或修正。
6. 参数错误响应格式与其他错误响应保持一致。

### 9.7 异常响应安全需求

系统异常响应应保护内部实现细节，避免直接暴露数据库结构、文件路径、第三方服务错误堆栈或 Python 原始异常信息。

**需求说明：**

1. 系统应提供全局异常处理机制。
2. 业务异常应返回明确业务错误码和错误信息。
3. 参数异常应返回统一参数错误响应。
4. 资源不存在应返回统一资源不存在响应。
5. 外部服务异常应返回统一外部依赖错误响应。
6. 未知异常应返回统一系统错误响应。
7. 接口响应中不应直接暴露原始异常堆栈。
8. 内部异常详情应写入日志或 Trace，而不是直接返回给调用方。
9. 开发环境可以保留更详细调试信息，但生产或演示环境应收敛异常输出。

**验收要点：**

1. 数据库异常不会直接把 SQL 堆栈暴露给调用方。
2. 模型调用异常不会直接把完整第三方响应暴露给调用方。
3. 文件解析异常不会暴露服务器内部路径。
4. 未捕获异常会被全局异常处理捕获。
5. 调用方收到的错误响应格式统一、信息明确。

### 9.8 日志与 Trace 安全需求

ForgeRAG 需要记录 RAG 和 Agentic RAG 链路，但日志与 Trace 中可能包含用户问题、文档片段、Prompt、模型输出和外部调用信息，因此需要控制记录内容。

**需求说明：**

1. 系统应记录必要的请求 ID 或 trace_id。
2. 系统应记录关键链路信息，例如检索、重排、Prompt、LLM 输出和异常。
3. 系统不应记录数据库密码、API Key、Secret Key 等敏感配置。
4. 系统应避免在日志中记录完整上传文件内容。
5. 系统应避免记录不必要的用户隐私信息。
6. Prompt 和 LLM 输出可以用于调试和观测，但应意识到其中可能包含敏感文档片段。
7. 评测数据和 Trace 数据应具备基本访问边界，后续可扩展权限控制。
8. 日志输出应区分普通业务日志和异常日志。
9. 观测工具不可用时，系统应尽量降级，不应让日志或 Trace 写入失败阻断核心问答流程。

**验收要点：**

1. 日志中不出现明文 API Key。
2. 日志中不出现数据库密码。
3. Trace 中可以关联问答记录，但不会记录不必要的敏感配置。
4. Langfuse 调用失败时，核心 RAG 问答流程仍可继续执行或返回可控错误。
5. 日志和 Trace 能够用于排查问题，同时不泄露系统敏感配置。

### 9.9 Prompt 与回答安全需求

RAG 系统的回答安全重点在于：模型回答应尽量基于检索上下文，不应在缺少依据时强行编造。同时，Prompt 应约束模型使用知识库内容，并在上下文不足时允许拒答。

**需求说明：**

1. RAG Prompt 应明确要求模型优先基于检索上下文回答。
2. Prompt 应要求模型在上下文不足时说明无法回答。
3. 系统应在检索结果为空或低相关时返回无法回答提示。
4. 系统应避免把无关 chunk 强行拼入上下文。
5. 系统应返回引用来源，便于调用方验证回答依据。
6. Agentic RAG 流程应包含上下文充分性判断。
7. Agentic RAG 流程应支持拒答策略。
8. 系统应避免将模型输出视为绝对事实，应保留引用和追踪信息。
9. 后续可以扩展对 Prompt 注入、越权提问和敏感内容输出的防护策略。

**验收要点：**

1. 无检索结果时，问答接口能够返回无法回答提示。
2. 检索结果明显不足时，系统不会强行生成确定性答案。
3. 回答结果包含引用来源。
4. 引用来源可以追溯到文档和 chunk。
5. Agentic RAG 能够在上下文不足时走拒答路径。
6. Prompt 模板中包含基于上下文回答和不足时拒答的约束。

### 9.10 后续权限扩展方向

虽然 ForgeRAG 第一版不优先实现复杂权限系统，但应在设计上预留扩展方向，便于后续逐步增强安全能力。

**后续可扩展方向包括：**

1. 用户注册与登录。
2. JWT 认证。
3. API Key 调用方认证。
4. 用户与知识库归属关系。
5. 基础角色模型，例如普通用户、管理员。
6. 知识库级访问控制。
7. 文档级访问控制。
8. 团队或组织空间。
9. 操作审计日志。
10. 企业单点登录。
11. 多租户隔离。
12. 敏感文档脱敏和访问审批。
13. 更严格的 Prompt 注入防护。
14. 更严格的日志与 Trace 数据访问权限。

**当前阶段处理原则：**

1. 只实现必要的基础安全能力。
2. 不提前设计过重的权限系统。
3. 保留必要字段和模块边界。
4. 确保后续扩展认证与授权时不破坏主业务链路。
5. 优先保证 RAG 后端核心闭环可运行、可评测、可观测。

### 9.11 权限与安全需求总结

ForgeRAG 当前阶段的权限与安全需求可以概括为以下原则：

1. **安全能力适度**

   第一版不做复杂 RBAC、多租户和企业单点登录，但必须具备基础安全边界。

2. **知识库边界清晰**

   文档、检索、问答和评测都应围绕明确的知识库范围展开。

3. **输入必须校验**

   接口参数、文件类型、文件大小、检索参数和流程控制参数都应进行校验。

4. **密钥不能硬编码**

   数据库密码、模型 API Key、Langfuse Secret Key 等敏感配置必须通过环境变量或配置文件管理。

5. **异常不能泄露内部细节**

   调用方应收到统一错误响应，内部堆栈和外部服务细节应进入日志或 Trace。

6. **日志和 Trace 需要安全边界**

   可观测性数据应服务于调试和评测，但不能泄露密钥、密码或不必要的敏感信息。

7. **回答必须有知识依据**

   RAG 问答应尽量基于检索上下文生成，并在依据不足时拒答或提示无法回答。

8. **为后续权限增强预留空间**

   数据模型、接口设计和模块边界应支持后续扩展用户身份、API Key、JWT、角色和知识库访问控制。





## 10. 可观测性与评测需求

可观测性与评测是 ForgeRAG 区别于普通 RAG Demo 的重要能力。普通 RAG 系统往往只关注“是否能回答”，但企业级 RAG 后端系统还需要回答以下问题：

1. 系统为什么这样回答？
2. 检索到了哪些文档片段？
3. Rerank 是否改善了上下文质量？
4. Prompt 输入了什么内容？
5. LLM 输出是否忠实于检索上下文？
6. 回答引用是否可靠？
7. Agentic RAG 的每个节点是如何决策的？
8. 当前 RAG 策略是否比上一版更好？
9. 检索质量和回答质量能否被量化评估？
10. 出现错误时能否定位失败节点和失败原因？

因此，ForgeRAG 需要同时建设可观测性能力和自动化评测能力。可观测性用于记录和分析一次请求的执行过程，自动化评测用于衡量系统在一组问题上的整体效果。二者共同支撑系统调试、质量分析和持续优化。

### 10.1 可观测性需求定位

可观测性需求的目标是让开发者能够理解 ForgeRAG 内部执行过程，尤其是 RAG 和 Agentic RAG 链路中的检索、重排、Prompt 构造、模型调用、节点决策和异常情况。

**需求说明：**

1. 系统应记录一次 RAG 问答请求的完整执行过程。
2. 系统应记录一次 Agentic RAG 请求的节点状态流转。
3. 系统应记录模型调用的输入、输出、耗时和 Token 消耗。
4. 系统应记录检索结果、Rerank 结果和引用来源。
5. 系统应记录异常信息和失败原因。
6. 系统应支持通过 trace_id 或 request_id 将业务记录与链路追踪数据关联。
7. 系统应支持接入 Langfuse 或类似可观测性工具。
8. 系统应保证可观测性能力服务于调试、评测和优化，而不是只记录零散日志。

**关键记录内容：**

1. request_id。
2. trace_id。
3. 用户问题。
4. 知识库 ID。
5. 检索查询。
6. 召回结果。
7. Rerank 结果。
8. Prompt 输入。
9. LLM 输出。
10. Token 消耗。
11. 模型名称。
12. 节点状态。
13. 执行耗时。
14. 异常信息。

**验收要点：**

1. 每次 RAG 问答请求都可以关联到一个 trace_id 或 request_id。
2. 开发者可以通过链路记录查看检索、重排、生成和引用过程。
3. Agentic RAG 请求可以查看节点流转过程。
4. 模型调用失败时可以定位失败原因。
5. 可观测性工具不可用时，核心业务流程应尽量降级，而不是直接崩溃。

### 10.2 RAG 链路追踪需求

RAG 链路追踪用于记录普通 RAG 问答流程中的关键步骤，帮助开发者分析回答质量和检索质量。

**需求说明：**

一次基础 RAG 问答请求应至少追踪以下步骤：

1. 接收用户问题。
2. 校验知识库。
3. 问题向量化。
4. 向量检索。
5. 候选 chunk 返回。
6. Rerank 重排。
7. 上下文选择。
8. Prompt 构造。
9. LLM 调用。
10. 答案生成。
11. 引用来源返回。
12. 问答记录保存。

**关键记录内容：**

1. 用户原始问题。
2. 目标知识库。
3. Embedding 模型名称。
4. 检索参数，例如 top_k、score_threshold。
5. 检索召回的 chunk 列表。
6. 检索相似度得分。
7. Rerank 前后的排序结果。
8. 最终进入 Prompt 的上下文。
9. Prompt 模板版本。
10. LLM 模型名称。
11. LLM 输出。
12. 引用来源。
13. 请求总耗时。
14. 各步骤耗时。

**验收要点：**

1. 开发者可以查看一次问答使用了哪些 chunk。
2. 开发者可以查看检索结果和最终引用是否一致。
3. 开发者可以判断 Rerank 是否改变了候选结果排序。
4. 开发者可以查看最终 Prompt 使用了哪些上下文。
5. 开发者可以根据耗时定位慢步骤。
6. 问答记录可以关联到对应 Trace。

### 10.3 Agentic RAG 节点追踪需求

Agentic RAG 链路比普通 RAG 更复杂，系统需要记录每个节点的输入、输出、判断结果和下一步流转方向。

**需求说明：**

Agentic RAG 流程应至少追踪以下节点类型：

1. 问题分析节点。
2. 是否需要检索判断节点。
3. 问题改写节点。
4. 检索节点。
5. Rerank 节点。
6. 是否需要二次检索判断节点。
7. 上下文充分性判断节点。
8. 回答生成节点。
9. 拒答节点。
10. 结束节点。

**关键记录内容：**

1. 节点名称。
2. 节点输入。
3. 节点输出。
4. 节点判断结果。
5. 下一步节点。
6. 节点执行耗时。
7. 节点异常信息。
8. 当前状态对象摘要。
9. 原始问题。
10. 改写后的问题。
11. 一次检索结果。
12. 二次检索结果。
13. 最终回答或拒答原因。

**验收要点：**

1. 开发者可以查看 Agentic RAG 执行经过了哪些节点。
2. 开发者可以查看系统为什么决定检索或不检索。
3. 开发者可以查看问题是否被改写，以及改写后的查询内容。
4. 开发者可以查看是否触发了二次检索。
5. 开发者可以查看系统为什么生成回答或为什么拒答。
6. Agentic RAG 不应出现无法追踪的隐式决策过程。

### 10.4 模型调用观测需求

ForgeRAG 需要调用 LLM、Embedding 模型和 Rerank 模型。模型调用是系统成本、性能和质量的重要来源，因此需要记录关键观测信息。

**需求说明：**

系统应记录以下模型调用：

1. Embedding 模型调用。
2. Rerank 模型调用。
3. LLM 问答生成调用。
4. LLM 问题改写调用。
5. LLM 上下文充分性判断调用。
6. LLM 自动评测或评分调用的扩展能力。

**关键记录内容：**

1. 模型类型。
2. 模型名称。
3. 输入摘要。
4. 输出摘要。
5. 调用参数。
6. Token 消耗。
7. 调用耗时。
8. 调用状态。
9. 失败原因。
10. 重试次数的扩展信息。

**验收要点：**

1. LLM 调用可以查看模型名称、输入、输出、耗时和 Token 消耗。
2. Embedding 调用失败时可以定位失败原因。
3. Rerank 调用失败时可以记录失败信息并支持降级策略。
4. 模型调用信息可以与问答记录或评测结果关联。
5. 日志和 Trace 中不得记录模型 API Key 等敏感配置。

### 10.5 异常与耗时观测需求

ForgeRAG 需要能够定位系统异常和性能瓶颈。尤其是文档入库、向量化、检索、模型调用、Agentic RAG 和评测任务等流程，都可能出现耗时较长或失败的情况。

**需求说明：**

系统应记录以下异常与耗时信息：

1. 文档解析失败。
2. 文本切分失败。
3. Embedding 调用失败。
4. Qdrant 写入失败。
5. Qdrant 检索失败。
6. Rerank 调用失败。
7. LLM 调用失败。
8. Agentic RAG 节点执行失败。
9. 评测任务执行失败。
10. 数据库访问失败。
11. 配置缺失或配置错误。
12. 请求总耗时和关键步骤耗时。

**关键记录内容：**

1. 异常类型。
2. 错误信息。
3. 失败模块。
4. 失败步骤。
5. request_id。
6. trace_id。
7. 业务对象 ID，例如 document_id、qa_record_id、eval_task_id。
8. 失败发生时间。
9. 当前处理状态。

**验收要点：**

1. 文档处理失败后，可以查看失败原因。
2. 问答失败后，可以通过 trace_id 定位失败步骤。
3. 评测任务失败后，可以查看失败样本和失败原因。
4. 请求耗时可以拆分到检索、重排、模型调用等关键步骤。
5. 未知异常不会直接暴露给接口调用方，但会被系统记录。

### 10.6 评测数据集需求

评测数据集是 RAG 自动化评测的基础。系统需要支持管理问题、参考答案、期望引用和标签信息。

**需求说明：**

系统应支持评测数据集相关能力：

1. 创建评测数据集。
2. 查询评测数据集列表。
3. 查询评测数据集详情。
4. 新增评测样本。
5. 修改评测样本。
6. 删除评测样本。
7. 为评测样本保存参考答案。
8. 为评测样本保存期望引用。
9. 为评测样本保存标签或分类。
10. 为后续导入和导出评测数据集预留能力。

**关键记录内容：**

1. 评测数据集名称。
2. 评测数据集描述。
3. 评测问题。
4. 参考答案。

7. 难度标签。
8. 适用知识库。

**验收要点：**

2. 一个评测数据集可以包含多个评测样本。
3. 每个样本至少包含问题。
4. 样本可以选择性包含参考答案和期望引用。
5. 评测数据集可以被后续评测任务复用。

### 10.7 评测任务需求

评测任务用于基于指定数据集和指定配置批量执行 RAG 或 Agentic RAG 问答，并保存执行结果。

**需求说明：**

系统应支持评测任务相关能力：

1. 创建评测任务。
2. 指定评测数据集。

4. 指定问答模式，例如基础 RAG 或 Agentic RAG。
5. 指定检索参数。
6. 指定是否启用 Rerank。
7. 指定 Prompt 版本或模型配置的扩展能力。
8. 启动评测任务。
9. 查询评测任务状态。
10. 查询评测任务结果。
11. 记录任务失败原因。
12. 支持对不同配置结果进行对比。

**关键记录内容：**

1. eval_task_id。
2. eval_dataset_id。
3. knowledge_base_id。
4. 问答模式。
5. 检索参数。
6. Rerank 配置。
7. Prompt 版本。

11. 成功数量。

**验收要点：**

1. 可以基于评测数据集创建评测任务。

3. 评测任务具备明确状态。

5. 可以查询每个样本的执行结果。

### 10.8 评测指标需求

评测指标用于衡量 RAG 系统的检索质量、回答质量、引用质量和上下文利用情况。

**需求说明：**

ForgeRAG 当前阶段可以优先支持以下评测维度：

1. 检索相关性。
2. 回答准确性。
3. 上下文利用情况。
4. 引用来源正确性。
5. 回答是否忠实于上下文。
6. 拒答是否合理。
7. Agentic RAG 决策路径是否合理。
8. 请求耗时。
9. Token 消耗。
10. 失败率。

**关键记录内容：**

1. 检索得分。
2. Rerank 得分。
3. 回答评分。
4. 引用评分。
5. 上下文利用评分。
6. 忠实性评分。

评测结果分析用于帮助开发者比较不同配置下的 RAG 效果，并找到优化方向。

**需求说明：**

系统应支持基于评测结果进行分析：

1. 查看评测任务整体结果。
2. 查看单个样本结果。
3. 查看失败样本列表。
4. 查看低分样本列表。
5. 查看检索结果与期望引用是否匹配。
6. 查看回答与参考答案的差异。
7. 对比不同检索参数的效果。
8. 对比是否启用 Rerank 的效果。
9. 对比不同 Prompt 版本的效果。
10. 对比基础 RAG 与 Agentic RAG 的效果。
11. 根据评测结果定位失败链路。
12. 输出后续优化方向。

**关键记录内容：**

1. 评测任务汇总结果。
2. 样本级结果。
3. 失败原因。
4. 低分原因。
5. 检索结果。

**验收要点：**

4. 可以对比不同配置下的评测结果。
5. 评测结果能够为切分策略、检索参数、Rerank 策略和 Prompt 优化提供依据。

### 10.10 可观测性与评测关联需求

可观测性和评测不应相互独立。评测发现的问题，应能够通过链路追踪进一步分析；链路追踪记录的数据，也应能够为评测结果解释提供依据。

**需求说明：**

1. 问答记录应关联 trace_id。
2. 评测样本执行结果应关联 qa_record_id。
3. 评测样本执行结果应关联 trace_id。
4. 评测失败样本应能跳转或定位到对应链路记录。
5. Trace 中应包含检索、重排、Prompt、LLM 输出和引用来源等信息。
6. 评测结果中应保存关键实验配置。
7. 开发者应能够根据评测结果定位到具体失败步骤。
8. 开发者应能够根据 Trace 判断评测低分原因。

**典型分析路径：**

```text
评测任务结果 → 低分样本 → 问答记录 → trace_id → 检索结果 → Rerank 结果 → Prompt → LLM 输出 → 引用来源 → 优化方向
```

**验收要点：**

1. 评测结果可以关联问答记录。
2. 问答记录可以关联 Trace。
3. 低分样本可以通过 Trace 查看完整执行链路。
4. 开发者可以判断问题出在检索、重排、Prompt、模型生成还是引用选择。
5. 可观测性数据和评测数据共同服务于 RAG 系统优化。

### 10.11 可观测性与评测需求总结

ForgeRAG 的可观测性与评测需求可以概括为以下原则：

1. **请求过程必须可追踪**

   普通 RAG、Agentic RAG、文档处理和评测任务都应能够记录关键执行过程。

2. **Agentic RAG 决策必须可解释**

   系统应能追踪每个节点的输入、输出、判断结果和状态流转。

3. **模型调用必须可分析**

   LLM、Embedding 和 Rerank 调用应记录模型名称、输入输出摘要、耗时、Token 消耗和失败原因。

4. **异常和耗时必须可定位**

   文档处理失败、检索失败、模型调用失败和评测失败都应具备明确记录。

5. **RAG 效果必须可评测**

   系统应支持评测数据集、评测任务、评测结果和多维度评分。

6. **评测结果必须可解释**

   评测结果应能关联问答记录和 Trace，帮助开发者定位低分原因。

7. **优化方向必须有依据**

   切分策略、检索参数、Rerank 策略、Prompt 模板和 Agentic RAG 流程的优化，应基于可观测性数据和评测数据共同判断。





## 11. 边界与约束

边界与约束用于明确 ForgeRAG 当前阶段的需求范围、技术限制、开发优先级和后续扩展边界。ForgeRAG 的目标是构建一个企业知识库 Agentic RAG 后端系统，而不是一次性覆盖完整 Web 平台、商业化 SaaS 平台、模型训练平台或大规模分布式架构。

本文档中的所有需求都应服务于以下主线：

```text
文档解析 → 文本切分 → 向量化入库 → 语义检索 → Rerank 重排 → 带引用问答 → Agentic RAG 流程控制 → 自动化评测 → 链路追踪与优化
```

当前阶段的核心原则是：优先完成一个清晰、稳定、可运行、可测试、可评测、可观测的 RAG 后端闭环，再逐步扩展高级能力。

### 11.1 项目范围边界

ForgeRAG 当前阶段只聚焦 RAG 后端能力建设，不做完整 Web 前端、不做完整商业 SaaS 平台、不做复杂企业管理系统。

**约束说明：**

1. 系统主要通过 REST API 对外提供能力。
2. 当前阶段不开发完整知识库管理后台。
3. 当前阶段不开发完整聊天页面。
4. 当前阶段不开发完整评测可视化平台。
5. 当前阶段不设计商业化租户、套餐、计费、运营后台等能力。
6. 当前阶段不以构建完整企业知识库产品为目标。
7. 当前阶段重点是 RAG 后端主链路、Agentic RAG、评测、可观测性和工程规范。

**当前阶段处理原则：**

1. 前端能力只作为调用方需求考虑，不作为开发重点。
2. API 设计应保持结构清晰，方便后续前端接入。
3. 项目文档应明确说明 ForgeRAG 是后端能力系统，不是完整 Web 应用。
4. 后续如果需要开发前端，应基于现有 API 独立规划，而不是影响当前后端主线。

### 11.2 技术实现约束

ForgeRAG 当前阶段采用 Python 生态下的后端与 AI 应用技术栈，围绕 FastAPI、LangChain、LangGraph、PostgreSQL、Qdrant、Langfuse 和 Docker Compose 构建系统。

**约束说明：**

1. 后端框架以 FastAPI 为主。
2. 业务元数据以 PostgreSQL 为主要存储。
3. 向量数据以 Qdrant 为主要存储。
4. RAG 基础链路优先基于 LangChain 进行封装。
5. Agentic RAG 流程优先基于 LangGraph 进行编排。
6. 可观测性优先接入 Langfuse 或保留兼容封装。
7. 数据库访问优先使用 SQLAlchemy。
8. 数据库迁移优先使用 Alembic。
9. 测试优先使用 pytest。
10. 本地开发和演示环境优先使用 Docker Compose。

**当前阶段处理原则：**

1. 不在第一版中引入过多同类框架进行对比实现。
2. 不为了追求架构复杂度提前引入微服务拆分。
3. 不在需求分析阶段过早绑定具体模型厂商。
4. 模型服务、Embedding 服务、Rerank 服务应通过配置管理，避免硬编码。
5. 技术选型应服务于项目可运行、可维护和可学习，而不是单纯追求复杂度。

### 11.3 开发阶段约束

ForgeRAG 应采用分阶段建设方式，先完成基础工程骨架和 RAG 主链路，再逐步增强 Rerank、Agentic RAG、自动化评测、可观测性、测试和部署能力。

**约束说明：**

1. 不应在项目初期同时开发所有模块。
2. 不应在基础工程尚未稳定前直接堆叠复杂 Agentic RAG 流程。
3. 不应在文档入库链路未完成前开发复杂评测能力。
4. 不应在基础 RAG 问答未稳定前过度优化高级 RAG 策略。
5. 不应在核心链路未跑通前投入大量精力实现权限系统、后台管理或云原生部署。
6. 每个阶段都应有明确产物和验收标准。

**当前阶段处理原则：**

1. 阶段 0 先完成项目规划、目录结构和文档规范。
2. 阶段 1 先完成 FastAPI 基础后端骨架。
3. 阶段 2 至阶段 4 优先打通知识库、文档入库和基础 RAG 问答。
4. 阶段 5 至阶段 8 再增强 Rerank、Agentic RAG、评测和观测。
5. 阶段 9 再完善测试、部署和 CI/CD。
6. 每个阶段完成后再进入下一阶段，避免需求交叉导致项目失控。

### 11.4 权限与安全约束

ForgeRAG 第一版不优先实现复杂权限系统，但必须具备基础安全边界，包括输入校验、文件上传限制、密钥保护、异常响应控制和日志安全。

**约束说明：**

1. 当前阶段不实现完整 RBAC 权限模型。
2. 当前阶段不实现多租户组织架构。
3. 当前阶段不实现企业单点登录。
4. 当前阶段不实现复杂部门级数据隔离。
5. 当前阶段不实现完整文档级权限控制。
6. 系统应为用户身份、调用方标识、知识库归属等能力预留扩展点。
7. 系统不得硬编码数据库密码、模型 API Key、Langfuse Secret Key 等敏感信息。
8. 系统不得在接口响应中直接暴露内部异常堆栈。
9. 系统不得在日志或 Trace 中记录不必要的敏感配置。
10. 文件上传必须限制类型和大小。

**当前阶段处理原则：**

1. 先实现基础安全要求。
2. 通过环境变量或配置文件管理敏感配置。
3. 通过统一异常处理控制错误响应。
4. 通过参数校验和文件校验降低输入风险。
5. 数据结构中预留用户、调用方或资源归属字段。
6. 后续再根据项目进度扩展 JWT、API Key、RBAC 或知识库访问控制。

### 11.5 数据与存储约束

ForgeRAG 同时涉及结构化业务数据、向量数据、文件数据、链路追踪数据和运行日志，不同数据类型应有明确存储职责。

**约束说明：**

1. PostgreSQL 用于管理结构化业务数据。
2. Qdrant 用于管理 chunk 向量数据。
3. Langfuse 或类似工具用于管理 Trace、Span 和模型调用观测数据。
4. 原始文件当前阶段可以先存储在本地文件系统。
5. 系统配置优先通过环境变量或配置文件管理。
6. PostgreSQL 不负责存储完整向量本体。
7. Qdrant 不负责承担完整业务数据库职责。
8. 日志系统不应替代业务数据存储。
9. Trace 数据不应替代问答记录和评测记录。
10. 评测结果应记录关键配置，便于后续复现。

**当前阶段处理原则：**

1. 业务数据与向量数据通过 `knowledge_base_id`、`document_id`、`chunk_id` 等标识关联。
2. 问答记录、评测结果和 Trace 通过 `qa_record_id`、`eval_task_id`、`trace_id` 等标识关联。
3. 文档删除或重新处理时，应考虑 PostgreSQL 与 Qdrant 的数据一致性。
4. 当前阶段不设计复杂数据湖、全文索引集群或多存储同步平台。
5. 数据库字段细节留到数据库设计文档中展开。

### 11.6 部署与运行约束

ForgeRAG 当前阶段以本地开发、课程项目展示和中小规模演示为主要运行场景，不追求复杂生产级部署体系。

**约束说明：**

1. 当前阶段部署方式以 Docker Compose 为主。
2. 当前阶段不引入 Kubernetes。
3. 当前阶段不拆分微服务。
4. 当前阶段不设计服务注册与发现。
5. 当前阶段不设计分布式事务。
6. 当前阶段不设计多副本高可用架构。
7. 当前阶段不设计多地域部署。
8. 当前阶段不设计完整生产运维平台。

**当前阶段处理原则：**

1. Docker Compose 应能启动 FastAPI、PostgreSQL、Qdrant 和 Langfuse 等基础组件。
2. 系统应提供 `.env.example` 或等价示例配置文件。
3. 系统应提供健康检查接口。
4. 系统应提供基础部署说明。
5. 系统应保证新开发者能够根据文档复现本地环境。
6. 后续如需生产化部署，再单独设计 Kubernetes、监控告警、日志采集和高可用方案。

### 11.7 评测与可观测性约束

ForgeRAG 将评测和可观测性作为核心能力，但当前阶段应保持实现范围可控，不应一开始构建过重的实验平台或监控平台。

**约束说明：**

1. 当前阶段评测重点是 RAG 检索质量、回答质量、引用质量和上下文利用情况。
2. 当前阶段不构建完整实验管理平台。
3. 当前阶段不实现复杂可视化评测报表。
4. 当前阶段不实现完整 A/B Testing 平台。
5. 当前阶段可先支持评测数据集、评测任务、评测结果和基础对比能力。
6. 可观测性重点追踪 RAG 和 Agentic RAG 的关键链路。
7. 当前阶段可优先接入 Langfuse，不需要自研完整链路追踪平台。
8. Langfuse 不可用时，核心业务流程应尽量具备降级能力。

**当前阶段处理原则：**

1. 先记录关键链路数据，再逐步增强分析能力。
2. 先支持基础评测任务，再扩展复杂评分维度。
3. 先支持人工评分和基础自动评分记录，再扩展 LLM-as-Judge。
4. 先保证问答记录、评测结果和 Trace 可以关联。
5. 复杂可视化分析可以作为后续前端或平台扩展方向。

### 11.8 模型能力约束

ForgeRAG 不负责训练模型，而是调用已有 LLM、Embedding 模型和 Rerank 模型能力，重点在于如何将模型能力工程化接入 RAG 后端系统。

**约束说明：**

1. 当前阶段不训练大语言模型。
2. 当前阶段不进行大语言模型微调。
3. 当前阶段不训练 Embedding 模型。
4. 当前阶段不训练 Rerank 模型。
5. 当前阶段不建设 GPU 训练集群。
6. 当前阶段不建设模型训练平台。
7. 系统应通过配置管理模型名称、服务地址和调用参数。
8. 系统应允许后续替换不同模型服务。

**当前阶段处理原则：**

1. 优先完成模型调用封装。
2. 优先保证模型配置不硬编码。
3. 优先保证模型调用可观测。
4. 优先保证模型异常可处理。
5. 后续如需私有模型或微调模型，应作为独立扩展方向设计。

### 11.9 高级 RAG 扩展边界

ForgeRAG 当前阶段优先完成文本知识库 RAG 后端闭环，不在第一版中展开所有高级 RAG 能力。

**暂不纳入第一版的高级能力包括：**

1. 多模态 RAG。
2. 知识图谱增强 RAG。
3. 多 Agent 协作。
4. 长期记忆系统。
5. 自动工具调用市场。
6. 跨系统知识同步。
7. 复杂工作流编排平台。
8. 多轮对话记忆增强。
9. 个性化推荐式知识检索。
10. 复杂企业搜索融合平台。

**当前阶段处理原则：**

1. 优先完成文本 RAG 主链路。
2. 优先保证引用溯源和拒答策略。
3. 优先保证检索、重排、生成、评测和观测形成闭环。
4. 高级能力只在架构上预留扩展可能，不作为当前需求主体。
5. 后续扩展高级 RAG 时，应先评估是否破坏现有主链路稳定性。

### 11.10 边界与约束总结

ForgeRAG 当前阶段的边界与约束可以概括为以下原则：

1. **只做 RAG 后端能力系统**

   当前阶段不做完整 Web 前端、不做完整 SaaS 平台、不做完整企业管理系统。

2. **先完成核心闭环**

   优先完成知识库、文档入库、语义检索、Rerank、带引用问答、Agentic RAG、评测和观测闭环。

3. **不提前复杂化架构**

   当前阶段不引入 Kubernetes、微服务、分布式事务和大型运维平台。

4. **不训练模型**

   使用已有 LLM、Embedding 和 Rerank 能力，重点训练 AI 应用工程化集成能力。

5. **基础安全必须具备**

   即使不做复杂权限系统，也必须保证输入校验、文件限制、密钥保护、异常响应控制和日志安全。

6. **数据职责必须清晰**

   PostgreSQL 管理业务数据，Qdrant 管理向量数据，Langfuse 管理链路追踪数据，日志系统管理运行日志。

7. **评测和观测服务于优化**

   可观测性和自动化评测应帮助开发者发现检索、重排、Prompt、生成和引用中的问题。

8. **高级能力后续扩展**

   多模态 RAG、知识图谱 RAG、多 Agent 协作、长期记忆和复杂权限系统都作为后续扩展方向，不纳入第一版核心范围。







## 12. 验收标准

验收标准用于判断 ForgeRAG 当前阶段的需求是否已经被正确实现。验收标准应与本文档中的功能性需求、非功能性需求、数据需求、接口需求、权限与安全需求、可观测性与评测需求保持对应关系。

ForgeRAG 的验收不应只判断“接口是否能调用成功”，还应判断系统是否具备完整的 RAG 后端闭环、清晰的工程结构、可靠的数据关联、可追踪的执行过程、可评测的质量指标和可复现的部署环境。

本章不定义具体测试代码，而是定义后续开发过程中需要逐项满足的验收条件。

### 12.1 总体验收标准

ForgeRAG 当前阶段的总体验收目标是：系统能够以企业知识库为边界，完成从文档入库到知识库问答，再到 Agentic RAG、自动化评测和链路追踪的完整后端闭环。

**验收标准：**

1. 系统能够正常启动 FastAPI 服务。
2. 系统能够连接 PostgreSQL。
3. 系统能够连接 Qdrant。
4. 系统能够接入或预留 Langfuse 链路追踪能力。
5. 系统能够创建知识库。
6. 系统能够上传文档并保存文档元数据。
7. 系统能够完成文档解析、文本切分和 chunk 保存。
8. 系统能够生成 Embedding 并写入 Qdrant。
9. 系统能够基于指定知识库进行语义检索。
10. 系统能够执行 Rerank 或具备 Rerank 降级策略。
11. 系统能够生成带引用来源的 RAG 回答。
12. 系统能够在上下文不足时拒答或提示无法回答。
13. 系统能够执行基础 Agentic RAG 流程。
14. 系统能够创建评测数据集并运行评测任务。
15. 系统能够记录问答、评测和链路追踪数据。
16. 系统能够通过 Docker Compose 启动基础开发环境。
17. 系统具备基础测试和 CI 检查能力。
18. 系统文档能够说明项目定位、需求范围、接口能力、部署方式和开发阶段。

### 12.2 工程基础验收标准

工程基础验收用于确认 ForgeRAG 是否具备可维护、可配置、可测试、可部署的后端工程基础。

**验收对象：**

1. FastAPI 项目结构。
2. 配置管理。
3. 统一响应。
4. 全局异常处理。
5. 日志系统。
6. 数据库访问基础。
7. 接口文档。
8. 测试与 CI 基础。

**验收标准：**

1. 项目目录能够体现 API、Schema、Service、Repository、Core、Infrastructure 等分层职责。
2. FastAPI 应用可以正常启动。
3. 健康检查接口可以正常访问。
4. 接口文档可以正常访问。
5. 系统配置通过配置文件或环境变量管理。
6. PostgreSQL、Qdrant、模型服务、Langfuse 等配置不硬编码在业务代码中。
7. API 成功响应和失败响应使用统一结构。
8. 参数错误、资源不存在、业务异常和外部服务异常能够通过统一异常处理返回。
9. 结构化日志能够记录关键请求、业务流程和异常信息。
10. Repository 层能够完成基础数据库读写。
11. Alembic 或等价迁移机制能够管理数据库结构变化。
12. pytest 或等价测试工具可以运行基础测试。
13. GitHub Actions 或等价 CI 流程可以执行基础检查。
14. README 或部署文档能够说明本地启动方式。

### 12.3 知识库与文档管理验收标准

知识库与文档管理验收用于确认系统是否具备知识边界管理和原始文档管理能力。

**验收对象：**

1. 知识库管理。
2. 文档上传。
3. 文档元数据。
4. 文档状态。
5. 文档删除。
6. 文档失败原因记录。

**验收标准：**

1. 可以创建知识库。
2. 创建知识库后，PostgreSQL 中生成对应知识库记录。
3. 可以查询知识库列表。
4. 可以查询知识库详情。
5. 可以更新知识库基础信息。
6. 可以删除或禁用知识库。
7. 不存在的知识库 ID 会返回统一错误响应。
8. 可以向指定知识库上传文档。
9. 上传文档后，系统保存文档元数据。
10. 文档元数据至少能够表达文件名、文件类型、文件大小、所属知识库和处理状态。
11. 可以查询指定知识库下的文档列表。
12. 可以查询文档详情和处理状态。
13. 文档处理失败时，可以查询失败原因。
14. 删除文档时，系统能够处理或标记关联 chunk 和向量数据。
15. 不支持的文件类型会被拒绝。
16. 超出大小限制的文件会被拒绝。
17. 文档必须归属于明确知识库。

### 12.4 文档入库链路验收标准

文档入库链路验收用于确认系统是否能够将原始文档转换为可检索的文本块和向量数据。

**验收对象：**

1. 文档解析。
2. 文本清洗。
3. 文本切分。
4. chunk 保存。
5. Embedding 生成。
6. Qdrant 写入。
7. PostgreSQL 与 Qdrant 数据关联。
8. 入库状态流转。

**验收标准：**

1. 系统能够从支持的文档格式中提取文本。
2. 系统能够对解析出的文本进行基础清洗。
3. 系统能够将长文本切分为多个 chunk。
4. chunk 能够保存到 PostgreSQL。
5. chunk 能够关联 knowledge_base_id 和 document_id。
6. chunk 能够保留 chunk 序号或来源位置信息。
7. 系统能够调用 Embedding 模型生成向量。
8. 系统能够将 chunk 向量写入 Qdrant。
9. Qdrant payload 中包含 knowledge_base_id、document_id、chunk_id 等关联标识。
10. 可以通过 Qdrant 检索结果关联回 PostgreSQL 中的 chunk 和文档记录。
11. 文档处理成功后，文档状态更新为处理成功。
12. 文档处理失败后，文档状态更新为处理失败，并记录失败原因。
13. 文档重新处理时，应避免旧 chunk 和旧向量造成脏数据。
14. 删除文档时，应能够同步处理对应 chunk 和向量数据。
15. 文档入库流程不应出现状态不可追踪的长时间卡死。

### 12.5 RAG 检索问答验收标准

RAG 检索问答验收用于确认系统是否能够基于指定知识库完成语义检索、Rerank、Prompt 构造、LLM 生成和引用返回。

**验收对象：**

1. 语义检索。
2. Rerank。
3. Prompt 构造。
4. LLM 调用。
5. 带引用回答。
6. 拒答策略。
7. 问答记录。

**验收标准：**

1. 可以向指定知识库发起问答请求。
2. 问答请求必须包含用户问题和知识库范围。
3. 系统能够将用户问题转换为查询向量。
4. 系统能够在 Qdrant 中按知识库范围检索候选 chunk。
5. 检索结果包含 chunk、相似度得分和来源元数据。
6. 系统支持 top_k、score_threshold 等检索参数。
7. 无检索结果时，系统返回空结果或无法回答提示，而不是异常崩溃。
8. 系统能够对候选 chunk 执行 Rerank。
9. Rerank 不可用时，系统具备降级策略或明确错误响应。
10. 系统能够选择最终上下文并构造 RAG Prompt。
11. 系统能够调用 LLM 生成回答。
12. 回答结果包含答案内容。
13. 回答结果包含引用来源。
14. 引用来源能够追溯到 chunk、文档和知识库。
15. 检索结果不足以支持回答时，系统能够拒答或提示无法回答。
16. 系统能够保存问答记录。
17. 问答记录包含问题、答案、知识库、引用、状态、耗时和 trace_id 的扩展能力。
18. 问答接口返回结构适合前端、业务后端和 Agent 解析。

### 12.6 Agentic RAG 验收标准

Agentic RAG 验收用于确认系统是否具备基于状态和条件分支的动态 RAG 执行能力。

**验收对象：**

1. Agentic RAG 入口。
2. 问题分析。
3. 是否检索判断。
4. 问题改写。
5. 一次检索。
6. 二次检索。
7. 上下文充分性判断。
8. 回答生成。
9. 拒答策略。
10. 节点追踪。

**验收标准：**

1. 系统提供 Agentic RAG 问答入口。
2. Agentic RAG 请求可以指定问题和知识库范围。
3. 系统能够对问题进行初步分析。
4. 系统能够判断问题是否需要检索知识库。
5. 对需要检索的问题，系统能够进入检索流程。
6. 对表达不清晰的问题，系统能够生成改写后的查询。
7. 系统能够执行至少一次语义检索。
8. 系统能够根据首次检索结果判断是否需要二次检索。
9. 系统能够限制二次检索或循环执行次数，避免无限循环。
10. 系统能够判断当前上下文是否足以支持回答。
11. 上下文足够时，系统能够生成带引用回答。
12. 上下文不足时，系统能够执行拒答策略。
13. Agentic RAG 返回结果能够区分成功回答、拒答和执行失败。
14. 系统能够记录每个节点的输入、输出、判断结果和下一步流转。
15. Agentic RAG 节点记录可以关联 trace_id。
16. Agentic RAG 流程设计可以映射到 LangGraph 或等价状态图结构。

### 12.7 自动化评测验收标准

自动化评测验收用于确认系统是否能够管理评测数据集、运行评测任务、保存评测结果，并为后续优化 RAG 效果提供依据。

**验收对象：**

1. 评测数据集。
2. 评测样本。
3. 评测任务。
4. 样本执行结果。
5. 评测指标。
6. 结果查询与对比。

**验收标准：**

1. 可以创建评测数据集。
2. 可以向评测数据集中添加评测样本。
3. 评测样本至少包含问题。
4. 评测样本可以保存参考答案、期望引用或标签信息。
5. 可以创建评测任务。
6. 评测任务可以绑定评测数据集和目标知识库。
7. 评测任务可以指定基础 RAG 或 Agentic RAG 问答模式。
8. 评测任务可以记录检索参数、Rerank 配置、Prompt 版本或模型配置的扩展信息。
9. 系统能够批量执行评测样本。
10. 每个样本执行结果能够保存检索结果。
11. 每个样本执行结果能够保存生成答案。
12. 每个样本执行结果能够保存引用来源。
13. 每个样本执行结果能够保存评测得分或人工评分结果。
14. 评测任务能够统计成功数、失败数和总样本数。
15. 评测任务失败时能够记录失败原因。
16. 可以查询评测任务结果。
17. 可以查看样本级评测结果。
18. 可以通过评测结果对比不同切分策略、检索参数、Rerank 策略、Prompt 版本或问答模式。
19. 评测结果可以关联 qa_record_id 或 trace_id。
20. 低分样本能够支持后续问题定位。

### 12.8 可观测性验收标准

可观测性验收用于确认系统是否能够追踪 RAG、Agentic RAG、模型调用、异常和评测链路。

**验收对象：**

1. Trace。
2. request_id。
3. RAG 链路记录。
4. Agentic RAG 节点记录。
5. 模型调用记录。
6. 异常记录。
7. 耗时记录。
8. 业务记录关联。

**验收标准：**

1. 关键请求能够生成 request_id 或 trace_id。
2. 普通 RAG 问答请求能够记录检索、Rerank、Prompt、LLM 输出和引用来源。
3. Agentic RAG 请求能够记录节点输入、输出、判断结果和状态流转。
4. 模型调用能够记录模型名称、调用状态、耗时和 Token 消耗。
5. Embedding 调用失败时能够记录失败原因。
6. Qdrant 检索失败时能够记录失败原因。
7. Rerank 调用失败时能够记录失败原因。
8. LLM 调用失败时能够记录失败原因。
9. 文档处理失败时能够记录失败原因。
10. 评测任务失败时能够记录失败原因。
11. 问答记录可以关联 trace_id。
12. 评测结果可以关联 trace_id。
13. 开发者可以通过 trace_id 分析一次请求的完整执行路径。
14. Langfuse 或观测工具不可用时，核心问答流程应尽量降级，而不是直接不可用。
15. 日志中包含必要的请求标识，便于关联排查。

### 12.9 安全与配置验收标准

安全与配置验收用于确认系统是否具备基础安全边界，并且不会出现明显配置和密钥管理风险。

**验收对象：**

1. 输入校验。
2. 文件上传限制。
3. 密钥管理。
4. 异常响应。
5. 日志与 Trace 安全。
6. 知识库访问边界。
7. 权限扩展点。

**验收标准：**

1. 接口参数缺失时返回统一参数错误响应。
2. 字段类型错误时返回统一参数错误响应。
3. 非法枚举值不会进入业务流程。
4. 不合理的 top_k、score_threshold 等参数会被拒绝或限制。
5. 上传不支持的文件类型时，系统返回明确错误。
6. 上传超过大小限制的文件时，系统返回明确错误。
7. 空文档或无有效文本内容的文档会被标记为处理失败。
8. 数据库密码不硬编码在代码中。
9. 模型 API Key 不硬编码在代码中。
10. Langfuse Secret Key 不硬编码在代码中。
11. `.env` 不提交到 Git 仓库。
12. `.env.example` 不包含真实密钥。
13. 接口响应不直接暴露内部异常堆栈。
14. 日志和 Trace 不记录 API Key、数据库密码等敏感配置。
15. 检索、问答和评测都能限定知识库范围。
16. 系统为后续用户身份、调用方标识、知识库归属或 API Key 认证预留扩展点。
17. 无可靠上下文时，问答接口能够拒答或提示无法回答。

### 12.11 阶段性验收总结

ForgeRAG 可以按照分阶段建设路线进行阶段性验收，避免所有功能堆到最后一次性检查。

| 阶段                               | 验收重点                                         | 验收结果要求                               |
| ---------------------------------- | ------------------------------------------------ | ------------------------------------------ |
| 阶段 0：项目初始化与工程规范       | 项目规划、目录结构、README、文档规范             | 项目结构清晰，文档能说明项目定位和开发规范 |
| 阶段 1：基础后端框架搭建           | FastAPI、配置、统一响应、异常、日志、健康检查    | 服务可启动，基础接口可访问，错误响应统一   |
| 阶段 2：知识库与文档管理           | PostgreSQL、知识库、文档元数据、状态管理         | 可创建知识库，可上传文档，可查询状态       |
| 阶段 3：文档解析、切分与向量化入库 | 文档解析、chunk、Embedding、Qdrant               | 文档可转为 chunk 和向量，数据可关联        |
| 阶段 4：基础 RAG 检索问答          | 检索、Prompt、LLM、引用来源                      | 可向知识库提问，回答包含引用               |
| 阶段 5：Rerank 与引用溯源增强      | Rerank、上下文筛选、引用增强                     | 检索结果可重排，引用更完整可追溯           |
| 阶段 6：Agentic RAG 流程控制       | 问题分析、改写、二次检索、拒答                   | Agentic RAG 可根据状态动态流转             |
| 阶段 7：RAG 自动化评测             | 评测集、评测任务、评测结果                       | 可批量评测并保存结果                       |
| 阶段 8：可观测性与链路追踪         | Trace、节点记录、模型调用、耗时、异常            | 可追踪 RAG 和 Agent 执行过程               |

### 12.12 最终验收原则

ForgeRAG 当前阶段最终验收应遵循以下原则：

1. **主链路优先**

   系统必须先完成从知识库、文档入库、检索问答到引用返回的核心链路。

2. **结果必须可追溯**

   问答结果必须能够关联引用来源，关键请求必须能够关联 trace_id 或 request_id。

3. **质量必须可评测**

   系统必须支持通过评测数据集和评测任务分析检索质量、回答质量和引用质量。

4. **异常必须可定位**

   参数错误、资源不存在、文档处理失败、模型调用失败和评测失败都应有明确错误信息或失败原因。

5. **工程必须可维护**

   项目结构、配置、异常、日志、测试、文档和部署方式应符合企业级后端项目的基本要求。

6. **范围必须可控**

   验收只覆盖当前阶段的 RAG 后端能力，不把完整 Web 前端、复杂 RBAC、多租户 SaaS、模型训练平台和大规模分布式架构作为第一版验收目标。

7. **开发必须可持续**

   每个阶段完成后都应形成可运行、可测试、可记录的阶段产物，为后续阶段继续扩展提供稳定基础。
