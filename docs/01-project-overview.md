# 1. 项目背景

随着大语言模型在企业知识问答、智能客服、研发辅助、运维支持和内部知识检索等场景中的应用不断增加，企业逐渐需要一种能够结合自身私有知识库的智能问答系统。普通大语言模型虽然具备较强的通用语言理解与生成能力，但它本身并不直接掌握企业内部文档、业务流程、技术规范、历史经验和项目资料，因此在企业实际场景中容易出现回答依据不足、内容不可追溯、知识更新不及时和幻觉回答等问题。

RAG，即 Retrieval-Augmented Generation，检索增强生成，是解决这一问题的重要技术路线。它通过在生成回答之前先从知识库中检索相关文档片段，再将检索结果作为上下文提供给大语言模型，从而提升回答的知识依据、准确性和可追溯性。对于企业级应用而言，RAG 系统不仅要能够完成“文档解析、文本切分、向量化、语义检索、重排、生成回答”这一核心链路，还需要具备知识库管理、引用溯源、权限边界、评测体系、日志追踪、异常处理、接口规范和部署能力。

ForgeRAG 项目正是在这一背景下设计的企业知识库 Agentic RAG 后端系统。项目不以完整 Web 应用为目标，而是聚焦于构建一个可被前端、后端服务或智能 Agent 调用的 RAG 后端能力平台。系统围绕企业知识库问答场景展开，重点解决以下问题：

1. 企业文档分散，缺少统一的知识入库、管理和检索能力。
2. 大语言模型直接回答时缺少企业私有知识支撑，容易产生不准确或不可验证的内容。
3. 普通 RAG 流程通常较为固定，无法根据问题复杂度动态判断是否检索、是否改写问题、是否二次检索或是否拒答。
4. RAG 系统的检索质量和回答质量难以量化评估，缺少自动化评测机制。
5. AI 应用在工程落地时容易忽视配置管理、异常处理、日志追踪、接口规范、测试和部署等企业级后端要求。

因此，ForgeRAG 不只是一个简单的“上传文档并问答”的演示项目，而是一个面向真实企业开发规范设计的后端系统。它将 RAG 核心链路、Agentic RAG 流程控制、RAG 自动化评测、可观测性、向量数据库、关系型数据库、结构化日志、统一异常处理、Docker Compose 部署和 CI/CD 等能力整合到一个完整的学习型工程项目中。

通过该项目，可以系统训练 AI 智能应用开发中的核心能力：既理解 RAG 的算法链路和 Agent 调度逻辑，又掌握后端系统在企业级场景下的工程设计、分层架构、接口规范、数据建模、测试验证和生产可观测性建设。





# 2. 项目定位

ForgeRAG 是一个面向企业知识库场景的 Agentic RAG 后端系统，主要用于提供文档知识入库、语义检索、重排、带引用问答、Agentic RAG 流程控制、自动化评测和链路可观测性等后端能力。项目不以完整 Web 应用为目标，而是聚焦于构建一个稳定、清晰、可扩展、可被调用的 RAG 服务层。

从系统定位上看，ForgeRAG 可以作为企业 AI 应用中的 RAG 后端能力平台。它通过 REST API 对外提供服务，前端页面、业务后端、自动化脚本或智能 Agent 都可以调用该系统完成知识库问答、文档检索、问答生成和评测分析等任务。系统内部则负责封装文档解析、文本切分、Embedding 向量化、Qdrant 向量检索、Rerank 重排、LLM 生成、引用溯源、请求追踪和质量评估等核心能力。

ForgeRAG 的目标不是简单调用大语言模型生成回答，也不是只跑通一个最小化 RAG 示例，而是按照现代企业后端开发规范，构建一个具备清晰架构边界和工程落地能力的 AI 应用后端系统。项目会重点关注分层架构、配置管理、统一响应、异常处理、结构化日志、数据库设计、测试策略、Docker Compose 部署、CI/CD 和可观测性等工程实践，使系统不仅能够运行，而且具备后续扩展、维护和评估的基础。

在学习定位上，ForgeRAG 是一个面向 AI 智能应用软件开发能力训练的综合项目。它既覆盖 RAG 应用的核心技术链路，也覆盖 Agentic RAG 中的流程决策能力，例如判断是否需要检索、是否需要改写问题、是否需要二次检索、是否应当拒答，以及如何根据检索结果生成带引用的可靠回答。

因此，ForgeRAG 的核心定位可以概括为：一个以企业知识库问答为场景、以 RAG 和 Agentic RAG 为技术核心、以现代后端工程规范为实现标准的 AI 应用后端系统。



# 3. 项目目标

ForgeRAG 的项目目标是构建一个面向企业知识库场景的 Agentic RAG 后端系统，使其能够完成从文档知识入库到检索增强问答，再到链路追踪和质量评测的完整闭环。项目既关注 RAG 技术链路的正确性，也关注后端系统在企业级场景下的工程规范和可维护性。

## 3.1 业务目标

ForgeRAG 在业务能力上需要实现以下目标：

1. **支持企业知识库管理**

   系统需要支持知识库的创建、查询、更新和删除，并能够围绕不同知识库组织文档、切分结果、向量数据和问答记录，使不同业务场景下的知识内容具备清晰边界。

2. **支持文档解析、切分和向量化入库**

   系统需要支持常见文档的解析流程，将原始文档转换为可处理的文本内容，并根据合理的切分策略生成文本块。随后通过 Embedding 模型将文本块转换为向量，写入向量数据库，为后续语义检索提供基础。

3. **支持语义检索与 Rerank 重排**

   系统需要支持基于用户问题的语义检索能力，从向量数据库中召回相关文档片段，并通过 Rerank 模型或重排策略对召回结果进行二次排序，提高最终提供给大语言模型的上下文质量。

4. **支持带引用来源的知识库问答**

   系统需要在生成回答时保留检索结果的来源信息，使回答能够附带引用片段、文档来源、知识库信息和相关元数据，降低无依据回答的风险，提高回答的可信度和可追溯性。

5. **支持 Agentic RAG 流程控制**

   系统需要引入 Agentic RAG 思路，使系统不再只是固定执行“检索—生成”的单一路径，而是能够根据用户问题和中间结果动态判断是否需要检索、是否需要改写问题、是否需要二次检索、是否能够直接回答，以及是否应该拒绝回答。

6. **支持 RAG 自动化评测**

   系统需要提供面向 RAG 链路的评测能力，用于评估检索结果相关性、回答准确性、上下文利用情况和引用质量，为后续优化切分策略、检索参数、重排策略和 Prompt 设计提供依据。

7. **支持请求链路追踪与运行观测**

   系统需要记录一次问答请求中的关键执行过程，包括用户问题、检索查询、召回结果、重排结果、Prompt 输入、模型输出、Token 消耗、耗时和异常信息，帮助开发者分析系统行为并定位问题。

## 3.2 工程目标

ForgeRAG 在工程实现上需要达到以下目标：

1. **采用清晰的后端分层架构**

   项目需要基于 FastAPI 构建后端服务，并按照企业级后端开发习惯划分 API 层、Schema 层、Service 层、Repository 层、Core 层和 Infrastructure 层，避免业务逻辑、接口定义、数据库访问和外部服务调用混杂在一起。

2. **使用 PostgreSQL 管理业务元数据**

   系统需要使用 PostgreSQL 存储用户、知识库、文档、文本块、问答记录、评测任务和运行记录等结构化数据，使业务数据具备可靠的持久化能力。

3. **使用 Qdrant 管理向量数据**

   系统需要使用 Qdrant 存储文档文本块对应的向量表示，并通过 collection、payload 和 metadata 组织向量数据与业务数据之间的关联关系。

4. **基于 LangChain 构建 RAG 核心链路**

   系统需要合理使用 LangChain 提供的模型调用、Embedding、文档处理、检索器和链式编排能力，完成文档入库、语义检索和问答生成等核心流程。

5. **基于 LangGraph 构建 Agentic RAG 流程**

   系统需要使用 LangGraph 表达 Agentic RAG 中的状态流转和节点控制，使问题改写、检索决策、二次检索、回答生成和拒答判断等流程具备清晰、可维护的图结构。

6. **接入 Langfuse 实现可观测性**

   系统需要接入 Langfuse 或同类可观测性工具，记录 RAG 和 Agent 执行过程中的 Trace、Span、输入输出、模型调用、评分和评测结果，为系统调试、质量分析和后续优化提供依据。

7. **建立统一的异常处理和响应结构**

   系统需要定义统一的 API 响应格式、业务错误码和异常处理机制，使接口在成功、失败、参数错误、资源不存在、外部服务异常等情况下保持一致的返回结构。

8. **建立结构化日志和配置管理机制**

   系统需要使用结构化日志记录关键业务流程和异常信息，并通过配置文件或环境变量管理数据库连接、向量库地址、模型参数、日志级别和第三方服务配置，避免硬编码。

9. **建立测试、评测和 CI/CD 基础能力**

   项目需要包含单元测试、核心链路测试和自动化评测脚本，并通过 CI/CD 流程完成基础检查，保证系统在持续迭代过程中保持稳定。

10. **支持 Docker Compose 本地部署**

系统需要提供 Docker Compose 部署方案，将 FastAPI 服务、PostgreSQL、Qdrant、Langfuse 等组件统一编排，降低本地开发和演示环境的搭建成本。

通过以上目标，ForgeRAG 最终应当成为一个既能体现 RAG 技术能力，又能体现企业级后端工程能力的综合型 AI 应用开发项目。





# 4. 核心功能范围

ForgeRAG 的核心功能范围围绕企业知识库 RAG 后端系统展开，覆盖知识库管理、文档处理、向量化入库、语义检索、重排、问答生成、Agentic RAG 流程控制、自动化评测和系统可观测性等能力。本章只描述系统需要包含的主要功能模块和职责边界，具体接口设计、数据库设计、向量库设计、Prompt 设计和实现方案将在后续详细设计文档中展开。

## 4.1 知识库管理模块

知识库管理模块负责对企业知识库进行统一管理，是整个 RAG 系统的业务入口。系统需要支持创建、查询、更新和删除知识库，并能够为不同业务场景维护独立的知识边界。

该模块主要负责：

1. 管理知识库基础信息，例如知识库名称、描述、状态和创建时间。
2. 维护知识库与文档、文本块、向量数据之间的关联关系。
3. 支持后续按知识库维度进行文档检索、问答和评测。
4. 为多知识库场景预留扩展能力。

## 4.2 文档管理模块

文档管理模块负责管理进入系统的原始文档，是知识入库流程的起点。系统需要支持文档上传、文档记录保存、文档状态管理和文档删除等基础能力。

该模块主要负责：

1. 接收用户上传的文档文件。
2. 保存文档元数据，例如文件名、文件类型、文件大小、所属知识库和处理状态。
3. 管理文档从上传、解析、切分、向量化到入库完成的状态流转。
4. 支持查询文档列表和文档处理结果。
5. 支持删除文档及其关联的文本块和向量数据。

## 4.3 文档解析与切分模块

文档解析与切分模块负责将原始文档转换为适合 RAG 检索的文本块。该模块是影响检索质量和回答质量的重要环节。

该模块主要负责：

1. 解析常见文档格式中的文本内容。
2. 清洗文档中的无效内容，例如空白字符、重复片段和格式噪声。
3. 按照指定切分策略将长文本拆分为多个文本块。
4. 为每个文本块保留必要的来源信息，例如所属文档、页码、段落位置和 chunk 序号。
5. 为后续 Embedding、检索、引用溯源和评测提供结构化文本数据。

## 4.4 向量化入库模块

向量化入库模块负责将切分后的文本块转换为向量表示，并写入向量数据库。该模块连接文档处理流程和语义检索流程。

该模块主要负责：

1. 调用 Embedding 模型将文本块转换为向量。
2. 将文本块向量写入 Qdrant 向量数据库。
3. 为向量数据附加 metadata，例如知识库 ID、文档 ID、chunk ID、文本内容摘要和来源信息。
4. 保证 PostgreSQL 中的业务数据与 Qdrant 中的向量数据可以互相关联。
5. 支持文档删除或重新入库时同步清理或更新向量数据。

## 4.5 语义检索模块

语义检索模块负责根据用户问题从知识库中召回相关文档片段，是 RAG 问答链路中的核心模块之一。

该模块主要负责：

1. 将用户问题转换为查询向量。
2. 根据指定知识库范围在 Qdrant 中进行相似度检索。
3. 返回与问题语义相关的候选文本块。
4. 支持配置 top_k、score_threshold 等检索参数。
5. 为后续 Rerank 重排和答案生成提供候选上下文。

## 4.6 Rerank 重排模块

Rerank 重排模块负责对语义检索召回的候选文本块进行二次排序，以提升最终上下文的相关性和可用性。

该模块主要负责：

1. 接收语义检索返回的候选文本块。
2. 根据用户问题和候选文本内容计算更精细的相关性得分。
3. 对候选文本块进行重新排序。
4. 过滤低相关性或质量较差的文本块。
5. 为最终问答生成阶段选择更可靠的上下文。

## 4.7 RAG 问答模块

RAG 问答模块负责基于检索结果生成最终回答，是系统对外提供知识库问答能力的核心入口。

该模块主要负责：

1. 接收用户问题和知识库范围。
2. 调用检索模块获取相关文本块。
3. 根据需要调用 Rerank 模块优化上下文。
4. 构造面向大语言模型的 Prompt。
5. 调用 LLM 生成回答。
6. 返回最终答案和引用来源。
7. 在检索结果不足时给出合理的无法回答提示，避免无依据生成。

## 4.8 Agentic RAG 流程模块

Agentic RAG 流程模块负责对 RAG 问答过程进行动态决策，使系统不再局限于固定的“检索—生成”链路，而是能够根据问题类型和中间结果选择不同执行路径。

该模块主要负责：

1. 判断用户问题是否需要检索知识库。
2. 在问题表达不清晰时改写或扩展查询。
3. 根据第一次检索结果判断是否需要二次检索。
4. 判断检索结果是否足以支持回答。
5. 在缺少依据或超出知识库范围时执行拒答策略。
6. 控制检索、重排、生成、反思和拒答等节点之间的状态流转。
7. 为复杂问答场景提供更灵活的流程编排能力。

## 4.9 RAG 自动化评测模块

RAG 自动化评测模块负责对系统的检索质量和回答质量进行量化分析，用于持续优化 RAG 链路。

该模块主要负责：

1. 管理评测数据集，例如问题、标准答案、期望引用和评测标签。
2. 执行批量问答评测任务。
3. 评估检索结果相关性、答案准确性、上下文利用情况和引用质量。
4. 记录评测结果和评分信息。
5. 支持对不同切分策略、检索参数、Rerank 策略和 Prompt 版本进行对比分析。

## 4.10 可观测性与链路追踪模块

可观测性与链路追踪模块负责记录系统运行过程中的关键数据，帮助开发者理解一次 RAG 或 Agentic RAG 请求的完整执行路径。

该模块主要负责：

1. 记录用户问题、检索查询、召回结果和重排结果。
2. 记录 Prompt 输入、LLM 输出、Token 消耗和调用耗时。
3. 记录 Agentic RAG 中每个节点的输入、输出和状态变化。
4. 记录异常信息、失败原因和外部服务调用情况。
5. 支持后续通过 Langfuse 或类似工具分析系统行为、定位问题和优化效果。

## 4.11 系统配置、日志、异常与部署模块

系统配置、日志、异常与部署模块负责保障系统具备基础的企业级后端工程能力。该模块不直接参与 RAG 业务逻辑，但决定系统是否易于维护、部署和排查问题。

该模块主要负责：

1. 提供统一配置管理机制，管理数据库、向量库、模型服务、日志级别和第三方服务参数。
2. 提供统一 API 响应结构，使接口返回格式保持一致。
3. 提供统一异常处理机制，规范业务异常、参数异常、资源不存在异常和外部服务异常。
4. 提供结构化日志，记录关键请求、业务流程和错误信息。
5. 提供 Docker Compose 本地部署方案。
6. 提供基础测试和 CI/CD 配置，为持续迭代提供质量保障。

通过以上功能模块，ForgeRAG 将形成一个完整的企业知识库 RAG 后端系统能力闭环：从知识管理到文档入库，从语义检索到问答生成，从 Agentic 流程控制到自动化评测，再到运行追踪和工程化部署。





# 5. 非目标范围

ForgeRAG 的目标是构建一个企业级规范的 Agentic RAG 后端系统，而不是覆盖所有 AI 平台、知识库平台或企业应用平台能力。为了保证项目范围清晰、开发节奏可控、学习重点明确，当前阶段需要明确以下非目标范围。

## 5.1 不做完整 Web 前端

ForgeRAG 当前阶段不以完整 Web 应用为目标，不开发完整的知识库管理后台、用户控制台、问答页面或可视化运营平台。

系统主要通过后端 API 对外提供能力，前端页面、业务后端、自动化脚本或 Agent 可以根据需要调用这些接口。开发和测试阶段可以使用 FastAPI 自动生成的接口文档、Postman、Apifox、curl 或测试脚本进行接口验证。

当前阶段的重点是 RAG 后端能力建设，包括文档入库、语义检索、重排、问答生成、Agentic RAG 流程、评测和可观测性，而不是前端交互体验设计。

## 5.2 不优先实现复杂权限系统

ForgeRAG 可以在数据结构和接口设计中预留用户、角色、知识库权限、文档权限等字段，但第一阶段不优先实现完整的企业级权限系统。

当前阶段不重点实现以下复杂权限能力：

1. 完整 RBAC 权限模型。
2. 多租户组织架构。
3. 部门级数据隔离。
4. 细粒度文档访问控制。
5. 企业单点登录。
6. 审批流和权限继承机制。

权限相关能力可以在后续版本中逐步增强。第一版可以先以基础用户身份、知识库归属和简单访问控制为主，避免过早引入复杂权限设计导致项目主线偏离 RAG 后端能力建设。

## 5.3 不做大规模分布式架构

ForgeRAG 当前阶段不以高并发、大规模、多地域部署为主要目标，也不优先采用复杂的分布式系统架构。

系统第一版以单体后端服务为主，通过 Docker Compose 编排 FastAPI、PostgreSQL、Qdrant、Langfuse 等基础组件，满足本地开发、课程项目展示和中小规模演示环境需求。

当前阶段不优先引入以下复杂基础设施：

1. Kubernetes 集群部署。
2. 微服务拆分。
3. 服务注册与服务发现。
4. 分布式事务。
5. 消息队列集群。
6. 多副本高可用部署。
7. 分布式链路治理平台。

这些能力属于后续工程扩展方向，不作为当前项目的核心开发目标。

## 5.4 不训练大语言模型

ForgeRAG 不涉及大语言模型的预训练、微调、强化学习或私有模型训练平台建设。

系统会调用已有的大语言模型、Embedding 模型和 Rerank 模型能力，将重点放在如何合理使用模型完成企业知识库问答，而不是训练模型本身。

当前阶段不包含以下内容：

1. 从零训练大语言模型。
2. 对大语言模型进行指令微调。
3. 训练专用 Embedding 模型。
4. 训练专用 Rerank 模型。
5. 构建模型训练平台。
6. 管理 GPU 训练集群。

项目关注的是 RAG 应用工程能力，包括文档处理、检索增强、上下文构造、引用溯源、Agentic 流程控制和质量评测。

## 5.5 不做完整商业化 SaaS 平台

ForgeRAG 不是一个完整商业化 SaaS 知识库平台，不追求覆盖企业知识库产品的全部商业功能。

当前阶段不重点实现以下 SaaS 平台能力：

1. 租户套餐和计费系统。
2. 企业组织架构管理。
3. 完整运营后台。
4. 用户行为分析平台。
5. 工单系统和客户支持系统。
6. 复杂审计报表。
7. 商业化插件市场。
8. 多区域云部署管理。

项目的主要价值在于以企业级工程规范实现 RAG 后端核心能力，帮助开发者理解真实 AI 应用后端系统的架构设计、核心链路和工程落地方式。

## 5.6 不追求一次性完成所有高级 RAG 能力

ForgeRAG 会围绕企业知识库 RAG 系统逐步建设，但不会在第一版中一次性实现所有高级 RAG 技术。

例如，多模态 RAG、知识图谱增强 RAG、复杂长期记忆系统、多 Agent 协作、自动工具调用市场和跨系统知识同步等能力，都可以作为后续扩展方向，而不是当前阶段的必做范围。

当前阶段应优先保证以下核心链路稳定可靠：

```text
文档解析 → 文本切分 → 向量化入库 → 语义检索 → Rerank → 带引用问答 → Agentic RAG 流程控制 → 评测与观测
```

在核心链路稳定之后，再逐步扩展更复杂的高级能力。

## 5.7 范围控制原则

ForgeRAG 的范围控制原则是：优先完成一个清晰、稳定、可运行、可评测、可观测的 RAG 后端闭环，而不是堆叠过多功能。

当前阶段所有功能设计都应服务于以下核心目标：

1. 跑通企业知识库 RAG 后端主链路。
2. 保证系统具备清晰的工程分层。
3. 保证回答具备知识依据和引用来源。
4. 保证检索与回答质量可以被评测。
5. 保证请求执行过程可以被追踪和分析。
6. 保证项目能够通过 Docker Compose 快速部署和演示。

通过明确非目标范围，ForgeRAG 可以避免项目边界失控，将开发重点集中在 RAG、Agentic RAG 和企业级后端工程能力训练上。







# 6. 技术栈概览

ForgeRAG 采用 Python 生态下的现代 AI 应用开发技术栈，围绕 FastAPI、LangChain、LangGraph、Qdrant、PostgreSQL 和 Langfuse 构建企业知识库 Agentic RAG 后端系统。技术选型的核心原则是：优先保证 RAG 主链路清晰、工程结构可维护、系统行为可观测、部署方式可复现，并为后续功能扩展预留空间。

本章只对主要技术栈及其职责进行概览说明，具体配置方式、代码组织、接口设计和落地细节将在后续专项文档中展开。

## 6.1 后端框架：FastAPI

ForgeRAG 使用 FastAPI 作为后端 Web 框架，负责对外提供 REST API 服务。

FastAPI 在项目中主要承担以下职责：

1. 提供知识库管理、文档管理、检索问答、评测任务等 HTTP 接口。
2. 结合 Pydantic 完成请求参数校验和响应数据建模。
3. 提供自动生成的接口文档，便于开发阶段调试和接口联调。
4. 支持异步接口能力，便于后续对接模型调用、向量数据库和外部服务。
5. 作为整个 RAG 后端系统的 API 入口层。

在 ForgeRAG 中，FastAPI 不直接承载复杂业务逻辑。接口层主要负责请求接收、参数校验、调用 Service 层和返回统一响应，具体业务流程会下沉到 Service、Core 和 Infrastructure 等模块中。

## 6.2 RAG 编排：LangChain

ForgeRAG 使用 LangChain 构建 RAG 核心链路，主要用于封装大语言模型调用、Embedding、Retriever、Prompt 和文档处理相关能力。

LangChain 在项目中主要承担以下职责：

1. 对接 LLM，完成问答生成。
2. 对接 Embedding 模型，完成文本向量化。
3. 构建检索器，连接用户问题与向量数据库。
4. 管理 Prompt 模板，使问答生成逻辑更加规范。
5. 支撑基础 RAG 链路的组合与复用。

在 ForgeRAG 中，LangChain 更适合承担“组件能力封装”和“基础链路组合”的角色，例如文档入库链路、普通 RAG 问答链路和 Prompt 管理。对于需要复杂状态流转和条件分支的 Agentic RAG 流程，则交由 LangGraph 负责。

## 6.3 Agentic 流程控制：LangGraph

ForgeRAG 使用 LangGraph 构建 Agentic RAG 流程，用于表达具有状态、分支和循环控制的复杂智能体执行逻辑。

LangGraph 在项目中主要承担以下职责：

1. 定义 Agentic RAG 的状态结构。
2. 编排问题分析、问题改写、检索、重排、回答生成和拒答判断等节点。
3. 根据中间结果决定下一步执行路径。
4. 支持二次检索、反思判断和条件分支。
5. 使复杂 RAG 流程具备清晰、可维护的图结构。

在 ForgeRAG 中，LangGraph 主要用于实现比普通 RAG 更灵活的流程控制。例如，系统可以先判断用户问题是否需要检索；如果问题不清晰，则先改写问题；如果第一次检索结果不足，则尝试二次检索；如果仍然缺少知识依据，则执行拒答策略。

## 6.4 向量数据库：Qdrant

ForgeRAG 使用 Qdrant 作为向量数据库，用于存储文档文本块的向量表示，并支持基于语义相似度的向量检索。

Qdrant 在项目中主要承担以下职责：

1. 存储 chunk 对应的向量数据。
2. 根据用户问题向量执行相似度检索。
3. 通过 payload 保存知识库 ID、文档 ID、chunk ID 和来源信息。
4. 支持按知识库范围过滤检索结果。
5. 为 RAG 问答链路提供候选上下文召回能力。

在 ForgeRAG 中，Qdrant 主要负责向量数据和语义检索能力，而不负责保存完整业务数据。知识库、文档、文本块、问答记录和评测任务等结构化业务数据仍由 PostgreSQL 管理。

## 6.5 关系型数据库：PostgreSQL

ForgeRAG 使用 PostgreSQL 作为主要关系型数据库，用于存储系统中的结构化业务数据。

PostgreSQL 在项目中主要承担以下职责：

1. 存储用户、知识库、文档、文本块等核心业务数据。
2. 存储文档处理状态、问答记录、评测任务和评测结果。
3. 管理业务数据之间的关联关系。
4. 为接口查询、状态追踪和数据管理提供可靠持久化能力。
5. 与 Qdrant 中的向量数据建立业务关联。

在 ForgeRAG 中，PostgreSQL 和 Qdrant 的职责需要明确区分：PostgreSQL 管理业务元数据和结构化数据，Qdrant 管理向量数据和语义检索能力。两者通过 knowledge_base_id、document_id、chunk_id 等标识建立关联。

## 6.6 可观测性：Langfuse

ForgeRAG 使用 Langfuse 作为 LLM 应用可观测性工具，用于追踪 RAG 和 Agentic RAG 请求的执行过程。

Langfuse 在项目中主要承担以下职责：

1. 记录一次问答请求的完整 Trace。
2. 记录检索、重排、Prompt 构造、LLM 调用等关键步骤。
3. 记录输入、输出、耗时、Token 消耗和异常信息。
4. 支持对 RAG 效果进行人工或自动评分。
5. 辅助分析系统行为、定位问题和优化链路。

在 ForgeRAG 中，可观测性不是附加功能，而是 RAG 系统工程化的重要组成部分。通过 Langfuse 记录关键链路数据，可以帮助开发者理解系统为什么这样回答、检索结果是否有效、Prompt 是否合理，以及 Agentic RAG 的状态流转是否符合预期。

## 6.7 数据校验与配置管理：Pydantic / pydantic-settings

ForgeRAG 使用 Pydantic 进行数据模型定义和参数校验，使用 pydantic-settings 管理系统配置。

该部分技术在项目中主要承担以下职责：

1. 定义请求参数 Schema。
2. 定义响应数据 Schema。
3. 校验接口输入数据。
4. 管理数据库连接、向量库地址、模型配置和第三方服务配置。
5. 避免在代码中硬编码环境相关参数。

通过统一的数据校验和配置管理，可以提高系统的稳定性、可读性和环境迁移能力。

## 6.8 数据库访问与迁移：SQLAlchemy / Alembic

ForgeRAG 使用 SQLAlchemy 作为数据库访问工具，使用 Alembic 管理数据库表结构迁移。

SQLAlchemy 在项目中主要承担以下职责：

1. 定义数据库 ORM 模型。
2. 封装 Repository 层的数据访问逻辑。
3. 管理业务数据的增删改查。
4. 支持事务控制和查询组合。
5. 降低业务逻辑与数据库操作之间的耦合。

Alembic 在项目中主要承担以下职责：

1. 管理数据库表结构版本。
2. 记录数据库迁移历史。
3. 支持在不同环境中复现数据库结构。
4. 便于后续修改表结构时进行版本化管理。

对于企业级后端项目来说，数据库结构不应只依赖手写 SQL 文件，而应通过迁移工具进行可追踪、可回滚和可协作的管理。

## 6.9 测试工具：pytest

ForgeRAG 使用 pytest 作为主要测试框架，用于编写单元测试、服务层测试和核心链路测试。

pytest 在项目中主要承担以下职责：

1. 测试核心业务逻辑。
2. 测试文档切分、检索、重排和问答链路。
3. 测试异常处理和统一响应结构。
4. 测试数据库 Repository 层。
5. 为 CI/CD 流程提供自动化质量检查基础。

在 ForgeRAG 中，测试不仅用于验证代码是否运行成功，还应服务于 RAG 质量优化。例如，不同切分策略、检索参数和 Prompt 版本可以通过测试和评测数据进行对比。

## 6.10 部署方案：Docker Compose

ForgeRAG 使用 Docker Compose 作为本地开发和演示环境的主要部署方案。

Docker Compose 在项目中主要承担以下职责：

1. 编排 FastAPI 后端服务。
2. 编排 PostgreSQL 数据库。
3. 编排 Qdrant 向量数据库。
4. 编排 Langfuse 及其依赖组件。
5. 统一管理本地开发环境，降低环境搭建成本。

当前阶段 ForgeRAG 不优先引入 Kubernetes 或复杂云原生部署方案，而是先通过 Docker Compose 保证项目能够快速启动、复现和演示。

## 6.11 CI/CD：GitHub Actions

ForgeRAG 使用 GitHub Actions 构建基础 CI/CD 流程，用于在代码提交和合并时执行自动化检查。

GitHub Actions 在项目中主要承担以下职责：

1. 执行代码格式检查。
2. 执行单元测试。
3. 执行基础构建检查。
4. 检查项目依赖和配置是否可用。
5. 为后续自动化部署预留扩展能力。

在第一阶段，CI/CD 不需要设计得过重，应优先保证每次提交后能够自动发现明显错误，例如测试失败、依赖缺失或代码格式不规范。

## 6.12 技术栈职责总结

ForgeRAG 的技术栈可以按照职责划分如下：

| 技术              | 主要职责                       |
| ----------------- | ------------------------------ |
| FastAPI           | 对外提供 REST API 服务         |
| LangChain         | 构建 RAG 基础链路              |
| LangGraph         | 编排 Agentic RAG 状态流程      |
| Qdrant            | 存储向量数据并执行语义检索     |
| PostgreSQL        | 存储业务元数据和结构化数据     |
| Langfuse          | 记录 Trace、观测链路和辅助评测 |
| Pydantic          | 请求响应建模与参数校验         |
| pydantic-settings | 系统配置管理                   |
| SQLAlchemy        | 数据库访问与 ORM 建模          |
| Alembic           | 数据库迁移管理                 |
| pytest            | 自动化测试                     |
| Docker Compose    | 本地开发和演示环境编排         |
| GitHub Actions    | CI/CD 自动化检查               |

通过以上技术栈，ForgeRAG 可以在保持项目规模可控的前提下，覆盖企业级 RAG 后端系统所需的核心能力：API 服务、业务数据管理、向量检索、RAG 编排、Agentic 流程控制、链路可观测性、自动化测试和可复现部署。





# 7. 系统使用对象

ForgeRAG 是一个面向企业知识库场景的 RAG 后端系统，主要通过 API 对外提供能力。它的使用对象不仅包括最终用户，也包括前端应用、业务后端服务、智能 Agent、开发者、运维人员和评测人员。不同使用对象关注的能力不同，但都围绕知识库管理、文档入库、语义检索、带引用问答、流程追踪和效果评测展开。

## 7.1 前端应用

前端应用可以将 ForgeRAG 作为后端服务调用，用于构建知识库管理页面、文档上传页面、智能问答页面和评测管理页面。

前端应用主要使用以下能力：

1. 调用知识库管理接口，完成知识库创建、查询、更新和删除。
2. 调用文档管理接口，完成文档上传、文档列表查询和文档状态展示。
3. 调用问答接口，向指定知识库提问并展示回答结果。
4. 展示回答中的引用来源，例如文档名称、文本片段、页码和相关元数据。
5. 展示文档处理状态、问答历史和评测结果。

当前阶段 ForgeRAG 不开发完整 Web 前端，但系统需要保证 API 结构清晰、响应格式统一、错误信息明确，方便后续前端应用接入。

## 7.2 业务后端服务

企业内部的其他业务后端服务可以通过调用 ForgeRAG API，将知识库问答和语义检索能力集成到现有业务系统中。

典型使用场景包括：

1. 客服系统调用 ForgeRAG，根据企业文档生成带依据的客服回复。
2. 工单系统调用 ForgeRAG，根据历史问题和知识库内容辅助分析工单。
3. 研发知识库系统调用 ForgeRAG，帮助开发人员检索技术文档、接口规范和故障处理记录。
4. 企业内部搜索系统调用 ForgeRAG，提供比关键词搜索更灵活的语义检索能力。
5. 自动化办公系统调用 ForgeRAG，从制度文档、流程规范和项目资料中生成回答。

对于业务后端服务而言，ForgeRAG 的定位是一个独立的 RAG 能力服务，而不是嵌入在某个具体业务系统中的临时代码模块。

## 7.3 智能 Agent

智能 Agent 可以将 ForgeRAG 作为一个知识检索与问答工具，在执行复杂任务时调用系统提供的检索、问答和引用查询能力。

智能 Agent 主要使用以下能力：

1. 在回答用户问题前调用 ForgeRAG 检索企业知识库。
2. 根据 ForgeRAG 返回的文档片段和引用来源生成更可靠的回答。
3. 在任务执行过程中调用 ForgeRAG 查询项目规范、技术文档、历史经验和业务流程。
4. 将 ForgeRAG 作为外部工具，与其他工具调用能力组合使用。
5. 根据检索结果判断是否继续执行任务、改写问题或提示用户补充信息。

在 Agentic RAG 场景下，ForgeRAG 不只是被动的问答接口，也可以承担智能流程中的知识支撑节点。Agent 可以根据任务上下文决定何时调用 ForgeRAG，而 ForgeRAG 内部也可以通过 LangGraph 编排检索、改写、重排、生成和拒答等流程。

## 7.4 开发者

4. 通过测试用例验证 Service 层、Repository 层和 RAG 核心链路。
5. 通过评测结果优化切分策略、检索参数、Rerank 策略和 Prompt 模板。

对于开发者来说，ForgeRAG 不仅是一个功能项目，也是一个训练 AI 应用工程能力的完整后端实践项目。

## 7.5 运维人员

当前阶段 ForgeRAG 不追求复杂的生产级运维平台，但需要具备基本的可部署、可配置、可观测和可排查能力。

## 7.6 评测人员

评测人员主要关注 RAG 系统的检索质量、回答质量、引用质量和整体效果稳定性。

在 ForgeRAG 中，评测不是后期附加能力，而是 RAG 系统质量建设的重要组成部分。只有能够评测，才能持续优化检索和回答效果。

# 8. 项目亮点

ForgeRAG 不是一个只用于演示的简单 RAG Demo，而是一个围绕企业知识库场景设计的 Agentic RAG 后端系统。项目既关注 RAG 技术链路的完整性，也关注后端系统在企业级开发中的工程规范、质量评测和可观测性建设。

## 8.1 完整的 RAG 核心链路

ForgeRAG 覆盖从文档进入系统到生成最终回答的完整 RAG 主链路：

```text
文档解析 → 文本切分 → 向量化入库 → 语义检索 → Rerank 重排 → Prompt 构造 → LLM 生成 → 引用溯源
```

相比只实现“向量检索 + 大模型回答”的最小示例，ForgeRAG 更强调链路完整性。系统不仅需要能回答问题，还需要能管理知识库、处理文档、追踪文本块来源，并在回答中返回可验证的引用信息。

## 8.2 Agentic RAG 流程控制

ForgeRAG 引入 Agentic RAG 思路，使系统不再固定执行单一的“检索—生成”流程，而是根据问题和中间结果动态决策。

系统会逐步支持以下能力：

1. 判断用户问题是否需要检索知识库。
2. 判断问题表达是否清晰，必要时进行问题改写。
3. 根据首次检索结果判断是否需要二次检索。
4. 根据上下文质量判断是否能够生成回答。
5. 在缺少可靠知识依据时执行拒答策略。
6. 通过状态图组织复杂 RAG 流程，使流程可维护、可扩展、可观测。

这一亮点可以帮助项目从普通 RAG 问答系统升级为具备流程判断能力的智能知识库后端。

## 8.3 企业级后端工程规范

ForgeRAG 不只关注 AI 能力调用，也重视后端工程质量。项目会按照现代企业后端开发习惯组织代码和文档，避免将所有逻辑堆叠在少量脚本中。

项目重点体现以下工程规范：

1. 清晰的分层架构。
2. 统一 API 响应结构。
3. 统一异常处理机制。
4. 配置集中管理。
5. 结构化日志记录。
6. 数据库迁移管理。
7. 单元测试和核心链路测试。
8. Docker Compose 本地部署。
9. CI/CD 自动化检查。
10. 完整的开发文档和接口文档。

通过这些设计，ForgeRAG 不只是能运行的 AI 示例代码，而是一个更接近真实企业项目结构的 RAG 后端系统。

## 8.4 可观测性与链路追踪

RAG 系统的难点不仅在于生成回答，还在于理解系统为什么这样回答。ForgeRAG 会将可观测性作为核心能力之一，而不是后期附加功能。

系统需要记录一次问答请求中的关键过程，包括：

1. 用户原始问题。
2. 改写后的检索问题。
3. 向量检索结果。
4. Rerank 重排结果。
5. Prompt 输入内容。
6. LLM 输出内容。
7. Token 消耗。
8. 请求耗时。
9. Agentic RAG 节点流转。
10. 异常信息和失败原因。

通过链路追踪，开发者可以分析检索结果是否相关、上下文是否有效、Prompt 是否合理、模型回答是否忠实于知识库，以及 Agentic RAG 的决策路径是否符合预期。

## 8.5 RAG 自动化评测能力

ForgeRAG 不只追求功能可用，还需要能够评估系统效果。项目会设计 RAG 自动化评测能力，用于持续分析检索质量、回答质量和引用质量。

评测能力主要体现为：

1. 管理评测数据集。
2. 批量执行问答任务。
3. 评估检索结果相关性。
4. 评估回答准确性。
5. 评估回答是否充分利用上下文。
6. 评估引用来源是否正确。
7. 对比不同切分策略、检索参数、Rerank 策略和 Prompt 版本的效果。

这一亮点可以帮助开发者理解：RAG 项目不能只凭主观感觉判断效果，而应通过数据集、指标和评测流程持续优化。

## 8.6 支持多种调用方接入

ForgeRAG 的定位是 RAG 后端能力系统，而不是单一聊天页面。因此系统设计上会面向多种调用方开放能力。

ForgeRAG 的核心亮点可以概括为：

## 9.11 阶段路线总结

ForgeRAG 的整体建设路线可以概括为：

| 阶段   | 名称                       | 核心目标                   |
| ------ | -------------------------- | -------------------------- |
| 阶段 0 | 项目初始化与工程规范       | 建立项目基础结构和开发规范 |
| 阶段 1 | 基础后端框架搭建           | 搭建 FastAPI 后端骨架      |
| 阶段 2 | 知识库与文档管理           | 完成业务元数据管理         |
| 阶段 3 | 文档解析、切分与向量化入库 | 打通知识入库链路           |
| 阶段 4 | 基础 RAG 检索问答          | 实现最小可用 RAG 问答      |
| 阶段 5 | Rerank 与引用溯源增强      | 提升上下文质量和回答可信度 |
| 阶段 6 | Agentic RAG 流程控制       | 实现动态决策式 RAG 流程    |
| 阶段 7 | RAG 自动化评测             | 建立效果评估和优化能力     |
| 阶段 8 | 可观测性与链路追踪         | 追踪 RAG 和 Agent 执行过程 |
| 阶段 9 | 测试、部署与 CI/CD 完善    | 完善工程质量和部署能力     |

通过以上阶段规划，ForgeRAG 可以从一个基础后端项目逐步成长为具备完整 RAG 链路、Agentic 流程控制、自动化评测、可观测性和企业级工程规范的 AI 应用后端系统。
